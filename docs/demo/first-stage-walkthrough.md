# Демонстрация первого этапа

Сценарий для директора ДИТ, ИТ-лидеров и куратора. Это инструкция воспроизведения, а не отметка о выполненной приёмке. Итог проверки фиксируется в [журнале доказательств](../verification/first-stage-evidence.md).

## Подготовка

Разместите приложение в разрешённой папке, установите среду и зависимости по [гайду запуска](../guides/setup-and-run.md). Настройте локальный реестр кураторов скрытым вводом через `npm run setup:curators`, затем запустите `npm run dev`. Не помещайте коды в этот документ.

Для демонстрации изменения данных используйте вымышленный набор чистого клона либо отдельную разрешённую тестовую копию. Рабочая карта и снимки в `.runtime/imports` сохраняются локально. Публичный RM_UOR содержит код и demo; корпоративную публикацию в нём проверять нельзя.

## 1. Картина директора

1. Откройте рабочее место в режиме читателя.
2. Проверьте полное название и знак DO с подписью «РМ УОР»; дополнительной надписи справа быть не должно.
3. На главной покажите компактную сводку: подтверждено, отклонения, ожидание УОР и отсутствие достаточных фактов. Показатель без данных не считается выполненным.
4. Покажите один основной график ИТ-лидеров. При сравнении показателя должны быть видны названия, фамилии, числовой факт, порог и период. При переключении на статусы виден знаменатель назначений.
5. В очереди действий сначала видны три записи. Откройте остальные только по необходимости.

Если используется подготовленный рабочий набор, явно назовите его историческим срезом 02.10.2026. Дата обновления самого источника неизвестна. Локальный импорт не превращает его в текущую картину.

## 2. От лидера к фактам

Выберите ИТ-лидера, затем цель с имеющимися наблюдениями. Проверьте, что контур лидера сохранился. Покажите факт, официальный и внутренний пороги, прогресс, статус, источник и период. Раскройте детализацию по командам и метрикам; исключения и отсутствие событий должны отличаться от нуля.

Вернитесь в отдельную «Матрицу целей». Покажите фильтр, смену плотности и переход в ячейку. Сверните группу и убедитесь, что это не меняет итоговый состав среза.

## 3. Направления

Откройте отдельный раздел направлений. Проверьте шесть начальных направлений, пустое направление и цели без привязки. Покажите, что исходная категория карты сохранена отдельно.

В режиме куратора создайте вымышленное направление, переименуйте его и отнесите к нему тестовую цель. Сохраните черновик. У цели одно направление либо явно отсутствующая привязка. Общий итог считает уникальные назначения; цели без направления не пропадают. Предварительное отнесение цели требует предметной проверки; неоднозначные рисковые цели не причисляются к МЕТЛА автоматически.

## 4. Самостоятельная настройка

Войдите куратором. В тестовой цели измените описание, внутренний порог, владельца, вес и ссылку. В существующем назначении измените применимость или особенность. Сохраните локальный черновик и проверьте запись в истории.

В базе знаний создайте вымышленный продукт и запись лидера продукта со связью на него. Это отдельная связь, а не переименование ИТ-лидера кластера. Для проверки сохранности остановите службу, запустите снова и найдите черновики.

## 5. Результат и подтверждение

На демонстрационной цели внесите ручной факт с текущим периодом. Значение ниже официального порога должно дать невыполнение. Значение выше порога — ожидание проверки УОР. Подтвердите с содержательным комментарием; затем внесите худший факт и покажите автоматический возврат невыполнения.

Повтор одинакового факта не должен сбрасывать подтверждение из-за времени скачивания. Другой период, порог или ожидаемый состав создаёт новую оценку. Попытка подтвердить устаревший срез отклоняется. Для исторического рабочего файла не подменяйте период ради демонстрации зелёного статуса.

Отдельно покажите кнопку проверки снимка и объясните: «данные и визуализация верны» не означает «цель выполнена».

## 6. Обновления и заглушка

Откройте выбор обновления. Покажите «Только данные УОР», один источник и «Обновить всё». В полном сценарии Git должен завершаться до источников. В истории видны этап, время и итог.

Выберите источник с заглушкой: приложение должно сообщить, что реального обращения к дашборду не было. Старые факты сохраняются. Не демонстрируйте это как отказ корпоративных прав, если реальная проверка доступа не выполнялась.

## 7. Общая публикация

Для тестового набора и настроенного Git отправьте черновик в `release/current`. Проверьте итог операции, а не только уведомление о запуске. Руководитель выпускает merge в `main`; второй клиент получает общую версию без скрытого обновления работающей программы.

Если реальная сеть не проверялась, покажите результат изолированного Git-теста и явно назовите его локальным. При отказе отправки черновик должен остаться. Изменение во время отправки не должно потеряться. В `demo-only` корпоративные данные остаются локальными.

## Завершение

Покажите перечень последующих этапов: реальный сбор и запись сценариев, универсальный Excel-импорт, отчёты и презентации, расписания. Проверку Windows не выдавайте за проверку macOS/СберОС. Заполните только фактически выполненные пункты журнала доказательств.
