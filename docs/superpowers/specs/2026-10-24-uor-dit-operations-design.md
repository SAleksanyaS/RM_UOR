# Рабочее место УОР ДИТ Operations

Мастерспека v0.3 · 24 октября 2026 года

УОР — управление обеспечения развития.

**Статус:** рабочая спецификация с уточнениями заказчика. Сохраняет правила v0.2 для запуска, ролей, публикации и подтверждения; v0.3 уточняет компактный обзор, направления и знак приложения. Реализованность требований подтверждается отдельными демонстрациями, а не наличием этого документа.

## 1. Назначение

Рабочее место помогает директору ДИТ, ИТ-лидерам кластеров и кураторам УОР видеть технологическую повестку: цели, ответственных, владельцев, прогресс, официальные и внутренние пороги, фактические результаты, проблемы, комментарии и решения. На основе выбранного снимка формируются недельные отчёты и презентации.

Приложение работает локально у каждого пользователя. Общие определения, кураторские комментарии и намеренно опубликованные проверенные данные распространяются через Git. Собственный сбор из источников выполняется с правами владельца компьютера.

Основные пользователи:

- директор ДИТ — общая картина, персональный результат каждого ИТ-лидера, проблемные обязательства и требуемые решения;
- ИТ-лидер — свои цели, продукты, команды, отклонения, динамика и подтверждения;
- куратор УОР — настройка целей, источников, методик, справочников, комментарии, проверка и публикация снимков, подтверждение выполнения;
- руководитель УОР — те же операции плюс выпуск общего набора изменений через слияние релизной ветки.

Фамилия ИТ-лидера является первоклассным измерением. Обзор по лидерам и переход в персональную картину обязательны, а не являются второстепенным фильтром.

## 2. Подтверждённые ограничения и первый этап

1. Рабочее название: «Рабочее место УОР ДИТ Operations».
2. Запуск из разрешённой директории командой `npm run dev`, после подготовки окружения по инструкции. Отдельный установщик, иконка и упаковка Python/Node внутрь приложения сейчас не нужны.
3. Целевые ОС: Windows, macOS, СберОС. Общая прикладная логика переносима, работа с браузером, сертификатом, процессами и путями выполняется через платформенные адаптеры.
4. На первом этапе данные уже находятся в базе знаний. Реальный вход в дашборд и получение файла остаются в явно помеченном демонстрационном адаптере.
5. Исходным шаблоном каталога служит предоставленная карта целей: определения, направления, назначения лидерам, ссылки, действия и локальные особенности назначений сохраняются при импорте.
6. Официальные и внутренние пороги, веса, приоритеты и прочие значения куратор заполняет и изменяет самостоятельно. Неизвестные значения не придумываются.
7. Только кураторы УОР имеют право записи в репозиторий. Пользователи получают читательские версии.
8. Кураторские изменения автоматически направляются в текущую релизную ветку; руководитель выпускает накопленное через UI Git-сервиса.
9. При старте приложение проверяет наличие удалённых изменений и уведомляет пользователя. Проверка не равна автоматическому слиянию и не должна скрытно менять выполняемую программу.
10. После операций видны результат, текущая стадия, время стадии и общее время.
11. Нужны общий журнал и понятное описание изменений: цель, вес, состав метрик, назначения, комментарии, опубликованные данные и подтверждения.
12. Нужны опубликованные куратором снимки как дополнительный способ доставки фактов пользователям без исходных доступов.
13. Положительный расчётный результат требует отдельного подтверждения куратора с артефактом либо содержательным комментарием. Невыполнение подтверждается расчётом автоматически.

Не входят в первый этап: реальная автоматизация корпоративного браузера, промышленное расписание выгрузок, универсальный конструктор любых PPTX и промышленная установка. Их интерфейсы предусматриваются, а реализация добавляется отдельными этапами.

## 3. Подходы и выбранное направление

Ранее рассматривались готовые установочные пакеты и запуск из подготовленного окружения. По последнему указанию заказчика выбран второй способ: локальный веб-интерфейс, служба и зависимости в разрешённой директории, пользовательский запуск через npm.

Техническая основа для реализации: React + TypeScript для интерфейса, Node.js для локальной службы, SQLite для локальных фактов и черновиков, отдельный адаптер сборщика. Существующий Python-сборщик Qlik можно подключить после получения и оценки его исходников. Первый демонстрационный адаптер Python не требует, но руководство учитывает будущий сборщик.

Предлагаемые минимумы для первого этапа: Node.js 22.20 или более новая совместимая версия 22.x; npm, входящий в закреплённую поставку Node; Git 2.43 или новее. Python 3.11+ требуется только для будущего Python-сборщика. Реализация закрепляет точные проверенные версии в документации и конфигурации проекта. Подготовка среды может использовать корпоративные аналоги дистрибутивов.

Локальная служба слушает loopback. Браузер отображает интерфейс, а служба выполняет разрешённые файловые операции, Git и расчёты. На первом этапе `npm run dev` поднимает обе части и открывает страницу после проверки готовности. За путями не закрепляются пользовательские имена или Linux-каталоги из существующих примеров.

Из каталога программы ничего не запускается из Downloads, /tmp или другого неразрешённого места. Рабочий корень задаётся при подготовке, проверяется при старте. Локальные изменяемые данные хранятся в разрешённой подпапке `.runtime/` этого корня; альтернативный разрешённый корень задаётся конфигурацией. Он не попадает в Git.

## 5. Общая и локальная информация

### 5.1. Что означает «локально»

Это данные, которые не отправляются в Git автоматически: личные настройки, собственные выгрузки, черновики, состояние авторизации, журналы, неподтверждённые расчёты и временные файлы. «Локально» не означает «скрыто внутри программы навсегда»: выбранный проверенный набор можно отдельно опубликовать.

### 5.2. Что распространяется через репозиторий

```text
catalog/
  manifest.json
  goals/<goalId>.json
  metrics/<metricId>.json
  assignments/<assignmentId>.json
  targets/<ruleId>.json
  entities/<type>/<entityId>.json
  sources/<sourceId>.json
  scenarios/<scenarioId>/scenario.json
  mappings/<sourceId>/<mappingId>.json
  comments/<goalId>/<commentId>.json
  knowledge/<articleId>.md
  report-profiles/<profileId>.json
  templates/<templateId>/
published/
  snapshots/<sourceId>/<snapshotId>/manifest.json
  snapshots/<sourceId>/<snapshotId>/observations.json
  attestations/<goalId>/<attestationId>.json
  evidence/<evidenceId>/
changes/<eventId>.json
```

`catalog/manifest.json` описывает схему и минимальную версию приложения. Номер содержания — commit Git; кураторы не меняют общий числовой счётчик версии при каждой правке. Это уменьшает конфликты независимых изменений.

`published/` содержит только явно выбранные проверенные данные и доказательства. Браузерные профили, коды в открытом виде, ключи, cookies и личные исходные выгрузки не являются допустимыми путями публикации.

Для публичного тестового репозитория рабочие корпоративные данные заменяются обезличенными примерами. Полная исходная карта может быть импортирована локально и опубликована в корпоративном контуре после его настройки.

### 5.3. Локальная область

```text
.runtime/
  app.db
  drafts/
  imports/
  source-artifacts/
  snapshots/
  operations/
  browser-profiles/
  exports/
  backups/
  git-workspaces/
  local-config/
```

Приложение использует разрешённые абсолютные пути с учётом символических ссылок и переходов `..`. `.gitignore` дополняет правило публикации, но основная защита — отдельный каталог и разрешённый список путей.

## 6. Самостоятельная настройка куратором

Все штатные изменения содержимого выполняются через UI: цель, описание, владелец, куратор, назначение, источник, метрика, правило расчёта из поддерживаемого набора, пороги, вес, приоритет, связь справочника, статья и комментарий.

«Не требует изменения программного кода» означает: куратор редактирует данные, приложение сохраняет их, формирует разрешённые файлы и отправляет в релизную ветку. Это не требование к куратору самостоятельно править исходники или JSON.

При вводе данные автоматически сохраняются как локальный черновик. Основная команда «Сохранить и отправить» запускает проверку и публикацию в `release/current`. Изменения объединяются в одну логическую операцию с понятным результатом. При недоступности Git черновик сохраняется, а статус честно говорит «Сохранено на этом компьютере, не отправлено».

Неизвестные значения обозначаются «Не задано» и видны в списке настройки. Можно начать с неполного каталога, но нельзя получить успешное выполнение без достаточной методики и данных.

Новый экземпляр поддерживаемого источника настраивается в UI. Новый протокол, нестандартная авторизация, новый тип интеграции или неизвестный алгоритм расчёта требуют адаптера/расширения программы. Эта граница не скрывается за обещанием универсальной записи любого процесса.

## 7. Роли и вход

Первый экран: «Вы куратор УОР?».

- Ответ «Нет» открывает режим просмотра и личных обновлений источников.
- Ответ «Да» открывает ввод кода, определяет профиль и приветствует по имени.
- Неверный код не открывает кураторские действия. Повторные неверные вводы ограничиваются.

Для Бугаева Александра предусмотрен индивидуальный код, переданный заказчиком отдельно. Он не повторяется в документации и журнале. В реализации проверяется сервером по хешу, а не сравнением открытой строки во фронтенде. Имена и области ответственности задаются реестром кураторов; секретная часть разворачивается локально/корпоративным способом.

Код включает рабочий режим приложения. Реальная публикация требует персонального права Git на запись. Читатель с локально изменённой страницей всё равно не получает право записи в репозиторий. Сессия хранится локально и не считается действительной только по флагу из браузера. Перед отправкой служба проверяет разрешение действия и соответствующий Git-доступ.

Для корпоративного переноса предусмотрен интерфейс замены кодов на корпоративную идентификацию без изменения целей и расчётов. Строгую защиту данных от владельца самого компьютера локальный кодовый вход не обеспечивает; источники и Git остаются границами доступа.

## 8. Ветки, несколько кураторов и выпуск

### 8.1. Порядок

- `main` — утверждённая версия для пользователей.
- `release/current` — общая текущая версия работы кураторов.
- Куратор сохраняет и отправляет общие правки в `release/current` из UI.
- Руководитель УОР просматривает накопленную разницу в Git UI и сливает `release/current` в `main`.
- Читатели узнают об опубликованном обновлении и получают его кнопкой обновления общих данных.
- Куратор может переключать просмотр «Опубликовано» / «Готовится к выпуску». Черновая релизная картина всегда помечена.

Для последовательного выпуска выбирается обычный merge commit. При таком способе после слияния релизная ветка остаётся предком опубликованной версии, и продолжение работы не требует удаления ветки или принудительного сброса. После выпуска клиент включает изменения `main` обратно в релизную ветку обычным fast-forward/merge, если это необходимо. Изменения программы, пришедшие в main, также сохраняются.

В промышленном Git прямую запись пользователей в main ограничивает политика репозитория. Реализация должна работать и при отсутствии прав администрирования у приложения. Для текущего тестового репозитория заказчик отдельно разрешил прямую публикацию подготовленных материалов.

### 8.2. Автоматическое объединение независимых изменений

1. Кураторский черновик хранит базовую ревизию каждого изменяемого объекта.
2. Перед отправкой клиент получает актуальный `release/current`.
3. Изменения разных объектов применяются автоматически к новой базе.
4. Для одного объекта непересекающиеся поля могут объединяться через проверенное трёхстороннее слияние.
5. Создаётся коммит только из разрешённых изменений и их событий.
6. Выполняется обычный push без перезаписи удалённой истории.
7. Если другой куратор успел отправить раньше, клиент получает новую вершину и повторяет объединение. Предлагаемый предел — три автоматические попытки; затем черновик остаётся в очереди с понятным сообщением.

Независимые цели, комментарии, наблюдения и подтверждения имеют разные файлы/идентификаторы. Единый файл «все цели» и единый файл журнала не изменяются каждым куратором.

Совпавшее изменение одного поля не решается правилом «последний победил». Сохраняются обе версии, UI показывает «Нужно согласовать изменение» и различие. Это исключение, а не штатный путь для разных зон ответственности. Программа не применяет `force push` для сокрытия конфликта.

### 8.3. Три разных согласования

Проверка корректности опубликованного снимка, подтверждение выполнения цели и выпуск ветки руководителем — разные события. Руководитель выпускает набор изменений, но не считается автоматически подтвердившим выполнение каждой цели. Куратор может публиковать достоверный красный результат без подтверждения «выполнено».

## 9. Проверка новых версий и понятная история

### 9.1. При запуске

После открытия локального снимка приложение в фоне проверяет удалённый main. До ответа показывает «Проверяем обновления»; при ошибке — «Не удалось проверить» и последнюю удачную проверку. Локальный просмотр остаётся доступен.

При новых коммитах появляется уведомление: какие группы изменений есть, сколько объектов затронуто, от кого и когда, кнопка «Посмотреть изменения» и команда получения. Куратор дополнительно видит новые изменения `release/current`.

Проверка — read-only fetch и сравнение с локальной известной версией. Она не выполняет pull в рабочую программу без действия пользователя и не создаёт коммитов.

### 9.2. Автоматический журнал

Каждое смысловое изменение записывает событие: id, тип, объект, автор, время, предыдущая ревизия, изменённые поля, старое/новое значение для безопасных полей, причина и id операции. Коммит связывает файлы данных и события одной отправкой. Секреты, коды и тела браузерной авторизации не логируются.

Примеры представления: «Вес цели: 2 → 3», «Добавлена метрика», «Назначен владелец», «Комментарий УОР добавлен», «Опубликован проверенный снимок», «Выполнение подтверждено куратором», «Подтверждение устарело после изменения порога».

Клиент также строит структурную разницу версий. Если кто-то правит файл в Git UI без события, изменение всё равно видно как полученное из Git; автор и время берутся из доступной истории, а не придумываются.

После синхронизации показывается сводка изменений с фильтром по своим лидерам, направлениям и целям. Отметка «прочитано» личная. Сохранённый changelog не заменяется только итоговой разницей: если значение меняли несколько раз, история доступна.

## 10. Команды обновления

Вместо единственного непрозрачного действия доступна панель выбора:

| Команда | Что делает |
|---|---|
| Обновить всё | Сначала общие данные из Git, затем все настроенные личные источники и пересчёт |
| Обновить данные УОР | Получает опубликованные цели, справочники, комментарии, проверенные снимки и подтверждения из main |
| Обновить все источники | Запускает сбор по текущей локальной версии каталога, не делает скрытую синхронизацию |
| Обновить выбранные источники | Список с галочками: один или несколько дашбордов/вложений |
| Пересчитать локальные данные | Повторяет нормализацию/расчёт без скачивания и Git |
| Проверить обновления | Проверяет наличие новой версии, ничего не применяет |

В панели видны текущая версия каталога, выбранный охват и список будущих действий. Совместный выбор Git и источников выполняет синхронизацию один раз, затем сбор. Общий источник нескольких целей выгружается один раз на одинаковые параметры.

При отказе одного источника независимые задания могут продолжиться. Каждый результат получает собственную дату и статус; зависимые цели учитывают неполноту. «Обновлено всё» допустимо только при успехе всего выбранного состава.

Если выбран только сбор по старому каталогу, рядом видна известная новая опубликованная версия. Пользователь понимает, по каким правилам он получил результат.

### 10.1. Что видно во время любой операции

Операции чтения, сохранения, отправки, синхронизации, проверки и формирования отчёта имеют id, название, текущий этап, статус, начало/окончание, длительность этапа и всей операции, количество выполненных элементов при известном объёме, итог и доступное действие.

Стадии полного обновления: проверка локальной готовности → получение Git → проверка схемы → получение источников → разбор → сопоставление → расчёт → публикация локального результата → итог. Стадии отправки: проверка изменений → сохранение → получение релизной ветки → объединение → коммит → отправка → подтверждение удалённой версии.

UI не показывает придуманный процент при неизвестном объёме. В таком случае есть текущая стадия и прошедшее время. Время отображается по данным службы и не сбрасывается при перезагрузке вкладки. Повторное открытие подключается к уже запущенной операции. На перезапуске службы незавершённая операция определяется как прерванная, а не успешная.

Итоговые состояния: выполнено, выполнено частично, ошибка, отменено, ожидает действия, сохранено локально/ожидает отправки. Короткое уведомление дополняется постоянной панелью и историей операций.

## 11. Источники и способы получения

Куратор выбирает для измерителя источник и способ получения:

1. Автоматически из дашборда.
2. Получение файла со страницы/вложения.
3. Ручной импорт файла.
4. Значения вручную вносит куратор УОР.

Доставка через опубликованный куратором снимок — дополнительная характеристика происхождения, а не стирание исходного способа. Пользователь видит, например: «Qlik · опубликовано куратором · автор · дата проверки».

Карточка источника содержит адрес, владельца источника, инструкцию доступа, ссылку заявки, способ входа, сценарий и версию, контракт, ожидаемый охват, периодичность, даты и последнюю ошибку. Вручную введённый факт хранит автора, дату ввода, период актуальности, основание и необязательное вложение.

Отчётный период, дата обновления самого источника, время получения и дата кураторской проверки показываются отдельно. Неизвестная дата источника явно обозначается. Скачивание сегодня не делает старые данные актуальными.

### 11.1. Демонстрационный адаптер первого этапа

Поддерживает успешное получение заранее подготовленного набора, отсутствие доступа, устаревший набор, изменение структуры, неполный охват и отмену. Во всех представлениях написано «Демонстрационные данные/демонстрационный источник». Он не открывает реальный корпоративный сайт и не выдаёт задержку по таймеру за фактическую выгрузку.

Процесс после получения артефакта настоящий: проверка, нормализация, сопоставление, расчёт, визуализация и проверка куратором. Позже адаптер заменяется реальным без переписывания этих модулей.

### 11.2. Будущая запись браузерного сценария

Общий сценарий содержит действия, устойчивые селекторы, проверки, параметры, состояние Qlik там, где оно поддержано, ожидаемые выгрузки и контракт. Снимки и DOM служат диагностике. Авторизация остаётся локальной.

Сертификат может подтянуться штатно, но также необходимы сеть, сессия, права на приложение/лист/экспорт и разрешённые политики браузера. Причина «нет прав» показывается только при подтверждённом отказе. Иначе сообщается, какая проверка не прошла, и предлагается диагностика.

Общие сценарии не содержат произвольного исполняемого кода. Корпоративные расширения и разные версии браузера проверяются по матрице совместимости.

## 12. Проверенные данные куратора для остальных пользователей

После загрузки куратор видит таблицу исходного состава и итоговую визуализацию. Команда «Проверил данные и расчёт — отправить» формирует проверенный набор для Git.

Перед отправкой видны состав, период, источники, охват, исключения и будущая аудитория. Отправляется компактный нормализованный набор с происхождением; исходные документы и личные профили не прикрепляются автоматически. Артефакты выбираются отдельно. Для публикации содержимого должны выполняться правила выбранного репозитория и корпоративного контура.

Манифест проверенного снимка: id и хэш данных, источник, параметры отбора, период, даты источника/загрузки, куратор, время проверки, методика и версия правил, охват, ограничения, доказательства и связанная публикация. После отправки в release/current набор имеет состояние «Проверен куратором, готовится к выпуску». Для обычного пользователя он доступен после выпуска в main и синхронизации.

Режимы просмотра фактов:

- **Автоматически:** подходящие актуальные личные данные, иначе совместимый проверенный опубликованный набор.
- **Мои данные:** только собственный источник; проблемы доступа видны без подстановки чужих значений.
- **Опубликовано УОР:** выбранный проверенный набор из Git.

При подстановке всегда видна плашка «Данные куратора <имя>, проверены <дата>, период <период>». Ошибка личного доступа остаётся в диагностике. Значения разных кураторов/периодов не смешиваются в один показатель без явно заданного правила. Для недостающего охвата не создаётся иллюзия полного ДИТ.

Личная новая положительная оценка не наследует подтверждение выполнения от другого снимка. Опубликованное подтверждение применимо только к совместимому проверенному набору. Пользователь может сравнить свои и опубликованные значения.

| Сущность | Основные данные |
|---|---|
| Цель | Устойчивый id, внешний код, название, результат, направление, период, срок, жизненный цикл |
| Ответственность | Владелец цели, куратор УОР, назначенные лидеры и участники |
| Измеритель | Единица, тип цели, база, методика, направление улучшения, период |
| Назначение | Цель/измеритель, тип участника, состав, ответственный, даты действия |
| Целевое правило | Официальный/внутренний контур, уровень применения, значение, период, основание |
| Справочная сущность | Кластер, команда, продукт, услуга, АС/ФП, агент, сотрудник, внешние id и алиасы |
| Наблюдение | Измеритель, участник, период, значение/особое состояние, источник, дата и исходная ссылка |
| Проверенный снимок | Наблюдения, состав, происхождение, проверивший куратор и ограничения |
| Подтверждение выполнения | Цель/назначение, отпечаток оценки, куратор, дата, комментарий/артефакт |

Владелец цели — отвечает за результат. Куратор УОР — ведёт методику, данные и проверку. ИТ-лидер — отвечает за свою область исполнения. Эти роли могут совпадать у человека, но хранятся раздельно.

Имена могут меняться без смены id. Организационные связи и назначения имеют даты действия. Исторический отчёт использует сохранённый состав либо явно выбранный режим пересчёта.

## 14. Прогресс, методики и качество данных

Каждая цель показывает текущий факт, прогресс, официальный и внутренний пороги, разрыв, срок, плановую траекторию при наличии и источник. Прогресс не равен одобрению куратором.

Поддерживаемые измерители: рост, снижение, удержание выше/ниже, диапазон, бинарный результат, вехи, изменение относительно базы, доля участников с выполненными индивидуальными требованиями. Формула прогресса определяется типом; сверхвыполнение не скрывает исходное число.

Для роста/снижения прогресс считается относительно зафиксированных базы и цели; при совпадении базы и цели работает явное правило удержания/бинарного достижения без деления на ноль. Для доли участников используются правильные числитель и знаменатель. Среднее процентов допускается только по заданной методике. Веса, приоритет и обязательность — разные поля.

Официальные и внутренние значения независимы и видны одновременно. Внутреннее значение не заменяет официальное и не меняет его историю. При неизвестных порогах расчёт не придумывает успешность.

Отдельно учитываются: числовой факт, неприменимость, исключение, отсутствие исходных событий, отсутствие данных, неполнота охвата, устаревание и ошибка. «Нет PR», «Нет релизов» и исключения не становятся автоматически нулём или успехом. Команда с нулём применимых данных не получает 100%.

Иерархические итоги выгрузки не суммируются вместе с деталями. Обогащение выполняется по внешним id; неясные соответствия попадают в очередь ручного сопоставления.

Выполнение, темп относительно плана, прогноз куратора и качество данных показываются независимо. Доказанное невыполнение не скрывается отметкой неполноты. Новые данные принимаются атомарно после проверки; предыдущий снимок сохраняется при сбое.

## 15. Подтверждение выполнения куратором

### 15.1. Правило

Расчётный результат положительный → «Выполнено, ожидает подтверждения УОР». Только ответственному куратору доступна команда «Подтвердить выполнение». Обязателен содержательный комментарий или хотя бы один артефакт. Команда проверяется службой, а не только состоянием кнопки.

После подтверждения отображается «Выполнено, подтверждено УОР» с именем, датой, основанием и связью с данными. Для цели удержания дополнительно показывается режим наблюдения и следующая проверка.

Отрицательный расчётный результат → «Не выполнено». При переходе из положительного состояния одновременно появляется отклонение. Подтверждение куратора для отрицательного или промежуточного состояния не требуется.

### 15.2. Отпечаток подтверждённой оценки

Подтверждение привязано к цели/назначению, периоду, фактам, составу участников, порогам и версии методики через `evaluationFingerprint`. Повторное получение идентичного содержимого и параметров не создаёт новое требование подтверждения.

Новый отчётный период либо существенное изменение факта, состава, порога или методики создаёт новую оценку. Если она положительная, требуется новое подтверждение. Если отрицательная, текущий статус автоматически становится отрицательным; прежнее подтверждение остаётся только в истории. Возвращение в зелёное после провала снова требует проверки.

Изменение описания или добавление комментария, не меняющего оценку, само по себе не сбрасывает подтверждение. Вес меняет портфельный итог, но не арифметический факт конкретной цели; это различие сохраняется в журнале.

Неизвестные/устаревшие данные не доказывают текущее выполнение. Старое подтверждение можно увидеть с датой, но оно не делает неизвестную текущую оценку зелёной.

### 15.3. Переходы

| Было / событие | Стало |
|---|---|
| Нет достаточных данных | Нет оценки; последнее подтверждение доступно в истории |
| Подтверждённый отрицательный факт | Не выполнено; никакой валидации куратора не нужно |
| Новый положительный факт | Выполнено, ожидает подтверждения УОР |
| Куратор приложил основание и подтвердил | Выполнено, подтверждено УОР для данного отпечатка |
| Идентичный повтор того же набора | Подтверждение сохраняется |
| Новые существенные данные, по-прежнему положительные | Ожидает подтверждения новой оценки |
| Данные стали отрицательными | Не выполнено и отклонение автоматически |
| Порог/методика изменены | Пересчёт и проверка применимости старого подтверждения |

## 16. Интерфейс и визуализация

Качество интерфейса оценивается по управленческим сценариям и визуальной демонстрации. Набор одинаковых карточек с несвязанными графиками не считается достаточным результатом.

### 16.1. Обзор директора

Главная — компактная сводка, один основной график по ИТ-лидерам и короткая очередь из трёх первых действий с раскрытием остальных. Подробная матрица «Цели × ИТ-лидеры» находится на отдельной странице. Каталог, направления, источники, знания и история имеют собственные разделы. Фамилии видны явно, цели подписываются полными русскими названиями; технический код остаётся дополнительным идентификатором.

График сравнивает факты с порогом выбранной сопоставимой цели либо распределение статусов назначений. По одному срезу не строятся вымышленные временные ряды, диаграмма сгорания или прогноз. Неизвестные и устаревшие данные имеют явные подписи. Развёрнутые методики, таблицы и настройки открываются по запросу, без повторения на главной.

Направления задаются отдельным редактируемым каталогом. Начальный состав: архитектура; производственный процесс; управление технологическим долгом; данные; МЕТЛА; тарифные модели ИТ и SberInfra. Куратор меняет состав и привязку целей через UI. Категории исходной карты не перезаписываются направлениями. Предварительные привязки обозначаются как требующие кураторской проверки; неоднозначная рисковая цель не считается МЕТЛА по догадке. Пустое направление показывает отсутствие назначенных целей. У цели одно направление либо отсутствующая привязка. Общие итоги считают уникальные назначения; цели без направления остаются в общей картине.

Переходы дают последовательную детализацию: направление → цель/лидер → участники. Матрица поддерживает плотность, прокрутку, фиксированные заголовки, поиск и фильтры. Полная виртуализация и автоматический семантический масштаб остаются расширением для больших объёмов; текущую смену плотности нельзя выдавать за их реализацию.

Другие полезные представления: динамика с порогом и планом; сравнительные горизонтальные полосы по лидерам; список изменений за неделю; очередь решений директора; удержание достигнутых целей; неполные/устаревшие источники. Пользователь сохраняет удобную раскладку и набор фильтров.

Нет единственного цвета, смешивающего факт, подтверждение и давность. Используются текстовые статусы, иконки и раскрываемые пояснения. Есть переключение официального/внутреннего контура с одновременным показом расхождения.

### 16.2. Страница ИТ-лидера

Фамилия, область ответственности, цели и прогресс, подтверждения, отклонения, команды/продукты, комментарии УОР, сроки и действия. Директор сравнивает лидеров на сопоставимом составе и видит объяснение разницы охвата. Лидер открывает тот же предметный состав своего профиля.

### 16.3. Цель и настройка

Паспорт, владелец, куратор, назначения, официальные/внутренние значения, измерители, источник, факты, прогресс, даты, история, основания выполнения, комментарии и действия. Режим редактирования доступен куратору; читатель видит структуру без управляющих операций публикации.

Настройка организована пошагово: определение → кому назначено → как измеряется → откуда факт → как отображается → предварительный просмотр → сохранить и отправить. Можно вернуться к локальному черновику.

### 16.4. Рабочая очередь куратора

Положительные оценки без подтверждения; импортированные данные без проверки; неизвестные соответствия; незаполненные пороги/владельцы; устаревшие комментарии; неотправленные правки; отличия релизной версии от опубликованной. Действия ведут к конкретному объекту.

### 16.5. Адаптивность

Проверка как минимум на ноутбуках 1366×768 и Full HD, клавиатурная навигация и достаточный контраст. Для больших матриц требуется последующая виртуализация; содержимое не уменьшается до нечитаемого размера. Мобильный просмотр не обещает мобильный сбор сертификатных источников.

## 17. Комментарии, знания и владельцы

Комментарий относится к цели целиком, назначению, измерителю или участнику. Общий комментарий виден рядом с частным и не подменяет его. Хранятся автор, время, текст, область, срок актуальности и ревизии. Дополнительные поля: причина отклонения, прогноз, следующий шаг, ответственный, срок и решение, требуемое от директора.

База знаний включает структурированные реестры и редактируемые статьи: продукты, команды, ИТ-услуги, кластеры, АС/ФП, агенты, лидеры, владельцы, кураторы, методики и источники. Лидер продукта хранится отдельной связью с продуктом и не заменяет ИТ-лидера кластера. Текущий этап предоставляет редактор структурированных объектов; полноценный редактор статей остаётся последующим расширением. Удаление используемого объекта заменяется архивом/переназначением. Все изменения проходят общий механизм сохранения, журнала и отправки.

Устаревший прогноз не продлевается при обновлении факта. Комментарий «завтра будет зелёное» хранит ожидаемую дату и попадает в проверку после её наступления. Он не меняет фактический статус.

## 18. Отчёты и презентации

Конструктор состава выбирает направления, цели, лидеров, периоды, уровень деталей, комментарии, источники и шаблон. Профиль можно сохранить и опубликовать.

Выпуск документа фиксирует версии фактов, каталога, подтверждений, методики и шаблона. Неподтверждённое выполнение явно помечено. Штатный отчёт не выдаёт «ожидает проверки» за окончательное подтверждение.

Недельный отчёт: изменения, прогресс и отклонения, решения директора, действия со сроками, выполненные подтверждённые цели, удержание и ограничения данных. Экран и документ используют единый расчёт.

Для зрелости исходная презентация служит визуальным и содержательным ориентиром: общий итог, лидеры и подробности, отдельные дополнительные показатели. Динамика требует реальных снимков соответствующих периодов. Отсутствующий источник не восстанавливается догадкой.

Шаблон имеет версию и привязки блоков. Пользователь меняет состав и настройки поддерживаемых блоков. Произвольный загруженный PPTX требует проверки привязок. Переполнение ведёт к переносу, а не потере строк или чрезмерному уменьшению шрифта.

## 19. Первый предметный пример и стартовое наполнение

Карта целей импортируется локально как содержимое каталога, без исполнения скриптов HTML. Сохраняются исходные id, направления, описания, ссылки, назначения и индивидуальные особенности. Новые поля владельца, куратора, прогресса и подтверждения добавляются отдельно. Пустые значения остаются пустыми и доступны куратору для настройки.

Первый расчёт — модель зрелости: пять базовых измерителей и доля команд, исполняющих применимые требования. Дополнительные показатели, показанные отдельно в исходной презентации, не добавляются в базовый состав молча.

Контрольные значения и рабочие наименования из предоставленных корпоративных материалов используются локально. В публичный репозиторий входит самостоятельный обезличенный набор, включающий успех, невыполнение, отсутствие данных, исключение, изменение состава и ожидающее подтверждение. Внешние id команд связываются с лидерами через редактируемый справочник.

## 20. Диагностика и надёжность

Подтверждённое отсутствие прав показывает понятную причину, объект доступа и настроенную ссылку заявки. Таймаут, недоступная сеть, просроченный сертификат, необходимость ручного входа, неполный отбор, изменившийся файл и неизвестное соответствие различаются.

Операция не пишет «нет прав», если проверка этого не доказала. При доступном проверенном снимке предлагается его просмотр с автором/датой; причина собственного отказа остаётся видна.

Применение данных и изменений каталога атомарно. Неверный контракт не повреждает предыдущую картину. Повторы идемпотентны по источнику, параметрам, периоду и содержимому. Двойной клик не запускает две конкурирующие публикации одной правки.

Одна браузерная очередь на профиль, ограниченные повторы временных ошибок, отмена и очистка дочерних процессов. После прерывания доступны результат сделанного и следующий шаг. Подробная диагностика локальна и не публикуется автоматически.

## 21. Безопасность, объём и переносимость

Локальная служба проверяет разрешённый Origin, локальную сессию и роль для изменяющих команд. Файловые пути ограничены рабочим корнем. Параметры Git и процессов передаются без сборки shell-команды из пользовательского текста. Импорт не исполняет HTML, макросы и активное содержимое.

Кураторский код хранится как хеш в локальной секретной конфигурации, ввод не логируется. Git-учётка, браузерный профиль и сертификат не экспортируются со снимком. Режим роли не расширяет доступы источников.

Компактные нормализованные публикации допустимы в Git для исходного объёма. История Git растёт даже после удаления файла из текущей версии. Для больших архивов, многочисленных тяжёлых доказательств или длительной полной истории предусматривается адаптер корпоративного хранилища артефактов; интерфейс снимка сохраняется. Нельзя обещать бесконечный архив Excel внутри Git.

Общие изменения передаются по устойчивым id, отдельным файлам и версионированным схемам. Большие таблицы виртуализируются, расчёты и разбор выполняются вне блокирующего потока UI. Численные профили нагрузки фиксируются после измерения на пилоте.

Переносимость прикладной логики не заменяет фактическую приёмку: отдельно проверяются ОС/CPU, Node/Python, Сбербраузер, сертификат/криптопровайдер, пути, завершение процессов и Git. Особенно проверяются Windows-пути с пробелами/кириллицей и macOS Intel/ARM.

## 22. Запуск и обновление программы

Гайд подготавливает Git, Node/npm, при необходимости Python/venv и корпоративный браузер, затем клонирует проект в разрешённый путь и устанавливает закреплённые зависимости. После этого штатный запуск — `npm run dev` из корня.

Git-синхронизация каталога не должна незаметно заменять работающие модули службы. Если пришли новые исходники, зависимости или минимальная версия схемы, UI показывает необходимость перезапуска и конкретную инструкцию. Установка зависимостей выполняется по гайду в разрешённом каталоге. Работа с несовместимым каталогом останавливается до обновления; старый снимок остаётся доступен для чтения.

Миграции локальной базы делают резервную копию и поддерживают восстановление. Программа не переносит себя в системные папки и не вводит обязательный автоустановщик.

## 25. Уточнение интерфейса от 24.10.2026

Главный обзор — управленческий экран с показателями, диаграммами, сравнением ИТ-лидеров и понятными следующими действиями. Подробная матрица доступна отдельно. Факт, проверка УОР, полнота и актуальность данных показываются раздельно; отсутствие фактов не закрашивается как выполнение. Динамические графики строятся только по реальным сопоставимым историческим снимкам. При единственном периоде интерфейс объясняет, почему динамики пока нет.

В пользовательских заголовках используются полные русские названия целей; технические коды остаются внутренними идентификаторами. Источники ручных фактов называют соответствующую цель человеческим языком. База знаний поддерживает лидера продукта и явную связь с продуктом. Знак приложения — предоставленный переплетённый DO с подписью «РМ УОР», без дополнительной надписи «ДИТ» справа. Актуальный файл — `public/brand/rm-uor.png`.

Публичная основа визуального языка — тема SDDS Service Malachite из Plasma/Salute; внутреннее банковское соответствие требует отдельной проверки при переносе. Цветовые и типографические токены подключаются локально из закреплённой зависимости, без обязательного обращения к внешнему CDN.
