# Обогащение данных целей и происхождение результатов

Дата: 27 октября 2026 года. Статус: подтверждённые требования и предлагаемая логическая модель для обсуждения. Физическое хранение и техническая реализация ещё не определены.

## Подтверждённые требования

Первый этап охватывает цели, данные, аналитику и рабочее место УОР. Отчёты и PowerPoint перенесены на следующий этап; контракт результатов необходимо предусмотреть заранее, чтобы впоследствии использовать те же расчёты.

Исходные данные отчёта отделяются от обогащённых данных и визуализаций. На входе — данные по продуктам. Основная иерархия: кластер с одним лидером кластера → продукты, каждый с одним лидером продукта → при необходимости команды со своими лидерами. Лидер кластера, лидер продукта и лидер команды — отдельные поля, не новые уровни доступа. Обогащение сохраняет исходные бизнес-поля и продуктовые факты.

УОР ведёт справочники; общая версия публикуется через main. Для дополнительной детализации продукт может быть связан с несколькими командами; куратор самостоятельно настраивает эти связи. Пользователи получают опубликованные изменения и используют их при локальной обработке. История оснований и версия применённых сопоставлений сохраняются.

У каждой цели свой источник. Для ОКО у цели фиксированная ссылка на отчёт со всем необходимым набором её продуктов; отдельные источники и карточки источников для каждого продукта не требуются. Штатные режимы: ОКО/Qlik Sense; Excel/CSV, если ОКО не настроено; ручной статус, если нет дашборда и файлов.

При ошибке Qlik используется последний успешный локальный факт с датой и предупреждением, затем, если его нет, — опубликованные данные Git. При отсутствии обоих явно показан пропуск. На Excel автоматическая цель не переключается. Центрального сервера нет.

## Предлагаемая последовательность обработки

Предлагается разделить обработку на пять логических стадий. Они описывают ответственность данных, а не обязательные отдельные сервисы или базы.

1. **Получение исходных данных и происхождения.** Сохраняются исходные бизнес-поля, идентификатор получения, первичный источник, период, выборки, дата данных, время получения и охват. Для файла сохраняется связь с импортом и строкой; для ОКО — с приложением, объектом и строкой полученного набора. Доставка через Git или локальный кэш обозначается отдельно от первичного источника.

2. **Проверка и нормализация.** Проверяются структура, ключи продуктов, единицы, даты, пропуски и ожидаемый состав. Приведение форматов выполняется в производном представлении с сохранением связи с исходными значениями. Ошибочные и непринятые строки получают объяснение; их нельзя незаметно потерять при обработке.

3. **Обогащение справочниками.** Добавляются данные кластера и его лидера, продукта и его лидера; при необходимости — команды и её лидера. Сохраняются версия справочника, правило сопоставления, исходные наименования и ключи. Если не найдена связь, необходимая выбранному срезу или расчёту, строка направляется куратору вместе с причиной; выдуманная принадлежность не назначается. Ошибки настройки также передаются куратору.

4. **Общие расчёты и представления для чтения.** По опубликованной методике формируются показатели и агрегаты для аналитики. Расчёт сохраняет основания: использованные факты, версию сопоставлений, версию методики, полноту и давность. Представления для чтения, или read models, готовят эти результаты под запросы экранов, сохраняя связь с общим расчётом.

5. **Визуализация.** Интерфейс показывает кластеры и продукты с соответствующими лидерами; при необходимости открывает команды продукта с их лидерами. Он объясняет неполноту и позволяет перейти к основаниям. Будущие отчёты используют тот же контракт результатов; отдельные формулы только для PowerPoint не предполагаются.

## Прослеживаемость и защита от искажения фактов

Для результата должен быть доступен путь «показатель → использованные факты → исходная строка», а также применённые версии сопоставления и методики. Для агрегата основанием служит набор строк. Изменения справочника не стирают основания согласованного среза. Периоды действия сопоставлений и правила применения новых связей к прошлым периодам предстоит определить отдельно; автоматический ретроактивный пересчёт не установлен.

До объединения данных со справочником требуется определить, что представляет одна строка факта и какие ключи её различают. Обогащение связями не должно молча размножать исходный факт и увеличивать итог. При необходимости детализации её расчёты должны сохранять происхождение продуктовых фактов.

При подключении источника уточняются идентификатор либо название продукта и ключи сопоставления. Наличие кода продукта или source ID пока не установлено. Конкретные API-запросы и пагинация не выбраны; полнота источника не означает полноту первой полученной порции.

Строки без необходимой связи сохраняют исходные значения и причину проблемы; их наличие отражается в полноте соответствующего среза или расчёта. Отсутствие необязательной детализации до команды само по себе не делает основной срез кластера и продуктов неполным: связь с командой не требуется каждому продукту. Отсутствие необходимого сопоставления не становится ложным нулём. Подтверждение выполнения цели по-прежнему блокируется при отсутствии данных применимого обязательного показателя.

## Принципы из официальных источников

Это внешние принципы; описанная выше локальная модель — наше предложение их применения.

- Microsoft отделяет исходные данные без бизнес-логики от очищенных и обогащённых, затем от готовых бизнес-представлений. Метаданные загрузки поддерживают аудит и повторную обработку. [Microsoft Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/databases/architecture/dataops-mdw).
- dbt описывает fan-out: одна строка соединяется с несколькими и размножает результат. Типы ключей и допустимые соединения ограничивают этот риск. [dbt Joins](https://docs.getdbt.com/docs/build/join-logic).
- В dbt явные ссылки между моделями формируют граф зависимостей; ссылка может закреплять конкретную версию модели. Это пример принципа прослеживаемости преобразований. [dbt ref](https://docs.getdbt.com/reference/dbt-jinja-functions/ref).

Эти принципы не требуют внедрения lakehouse, dbt или новых серверов. По D-111 вся история хранится бессрочно, автоматическое удаление не допускается. Физическое размещение полных исходных файлов и байтов и состав пакета Git ещё проектируются с учётом этого требования. Обязательная публикация всех полных отчётов в Git не установлена.
