# Решения по устройству рабочего места

Начало: 27 октября 2026 года. Обновлено: 28 октября 2026 года. Статус каждой записи показывает, является ли она требованием пользователя или предложением для обсуждения.

## Подтверждённые решения

| Код | Решение | Следствие |
|---|---|---|
| D-001 | На текущем этапе есть локальные ноутбуки и общий Git; единого сервера нет | Сценарии должны работать без общего прикладного сервера |
| D-002 | Git — источник истины для общих настроек, правил, комментариев и согласованных итогов; свежие факты каждый получает напрямую по D-064 | Прямое получение фактов отделено от публикации согласованного среза и локальной кастомизации |
| D-003 | Обычный локальный редактор настраивает отображение и независимые инструменты; панель подготовки УОР доступна кураторам | Все кураторы, включая владельца проекта, равны в приложении; право внешнего слияния задаётся D-009 |
| D-004 | Общие предметные данные видны всем | Фильтр «моя команда» не ограничивает просмотр других команд |
| D-005 | Уточнено: вне области УОР допускаются самостоятельные локальные инструменты и данные | Их конкретный набор для первой версии ещё не выбран; они не входят в общую базу УОР |
| D-006 | Приложение периодически проверяет ветку и предлагает обновиться; получение изменений запускается кнопкой | Обнаружение новой версии и её применение — разные действия |
| D-007 | Исходные версии: Node.js 22.16.0, npm 10.9.2, Python 3.13.5 | Подготовка, зависимости и приёмка должны учитывать эти версии |
| D-008 | Приложение должно быть масштабируемым и переиспользуемым рабочим местом УОР и его клиентов | Нужно определить поддержанные виды целей и расширений, реальные объёмы и измеримые критерии качества |
| D-009 | Официальный выпуск в main выполняет только владелец проекта через merge в Bitbucket | Кураторы могут отправлять ветки предложений и PR; приложение не выполняет итоговый merge |
| D-010 | Допустимые локальные настройки и независимые данные остаются у сотрудника | Общие обновления сохраняют их; настройки представления учитывают изменение и удаление общих объектов |
| D-011 | Нужны общие платформенные механизмы для новых сервисов и интеграций | Для расширений требуется контракт подключения и жизненного цикла |
| D-012 | Значения и статусы целей УОР из Git локально менять нельзя; разрешены фильтры и визуализация без изменения смысла | Локальная настройка порога или подмена официального результата не допускается; содержание обновляется общим выпуском |
| D-013 | Независимые локальные инструменты вне ответственности УОР можно настраивать самостоятельно | Их записи и операции отделены от общего каталога и его публикации |
| D-014 | Уточнено D-064: свежие факты каждый получает напрямую; кураторы проверяют и готовят согласованные итоги | Прежнее ограничение доставки свежих фактов только через Git заменено; опубликованный срез остаётся отдельным |
| D-015 | При отправке накопленного пакета приложение готовит нативный PR Bitbucket, ветку, файлы и сводку | Обновление источника и сохранение записи не создают отдельный PR; частота определена D-065 |
| D-016 | Нужны человеческая сводка «что и как изменится», машинные файлы, замечания и уведомления | Обзор должен отражать фактическое содержание предложения и его влияние |
| D-017 | В приложении нужна единая панель кураторов; владелец проекта равен остальным кураторам | Особых действий владельца и кнопки merge внутри приложения нет; финальное решение выполняется в Bitbucket |
| D-018 | Выбран Bitbucket; операции Git выполняются через консоль от имени сотрудника | Для нативных PR требуется интерфейс конкретного Bitbucket; его редакция, версия и аутентификация пока открыты |
| D-019 | Подтверждено: Write основного репозитория только у кураторов УОР; merge в main только у владельца | Выбор режима приложения уточнён D-120–D-121: закрытый реестр компьютеров и ролей. Реальные права push/merge по-прежнему обеспечивает Bitbucket; право выпуска не добавляет кнопку merge в приложение |
| D-020 | Требуется прослеживать, кто и с какого рабочего места отправляет изменения | Для реализации предложены идентичность Bitbucket, UUID установки, рабочий пакет, операции и версии |
| D-021 | У общей цели ДИТ кластеры и команды могут иметь разные целевые значения и сроки; их настраивает куратор УОР | Условия назначений должны храниться явно; наследование ещё не определено |
| D-022 | ДИТ, кластер и команда имеют собственные показатели, требования и статусы | Неуспех отдельного назначения не отменяет достижение общего показателя ДИТ автоматически |
| D-023 | Куратор УОР самостоятельно настраивает правила расчёта каждой цели | Разные методики одной цели по уровням разрешены D-030; требуются явные проверяемые правила |
| D-024 | Для каждой цели куратор задаёт обязательные показатели, показатели с весами и итоговую формулу; невыполнение обязательного показателя означает невыполнение цели | Высокий итоговый балл не компенсирует известный провал обязательного показателя |
| D-025 | При неполных данных показывается предварительный балл и явный перечень отсутствующих показателей; подтверждение запрещено до получения всех необходимых показателей | Полнота — необходимое условие подтверждения, остальные правила цели также должны выполняться; взвешенный предварительный расчёт определён D-029 |
| D-026 | Куратор может исключить неприменимый показатель для конкретной команды/кластера с причиной и периодом | Исключение применяется только в заданной области и периоде |
| D-027 | После исключения неприменимого показателя веса оставшихся пропорционально нормализуются до 100%; исходные веса сохраняются | Согласованный пример 60/20/20 → исключение последнего → 75/25; это правило не переносится автоматически на пропуски данных |
| D-028 | Если все показатели цели неприменимы в данной команде/кластере, цель «Неприменима», без балла/подтверждения; исключена из процента выполнения и показана отдельным количеством | Пустой применимый состав не означает достижение; результат другой области и общего ДИТ не меняется автоматически |
| D-029 | Для взвешенной методики предварительный балл нормируется по весу полученных применимых данных; покрытие их веса показывается отдельно | Пример 50/50, результат 80% первого и отсутствие второго: предварительно 80%, покрытие 50%; подтверждение заблокировано, пропущенный вес сохраняется для окончательного расчёта |
| D-030 | Для одной цели разрешены разные наборы показателей, обязательность, веса и формулы ДИТ, кластеров и команд | Методика привязана к соответствующей области; публикация общего шаблона действует по D-032 |
| D-031 | Настройка методик должна быть простой и интуитивной для куратора | Последовательный мастер, шаблоны и проверка на примере предложены для оценки; конкретный интерфейс ещё не утверждён |
| D-032 | После публикации новая редакция общего шаблона применяется ко всем использующим его назначениям; самостоятельные методики не меняются | Влияние общего изменения нужно показать в PR; историческая основа расчётов сохраняется |
| D-033 | Для каждой цели куратор выбирает состояние на дату или результат за период, отдельно задаёт срок достижения и частоту обновления данных | Частота сбора фактов и интервал проверки main — разные настройки; пороги давности и календарь ещё уточняются |
| D-034 | При устаревании сохраняем последний результат/дату, показываем предупреждение и уведомляем куратора; новое подтверждение актуального выполнения — после обновления данных | История не меняется; предупреждение о давности отделено от опубликованного результата достижения |
| D-035 | У показателей одной цели могут быть разные частота обновления и допустимая давность; куратор настраивает их отдельно | Актуальность оценивается по каждому показателю и объясняется на уровне цели; время загрузки не заменяет дату факта |
| D-036 | Куратор может вручную исправить факт, сохранив исходное значение, источник, автора и причину; официальное исправление только после merge PR владельцем | Происхождение и история сохраняются; повторная загрузка обрабатывается по D-037 |
| D-037 | При повторном импорте того же факта сохраняем принятое исправление и показываем расхождение куратору; он оставляет исправление либо предлагает новое значение через PR | Новое официальное значение появляется только после merge владельцем; повторный импорт не стирает принятую корректировку |
| D-038 | Справочники команд, кластеров, продуктов, ИТ-услуг и руководителей ведёт УОР | Изменения относятся к общему содержимому и проходят публикацию; новые команды получают цели по D-039 |
| D-039 | Новая команда автоматически получает все цели своего кластера | Создание команды и назначений входит в PR; командные настройки задаются по D-040, дата действия ещё уточняется |
| D-040 | Новая команда по умолчанию получает командный шаблон каждой назначенной цели; куратор может отдельно настроить методику, целевые значения и срок | Связанный шаблон и самостоятельная методика сохраняют различимую семантику |
| D-041 | Команды закреплены за своими кластерами; перевод между кластерами не выполняется | Сценарии переноса и перераспределения фактов между кластерами в текущем объёме не нужны |
| D-042 | У цели есть основной куратор УОР и со-кураторы | Это распределение ответственности, а не ограничение равных возможностей панели; адресаты уведомлений определены D-056, ручная смена основного — D-062 |
| D-043 | Кураторы вручную ведут планы и состояние работ в приложении, которое служит единым местом ведения | Общая принятая версия распространяется через PR/main; обязательная интеграция с внешним трекером не выбрана |
| D-044 | Нужен полноценный список работ и вех с исполнителями, сроками и состояниями | Детализация подтверждена; модель ответственности и связи работ ещё уточняются |
| D-045 | Работа с планами должна быть простой, понятной и опираться на клиентские пути | Сценарии и критерии удобства разрабатываются; интерфейс и числовые нормативы ещё не утверждены |
| D-046 | Куратор настраивает одного ответственного от кластера на несколько команд либо отдельных ответственных по командам | Отдельный человек в каждой команде не обязателен; назначения ответственности не меняют права доступа и авторство |
| D-047 | Куратор заранее отмечает риск срыва, причину, прогнозную дату завершения и требуемую помощь; плановый срок сохраняется отдельно | Риск виден до просрочки; изменение прогноза не заменяет плановый срок |
| D-048 | Нужен отдельный запрос решения: что решить, кто должен решить, до какой даты и какое решение принято; всё ведёт куратор | Запрос связан с работой; бизнес-решение и merge PR с его записью различаются, новых прав руководителя не появляется |
| D-049 | Куратор связывает зависимые работы, в том числе разных команд; видны препятствия, ответственные и цели под угрозой | Направление зависимости должно быть понятно; автоматический перенос дат не выбран |
| D-050 | Приложение показывает всю затронутую задержкой цепочку; новые прогнозные даты связанных работ куратор задаёт вручную после проверки | Плановые сроки сохраняются отдельно; показ влияния задержки сам по себе не меняет прогнозы |
| D-051 | Одна работа хранится одной записью и может быть связана с несколькими целями; состояние обновляется один раз и отображается во всех связях | Достижение каждой цели оценивается по её методике; завершение общей работы не означает достижения всех связанных целей |
| D-052 | При завершении работы куратор обязательно кратко описывает результат; подтверждающую ссылку или файл добавляет при необходимости | Отметка завершения требует результата, необязательное подтверждение не становится общим запретом на завершение |
| D-053 | Состояния работы: Запланирована, В работе, Приостановлена, Выполнена, Отменена; причина паузы/отмены обязательна | Риск и блокировка отображаются отдельно от состояния; полный граф переходов ещё уточняется |
| D-054 | Куратор может вернуть выполненную работу в «В работе» с причиной; прежнее завершение сохраняется в истории, изменение публикуется через PR | Возврат является новой редакцией работы; прежний результат не стирается |
| D-055 | При отмене блокирующей работы показывается предупреждение; куратор указывает заменяющую работу либо снимает зависимость с причиной | Отмена не означает получения ожидаемого результата; зависимая работа не закрывается автоматически |
| D-056 | Уведомления внутри приложения: риски/блокировки — основному куратору и ответственному за работу, запрос решения — адресату; остальные могут подписаться на цели | Маршрутизация внимания не меняет доступ к общим данным; повторы определены D-057 |
| D-057 | Новое событие — одно уведомление; открытые риски, блокировки и просроченные решения — раз в день с настройкой частоты куратором; после перерыва актуальное напоминание без накопления повторов | Дубликат события отличается от планового напоминания; календарь повторов определён D-058, момент повтора ещё уточняется |
| D-058 | Повторные ежедневные напоминания показываются только по рабочим дням общего календаря УОР; календарь настраивает куратор | Это календарь повторов; правила сроков, границ периодов и давности фактов не определяются им автоматически |
| D-059 | Для общих сроков, границ дня и напоминаний используется единый часовой пояс Москвы — Europe/Moscow | Локальный пояс ноутбука не меняет общую интерпретацию; крайний момент срока определён D-060 |
| D-060 | Срок датой действует до конца указанного дня по Москве, просрочка с 00:00 следующего; выходной не переносит срок, изменение куратором через PR | Календарь повторных напоминаний не сдвигает сроки; сравнение идёт с началом следующего дня |
| D-061 | Ежедневное напоминание по умолчанию в 09:00 по Москве; куратор может менять время; при позднем запуске показывается актуальное напоминание | Сохраняются рабочие дни календаря УОР и отсутствие накопленных повторов; фоновой службы это решение не вводит |
| D-062 | Основного куратора при необходимости меняют вручную; временное замещение на период с автоматическим возвратом не выбрано | Назначение публикуется через PR/main, уведомления следуют принятому назначению; авторство и права не переписываются |
| D-063 | Поддержаны ОКО/Qlik, Excel/CSV и ручной ввод; распределение штатных способов по целям уточнено D-074 | Это способы для разных случаев, не требование конкурирующих источников; прав читателям на ручную правку не добавлено |
| D-064 | Каждый сотрудник получает свежие данные напрямую; Git служит для общих настроек, комментариев и согласованных итогов | Оперативный расчёт по общей принятой методике отделён от согласованного среза; обновление факта не требует PR |
| D-065 | PR готовится накопленным пакетом по важному событию либо один-два раза в неделю | Изменения и комментарии накапливаются; прежняя рекомендация PR на каждое небольшое изменение заменена |
| D-066 | При нехватке данных требуется явное отображение неполноты либо исключение из расчёта | Отсутствие не равно нулю или N/A; блок подтверждения для отсутствующего обязательного показателя определён D-069, прочие правила ещё уточняются |
| D-067 | При недоступности прямого получения предусмотрен резервный путь через опубликованные данные репозитория | Git-пакет содержит данные для резервного чтения с датой/областью/полнотой; приоритет успешного локального результата определён D-068 |
| D-068 | При отказе источника сохраняем последние успешно полученные локальные данные с датой и предупреждением; если локальных нет — данные репозитория | Чтение кэша/Git не обновляет дату факта; неуспешный импорт не заменяет последний успешный результат |
| D-069 | Отсутствие применимого обязательного показателя блокирует подтверждение выполнения, даже если предварительный балл рассчитан без него | Исключение из предварительного расчёта не отменяет обязательность; согласованное N/A с причиной/периодом — отдельный случай |
| D-070 | Каждый куратор отправляет отдельный накопленный PR за цикл публикации; владелец принимает пакеты независимо или отправляет на доработку | Общий PR всех кураторов на выпуск не выбран; сохраняется ритм по событию либо один-два раза в неделю |
| D-071 | При подготовке пакета разные поля совмещаются в предпросмотре, разные значения одного поля требуют явного выбора куратора по сравнению «было / main / моё» | После выбора повторяются проверки и сводка; итоговый merge остаётся в Bitbucket |

## Предложения по разделению данных

**Общее опубликованное содержимое.** Каталог, методики, назначения, общие комментарии и согласованные результаты приходят из Git. Для отображения сохраняется происхождение: версия публикации, автор и время. Точный состав публикуемых фактов ещё предстоит согласовать.

**Оперативные факты УОР.** Каждый сотрудник получает свежие данные напрямую при доступности источника. Штатный способ определяется случаем цели по D-074: ОКО, файл при отсутствии настроенного ОКО или ручной статус без дашборда/файлов. Текущий расчёт использует общую принятую методику и явно показывает область, период, полноту и давность. Обновление источника не является локальной ручной подменой значения из согласованного среза и не переписывает этот срез. При отказе сохраняется последний успешный локальный результат с датой и предупреждением; если его нет — соответствующие опубликованные данные Git. Получение из резерва не делает факт свежим.

**Локальные настройки представления УОР.** Фильтры, сортировка, графики и состав представления сохраняются на ноутбуке. Они не меняют официальные значения, статусы и правила. Отображение выбранного среза должно обозначать его область. При обновлении сохраняются применимые настройки; ссылки на изменённые или удалённые объекты требуют обработки.

**Независимые локальные инструменты.** Имеют собственные данные и настройки, остаются на ноутбуке и не входят в общую базу УОР. Их редактирование не даёт права записывать в официальный каталог. Конкретный набор инструментов первой версии ещё не определён.

**Подготовка публикации УОР.** Кураторы проверяют факты, накапливают изменения, комментарии и согласованные итоги в рабочем пакете. Он публикуется по важному событию либо один-два раза в неделю и не меняет согласованный срез до merge в main. Оперативные данные читателя могут обновляться независимо. Независимые локальные источники других инструментов имеют собственный жизненный цикл.

**Версия программы.** Получение новых общих данных и изменение исполняемого кода требуют разных проверок совместимости. В интерфейсе это может быть одно понятное действие; внутри необходимо сохранить пользовательские данные и завершить активные операции.

Эти области описывают владение, происхождение и обновление содержимого. Локальное редактирование отделено от публикации в общий Git.

## Уточнение ранее рассмотренных вариантов кастомизации

Ранее рассматривались локальные переопределения общего каталога и полная самостоятельная копия. Уточнение D-012 исключило оба варианта для официальных значений и статусов. Новый вопрос — сохранение настроек представления и независимых модулей при обновлении защищённой общей базы.

Предлагаемая структура хранения: принятая общая версия УОР; отдельные настройки её отображения; самостоятельные пространства данных локальных модулей. Подробные схемы и интерфейсы будут согласованы в проектном решении. Подготовка официального изменения является отдельным процессом выпуска.

## Панель кураторов и согласование

Панель одинакова для всех кураторов, включая владельца проекта. Предлагаемые разделы: источники и свежесть данных; рабочие пакеты и проверки; подготовка комментариев и подтверждений; PR и замечания; уведомления и история операций. Окончательный состав экранов ещё не согласован.

Предлагаемый процесс:

1. Куратор получает актуальную общую основу и готовит законченный набор фактов, комментариев или подтверждений в рабочем пакете.
2. Приложение проверяет форматы, ссылки, периоды, методику, полноту и основания подтверждений, показывает состав отправки и ожидаемое влияние.
3. По действию «Отправить на согласование» Git-команды формируют commit и ветку предложения от имени сотрудника, затем создаётся нативный PR Bitbucket. Самостоятельное автосохранение черновика не обязано создавать новый PR.
4. В приложении показаны автор, затронутые цели, изменения «было → станет», проверки, замечания и ссылка на PR. Аналогичная понятная сводка включается в описание PR.
5. Замечания Bitbucket отображаются куратору. Доработка обновляет существующий PR; окончательное отклонение отличается от возврата на исправление.
6. Владелец проверяет PR и выполняет финальное слияние в интерфейсе Bitbucket. Приложение не принимает это решение автоматически.
7. Приложения обнаруживают результат: автор получает уведомление о merge/отклонении, остальные — о доступном обновлении main. Новая общая картина принимается с сохранением локальных настроек и независимых данных.

Пользователь заменил рекомендацию частых PR пакетной публикацией: по важному событию либо один-два раза в неделю. Каждый куратор накапливает свой пакет изменений и комментариев и отправляет отдельный PR за цикл; приложение показывает его состав и влияние перед отправкой. Владелец принимает пакеты независимо или отправляет на доработку. Общий PR всех кураторов не выбран. Отдельное получение фактов или сохранение записи PR не создаёт.

Рабочий пакет должен содержать машинные данные и их схему, идентификаторы, исходную ревизию, ссылки и зависимости, период, происхождение и основу расчёта, необходимые подтверждения и хеши приложенных файлов. Точный формат файлов определяется в спецификации. Двоичный файл всей локальной БД не является форматом слияния предложений.

Сводка влияния строится по реальным изменениям, а автор отдельно поясняет причину. При изменении main, фактов или методики предложение перепроверяется; старое подтверждение и старый обзор не переносятся автоматически на новый результат. В частности, текстовый merge без конфликта не гарантирует предметную совместимость.

Поддерживаемые операции Bitbucket-адаптера: создать или найти существующий PR рабочего пакета, прочитать список/состояние/замечания/проверки, обновить описание и перейти к PR. Команды работы с замечаниями уточняются при проектировании. Итоговый merge не входит в операции пользовательского интерфейса приложения. Подключение использует учётную запись самого сотрудника; общая учётная запись владельца для автоматизации не предполагается.

Официальные материалы для технического уточнения: [REST API Bitbucket Data Center](https://developer.atlassian.com/server/bitbucket/rest/v1000/api-group-pull-requests/), [права веток Bitbucket Data Center](https://confluence.atlassian.com/bitbucketserver/using-branch-permissions%20-776639807.html). Они показывают возможности конкретной редакции и не устанавливают версию корпоративной системы. Обычный [git request-pull](https://git-scm.com/docs/git-request-pull) формирует текст запроса; это не создание объекта PR в Bitbucket.

## Автоматическое определение доступа

Действующая схема по D-120–D-123: hostname определяет запись закрытого реестра, из неё берутся имя и роль viewer/curator/chief. Панель подготовки одинакова у curator и chief, итоговый merge остаётся в Bitbucket. Прикладная роль не выводится из admin/Write аккаунта и не требует совпадения аккаунта с профилем компьютера.

Для фактических операций сохраняется D-019: Write основного репозитория только у кураторов УОР, итоговый merge в main только у владельца. Это права внешней системы, отдельно от реестра режимов приложения; реестр обслуживает только главный УОР. Прежняя рекомендация связать его с аккаунтами Bitbucket сейчас не применяется по D-123.

По [официальным правам Bitbucket Data Center](https://confluence.atlassian.com/security/using-repository-permissions-1409092189.html) Read позволяет создавать PR, а Write допускает merge при отсутствии других ограничений. [Права веток](https://confluence.atlassian.com/bitbucketserver/using-branch-permissions%20-776639807.html) дополнительно регулируют действия над main. Точный механизм чтения прав и ограничений проверяется на корпоративной версии; обычное Git-подключение не возвращает полный набор прав Bitbucket.

Git и Bitbucket авторизуют фактические операции своим механизмом; их отправитель сохраняется в аудите независимо от имени в профиле hostname. Сбой API PR не меняет прикладную роль и не удаляет черновики. Проверка режима относится к hostname, установке и контексту репозиториев; перед отправкой требуется свежая проверка служебного реестра, без сопоставления аккаунта с его записью.

По D-098 при недоступности Git разрешена локальная подготовка и редактирование черновиков куратора. Восстановление связи запускает проверку актуального доступа и состояния main перед отправкой PR. Незавершённые локальные изменения сохраняются; само восстановление связи не является командой отправки. По D-099 описанный сценарий одновременного пересечения правок не ожидается пользователем; отдельный интерфейс его разрешения сейчас не прорабатывается. Это не отменяет проверки перед отправкой.

## Предложение по происхождению изменений

| Уровень | Что сохраняется | Что это позволяет установить |
|---|---|---|
| Отправитель | Идентификатор и учётная запись аутентифицированного автора PR Bitbucket | Под какой учётной записью отправлено предложение |
| Подготовка фактов | Участники сбора, проверки и подтверждения | Кто выполнял разные действия, если они распределены между кураторами |
| Рабочее место | UUID установки и понятная подпись | Из какого экземпляра приложения подготовлен пакет |
| Работа | Идентификаторы операций и рабочего пакета, время, цели, периоды и поля | Какие действия связаны с предложением |
| Редакция | Основание main, точная версия предложения и хеш содержимого | Что именно проверялось и предлагается принять |
| Выпуск | PR, результат согласования, запись merge и её участник в Bitbucket | Как предложение стало частью официальной версии |

UUID рабочего места обозначает установку приложения. При подготовке другой станции создаётся новый UUID; исторические записи сохраняют прежнее происхождение. Подпись вроде «Рабочий ноутбук Анны» предназначена для удобства просмотра, а не для аппаратной аттестации. Чистая поставка не содержит идентичность чужой установки.

Метаданные git author/committer сохраняются в истории, но основным подтверждением отправителя служит аутентифицированная учётная запись Bitbucket. Настраиваемые [git user.name/email](https://git-scm.com/docs/git-config#Documentation/git-config.txt-username) не заменяют её. Автор PR не обязательно является единственным участником сбора и проверки данных; эти действия фиксируются отдельно.

В общей панели видны отправленные предложения и события Bitbucket. Локальная работа до отправки остаётся на станции; присутствие всех сотрудников онлайн не определяется через Git. Сопоставление ревизий main и предложений позволяет обнаруживать пересечение изменений при подготовке и согласовании.

## Цель ДИТ и условия назначений

Подтверждено существование общей цели ДИТ и различных требований/сроков для кластеров и команд. Предлагается сохранять общую идентичность цели, а область назначения, её целевые значения и официальный срок описывать отдельными данными. План и прогноз остаются самостоятельными сведениями.

Подтверждено: ДИТ оценивается по своему общему показателю, кластеры и команды — по своим. В согласованном примере ДИТ 92% при требовании 90% достигает общего порога, а кластер 88% при требовании 95% своего порога не достигает. Нельзя автоматически подставлять правило «все команды должны выполнить» или переносить зелёный результат ДИТ на все назначения.

Правила расчёта каждой цели настраивает куратор УОР. Пользователь подтвердил сочетание обязательных показателей и показателей с весами и настройку формулы итога. Известное невыполнение обязательного показателя определяет невыполнение цели независимо от балла.

При отсутствии части данных пользователь выбрал предварительный балл с явным перечнем недостающих показателей. Подтверждение выполнения запрещено до получения всех необходимых показателей и выполнения остальных условий цели. Известный провал обязательного показателя сохраняет значение независимо от полноты остальных данных.

Неприменимый показатель куратор исключает из расчёта для конкретной команды или кластера, указав причину и период. Это отдельное правило применимости, не подстановка для пропущенных данных. Исключение и исходная методика хранятся раздельно и проходят общий процесс выпуска.

После исключения неприменимого показателя согласована пропорциональная нормализация оставшихся весов до 100% при сохранении исходных настроек. Для оставшегося применимого показателя effectiveWeight = originalWeight / sum(оставшихся применимых исходных весов) × 100%, если сумма положительна. Пример 60/20/20 с исключённым последним показателем даёт 75/25. Отсутствующий показатель по этому правилу неприменимым не становится.

Если все показатели цели неприменимы для команды/кластера, согласован статус «Неприменима», без балла и подтверждения выполнения. Такая цель исключается из процента выполнения этой области и учитывается отдельным количеством. Результат других областей и общей цели ДИТ не меняется автоматически.

Для взвешенной методики согласован предварительный средневзвешенный балл по известным применимым показателям и отдельное покрытие всего применимого веса. При положительных знаменателях P = sum(w_i × r_i по известным применимым) / sum(w_i по известным применимым); C = sum(w_i по известным применимым) / sum(w_i по всем применимым) × 100%. r_i — нормированное выполнение показателя в процентах, отдельное от сырого факта. Пример 50/50 с первым результатом 80% и отсутствием второго даёт P = 80%, C = 50%; подтверждение запрещено. Отсутствующий показатель сохраняет ожидаемость и вес. По D-081 нормированное выполнение и общий балл могут превышать 100%; веса и покрытие не являются перевыполнением.

Разные наборы показателей, обязательность, веса и формулы одной цели на уровнях ДИТ, кластера и команды подтверждены. Пользователь требует простой и интуитивной настройки. Для обсуждения предложены выбор области, короткие последовательные шаги, повторное использование шаблонов и проверка примера с понятным объяснением. Интерактивный макет пользователь пока отложил, интервью продолжается вопросами.

Для использования общего шаблона подтверждено автоматическое получение его новой редакции после публикации всеми связанными назначениями. Самостоятельные методики остаются без изменений. Подготовка PR должна показать затронутые области и влияние на результаты и подтверждения. Исторические правила и отчётные снимки сохраняют прежнюю основу; обновление шаблона не обновляет возраст исходных фактов.

Открыты нормирование исходных единиц в результат показателя, другие конкретные формулы, предварительный расчёт невзвешенных формул, округление, нулевая сумма весов и наследование отдельных требований/сроков между уровнями. Обязательность показателя и его вес пока не объявлены взаимоисключающими свойствами. Расчёт и подтверждение УОР остаются разными стадиями.

## Справочники и назначения

Подтверждено ведение справочников силами УОР. Приложение должно позволять поддерживать команды, кластеры, продукты, ИТ-услуги и руководителей, сохраняя идентичность объектов и исторические основания расчётов. Официальные изменения публикуются общим процессом PR.

Организационный список и ожидаемые участники цели имеют разный смысл. Пришедшие строки источника не задают ожидаемый состав. Для новой команды пользователь выбрал автоматическое назначение всех целей её кластера. Создание команды и назначений составляет согласованный пакет, а влияние на текущие оценки и подтверждения показывается при подготовке PR. До публикации официальный состав сохраняется.

По умолчанию новая команда использует общий командный шаблон соответствующей цели; куратор может отдельно задать методику, целевые значения и срок. Это подтверждено пользователем. Методика командного уровня может отличаться от кластерной; связанные шаблоны и самостоятельные правила не смешиваются.

Пользователь исключил перенос команд между кластерами: команда закреплена за своим кластером. Не требуется проектировать перевод, замену назначений при переводе или распределение периода между старым и новым кластерами. Дата начала действия новых назначений ещё может требовать уточнения; исторические составы не переписываются.

## Кураторы и ответственность

У каждой цели определяются основной куратор и со-кураторы. Все сохраняют одинаковые возможности панели. Назначение ответственного отделено от авторства собранных данных, проверок, комментариев и отправленных PR: для каждого действия сохраняется фактический участник. Техническое право итогового merge принадлежит владельцу и реализуется в Bitbucket.

Источник планов и состояния работ определён: кураторы ведут их вручную в приложении. Изменения подготавливаются здесь и становятся общими после согласования в Bitbucket и merge в main. Приложение является бизнес-источником ведения, main — принятой общей версией для распространения. Маршрутизация уведомлений определена D-056; при отсутствии основного куратора назначение меняют вручную по D-062.

Подтверждён полноценный список работ и вех с исполнителями, сроками и состояниями. Измеренный результат, кураторское подтверждение и план исполнения остаются разными понятиями. Завершение работы не подменяет методику и подтверждение достижения. Выбор ответственных команд определён D-046; соисполнители и связи отдельных работ с областями цели ещё требуют определения.

Пользователь потребовал простой и понятный клиентский путь. Для читателя предлагается последовательность «отклонение → причина → работа → ответственный/срок → следующий шаг»; для куратора — подготовка в нужном контексте, проверка, PR и видимый результат согласования. Конкретные экраны и числовые критерии удобства ещё не выбраны, интерактивный макет ранее отложен пользователем.

## Временная модель целей

Подтверждены отдельные настройки режима оценки, срока достижения и частоты обновления. В режиме состояния на дату требуется дата состояния, в режиме результата за период — границы и смысл периода. Конкретные календарные правила ещё не определены.

Срок достижения не заменяет частоту получения фактов. Период факта, обновление источника, загрузка куратором и принятие публикации из Git имеют разный смысл. Читатели получают готовые официальные факты; их периодическая проверка main не является сбором источников и не обновляет возраст факта.

Политика устаревания текущих данных подтверждена: последний результат и его дата сохраняются, показывается предупреждение «Данные устарели», уведомляется куратор. Новое подтверждение актуального выполнения возможно только после обновления необходимых данных. История сохраняется; закрытый исторический период не переписывается из-за течения времени. Сигнал давности не должен молча менять опубликованное достижение или прежнюю запись подтверждения.

Пользователь подтвердил разные частоту обновления и допустимую давность показателей одной цели, настраиваемые куратором отдельно для каждого показателя. Конкретные числовые значения, значения по умолчанию и календарные правила ещё не заданы. Неизвестная дата источника не заменяется временем сегодняшней загрузки; это отдельная неопределённость актуальности.

## Исправления фактов

Ручные исправления разрешены кураторам с сохранением исходного значения, источника, автора и причины. Они подготавливаются как изменение конкретного факта и становятся официальными только после merge PR владельцем. Оригинал и редакции сохраняются, а пересчёт затрагивает соответствующее основание оценки. Прежнее подтверждение не переносится автоматически на изменённый результат.

Исправление не является новым наблюдением и не делает измерение свежим только за счёт даты редактирования. При повторной загрузке того же факта подтверждён приоритет принятой корректировки: она сохраняется, расхождение показывается куратору. Он оставляет её или предлагает новое значение через PR. Официальное значение меняется после merge владельцем. Новый период или дата измерения различаются с исправлением прежнего факта.

Пример для приёмки: источник дал 10, куратор исправил на 12, исправление принято. Новая загрузка того же факта за тот же период даёт 11: официально остаётся 12, расхождение доступно куратору. Если он предлагает 11, изменение снова проходит PR. Повтор одного расхождения не должен создавать дубликаты задач. Действия при совпадении источника с исправлением и закрытие расхождения ещё уточняются.

## Предложения по обновлению

При запуске и затем с настраиваемым интервалом проверять опубликованную ветку. При изменении показывать доступное обновление и содержательную сводку: какие цели, правила, назначения или комментарии изменились. Интервал пока не выбран.

По кнопке обновления проверять совместимость и сохранять локальную кастомизацию и незавершённый ввод. Затем получать и проверять общую версию, применять её и показывать результат. Сбой связи сохраняет последнюю принятую версию с её датой. Изменение кода дополнительно требует подготовки зависимостей, миграций и согласованного перезапуска.

Необходимо отдельно определить поведение при изменении ветки между проверкой и применением, конфликте локальной правки куратора, повреждённом пакете, недоступном Git и повторном запуске после прерывания.
