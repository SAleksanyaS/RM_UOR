# Требования к будущим спецификациям и передаче агенту

Цель — дать исполнителю однозначное описание поведения и последовательность проверяемых шагов. Документация должна помогать собрать систему заново, изменить отдельный модуль и проверить, что изменение сохранило нужные свойства.

По D-117 приложение сопровождает пользователь с помощью агентов, отдельной команды нет. Требование к понятности и пошаговости подтверждено; ниже предложен формат, которым агент-проектировщик должен обеспечить эту передачу. Архитектурный каркас уже подготовлен, точные схемы и план реализации ещё предстоит завершить.

## Комплект спецификаций

Первый этап по решению пользователя: цели, данные, аналитика и панель УОР. Реализация отчётов и презентаций — следующий этап; сейчас нужен предусмотренный контракт потребления подготовленных данных и оснований расчёта. Наличие спецификаций отчётности в общем комплекте не означает реализацию экспорта в первом этапе.

| Документ | Обязательное содержание |
|---|---|
| Назначение и границы | Пользователи, задачи, ожидаемая польза, критерии успеха, ограничения первой версии |
| Словарь и предметная модель | Термины, сущности, идентификаторы, связи, владельцы, примеры и смена во времени |
| Бизнес-процессы | Триггеры, участники, шаги, решения, результат, исключения |
| Пользовательские сценарии | Роль, намерение, предусловия, основной путь, альтернативы, ошибки, проверка результата |
| Правила и расчёты | Формулы, единицы, точность, статусы, переходы, периоды, состав, неполнота и подтверждение |
| Данные | Схемы, ограничения, авторитетные источники, защищённая общая база УОР, настройки представления, данные независимых модулей, происхождение, качество, миграции и хранение |
| Интеграции | Контракты адаптеров, доступ, стадии, повторы, отмена, диагностика, тестовые примеры |
| Архитектура | Рассмотренные варианты, выбранные решения и причины, компоненты, зависимости, транзакции и фоновые операции |
| API | Запросы и ответы, схемы, ошибки, локальное редактирование и право общей публикации, конфликты, идемпотентность и версии |
| Интерфейс | Карта экранов, прототипы, поля, действия, сообщения и состояния, доступность и адаптация |
| Отчётность | Состав снимка, период, ручной текст, шаблоны, форматы, воспроизводимость и визуальная приёмка |
| Согласование изменений | Одинаковая панель кураторов, рабочие пакеты, машинные файлы, сводка влияния, нативные PR Bitbucket, замечания, доработка, внешнее слияние и уведомления |
| Эксплуатация | Подготовка среды, установка, настройка, диагностика, наблюдаемость, копии, восстановление, проверка Git, обновления данных и программы, уведомления |
| Проверка и приёмка | Эталонные наборы, расчёты, сценарии, целевые среды, критерии и сохраняемые доказательства |
| Миграция и поставка | Перенос старых данных, пробный прогон, сверка, переключение и восстановление |
| План исполнения | Малые зависимые задачи, точные входы и выходы, команды и проверка каждой задачи |
| Руководства | Отдельные инструкции читателю, редактору, сопровождающему и агенту-разработчику |

## Связь требования с проверкой

Для каждого существенного поведения сохраняется цепочка: бизнес-потребность → пользовательский сценарий → правило → данные/API/экран → приёмочный пример → задача реализации → результат проверки.

Например, потребность «не принять отсутствие данных за успех» должна получить точное правило статуса, пример неполного входа, ожидаемый результат на экране и в отчёте, а затем проверку этого сценария. Названия модулей и графиков сами по себе не заменяют такую цепочку.

Каждое требование имеет стабильный идентификатор, статус и основание: подтверждено пользователем, ограничено средой, предложено проектировщиком или остаётся открытым. Решение сохраняется вместе с причиной; последующие изменения явно заменяют прежнюю версию.

## Как описывается отдельная функция

1. Кто запускает действие, с какой целью и из какого исходного состояния.
2. Какие входные данные обязательны, как они проверяются и откуда берутся.
3. Какой результат получается и что сохраняется; какие побочные эффекты допустимы.
4. Как выглядит успех, пустой результат, неполнота, устаревание, отказ доступа, конфликт, отмена и повтор.
5. Как функция участвует в истории, общей публикации, отчётности и восстановлении.
6. Какие конкретные примеры подтверждают правильность и где заканчиваются поддержанные возможности.

## Эталонные примеры

Для каждой обязательной методики нужны входы, формула и ожидаемые выходы. Покрываются граница порога, округление, отсутствие и неприменимость данных, изменение состава, дубликат, исправление старого периода и влияние на подтверждение. Значения берутся из согласованных примеров либо явно обозначенных синтетических наборов.

Для сквозного сценария нужны согласованные примеры на уровне API, интерфейса и отчёта. Они должны объяснять одно и то же состояние. При смене правил определяется, сравнимы ли периоды и как это сообщить человеку.

## Как агент получает задачу

Входная инструкция указывает актуальный индекс документов, приоритет источников, границы задачи, нужный контекст, зависимости и критерии готовности. В рабочем репозитории она ссылается на действующие AGENTS.md и навигацию, а исторические материалы помечаются отдельно.

В каждой задаче реализации указываются:

- Предварительные условия и зависимые решения.
- Точные файлы или модули изменения после выбора архитектуры.
- Контракты, которые необходимо реализовать или сохранить.
- Конкретные команды подготовки, запуска и проверки, рабочий каталог и ожидаемый наблюдаемый результат.
- Обработка ошибки и способ продолжить без потери данных.
- Обязательные изменения документации и способ продемонстрировать результат.

Исполнитель не должен самостоятельно придумывать формулу, смысл статуса, владельца данных или порядок согласования. Существенный нерешённый вопрос получает идентификатор и явный маршрут разрешения. Рутинные технические решения имеют заранее согласованные границы самостоятельности.

### Обязательный формат задания исполнителю

| Поле задания | Что нужно заполнить до статуса «готово к исполнению» |
| --- | --- |
| ID и статус | Стабильный ID, версия, готово/черновик/зависимость; ссылка на задачу в общем плане. |
| Результат | Наблюдаемое поведение или конкретный артефакт, ради которого выполняется задача. |
| Основание | Решения пользователя и действующая спецификация; предложения явно отличаются от принятых правил. |
| Рабочее место | Репозиторий, исходная ревизия, рабочий каталог, нужные версии и предварительные проверки. |
| Материалы | Точные документы, входные схемы и наборы; для эталонных данных заранее известны ожидаемые результаты. |
| Изменения | Точные файлы/точки регистрации и границы задачи после проектирования; сохраняемые контракты и данные. |
| Шаги | Нумерованные действия в порядке зависимостей; у команды указан каталог, вход и ожидаемый наблюдаемый результат. |
| Проверка | Необходимые для изменения проверки, команды, ожидаемые значения/состояния и место доказательств. |
| Ошибки | Что означает неуспех, какие данные сохраняются, где безопасно остановиться и как повторить шаг. |
| Завершение | Что показать владельцу: изменение, объяснение, результат проверок, ограничения и следующий шаг. |

Незаполненное существенное поле не маскируется фразами «по аналогии», «сделать правильно» или «агент разберётся». Шаблон с незаполненными полями является черновиком, а не готовой задачей. Один шаг должен позволять проверить, что именно уже сделано; длинная цепочка команд без промежуточных критериев не заменяет инструкцию.

Инструкция использует обычные файлы проекта и доступные команды Git/npm/Python. Наличие Codex, его специальных инструментов или конкретного интерфейса чата не должно быть условием воспроизводимости. Если способ работы отличается в реальной среде, он фиксируется в инструкции до передачи этой задачи.

Проверки выбираются по изменённому поведению. Изменение только текста документа не требует запуска продуктовых сценариев; изменение расчёта требует эталонных входов и выходов. Исполнитель не меняет ожидаемый бизнес-результат только для получения зелёной проверки и не выдаёт старый прогон или тест на подставном адаптере за проверку банковского доступа.

Для смены агента сохраняется краткая запись продолжения: задача и версия, фактические изменения, выполненные команды и результаты, незавершённый шаг, препятствие и точное следующее действие. Она ссылается на файлы, а не требует восстановления контекста из всей истории чата.

## Расширение системы

Для добавления нового типа цели, источника, представления или шаблона нужен отдельный пример расширения: контракт → реализация → регистрация в явных точках → интерфейс настройки → хранение и версия → проверка → публикация/перенос → инструкция.

Модель поставки подтверждена D-097: новый программный модуль входит в общий выпуск приложения через Git и использует общие платформенные механизмы. Независимую установку и обновление исполняемых модулей в требования текущего этапа не включаем. Настройка уже реализованного источника или методики остаётся отдельным пользовательским сценарием.

По D-102 дополнительные модули входят в общую навигацию и видны всем. Персональный каталог включения/скрытия модулей не требуется. Регистрация нового модуля должна описывать его пункт навигации и применять действующие права редактирования; видимость модуля не выдаёт право изменять официальные данные.

Расширяемость — требование пользователя, конкретные архитектурные механизмы ещё предложены для дизайна. Предлагаемый проверяемый критерий: по инструкции добавить один новый источник и один новый способ расчёта, подключить их через опубликованные контракты/реестр и проверить на эталонных данных без переписывания основной логики приложения. Общие интерфейсные компоненты, операции, диагностика и публикация должны переиспользоваться. Новые предметные понятия могут потребовать развития ядра и миграций; это не обещание произвольных расширений без изменения платформы. Динамическая загрузка исполняемых плагинов и отдельные микросервисы этим требованием не предписаны.

Контракт платформенного модуля описывает идентичность и зависимости, версию схемы, входы и выходы, предоставляемые сценарии, интерфейс и API, область хранения, настройки и участие в общей публикации. Независимый локальный модуль может читать опубликованные цели УОР по явному контракту; его операции не меняют официальные значения, статусы или правила. Его данные не включаются в публикацию УОР автоматически. Контракт также задаёт прогресс/отмену, диагностику, историю, миграцию, резервирование и перенос. Подключение модуля должно использовать общие механизмы этих функций.

Приёмка разграничения проверяет, что локальный редактор и интеграция не меняют официальное содержание УОР; фильтрация и визуализация сохраняют исходные значения и обозначают выбранный срез; общий выпуск обновляет официальные данные, сохраняя независимые локальные данные и допустимые настройки представления. Подготовка официального изменения проходит отдельный процесс выпуска.

## Условия общей цели и назначений

Спецификация должна явно различать общую цель ДИТ и её назначения кластерам и командам. Для назначений задаются собственные типизированные целевые значения и официальные сроки, редактируемые куратором УОР через процесс подготовки выпуска. Официальный срок отделяется от внутреннего плана и прогноза.

Оценка относится к цели и её области: ДИТ, кластер или команда. Для каждого уровня сохраняются собственный показатель, требование и статус. Для одной цели куратор УОР может настроить разные наборы показателей, обязательность, веса и формулы на этих уровнях. Допустимые формулы и способы настройки ещё требуют спецификации. Нельзя выводить среднее или обязательность выполнения всеми участниками из одного факта наличия иерархии.

Проверяемый согласованный пример: при пороге ДИТ 90% и факте 92% общий порог достигнут, а кластер с фактом 88% при собственном пороге 95% не достиг своего требования. Эти два результата сохраняются одновременно; стадия подтверждения УОР определяется отдельно. После публикации новая редакция общего шаблона применяется ко всем связанным назначениям; самостоятельная методика сохраняется. Наследование отдельных условий ещё не согласовано. Другие примеры должны включать изменение срока, смену состава и отсутствие двойного счёта кластера и его команд.

Простота настройки является самостоятельным требованием. Предлагаемые способы — последовательная настройка выбранной области, готовые шаблоны, понятные подписи обязательности и весов, раскрытие дополнительных параметров по необходимости, проверка на примере с объяснением. Приёмка должна включить настройку методики куратором без помощи разработчика и проверку понимания результата. Конкретные экраны и измеримые критерии удобства ещё согласуются. Использование общего шаблона и самостоятельная методика должны различаться в данных и интерфейсе.

В PR изменения шаблона показываются все связанные назначения и влияние на их текущие оценки/подтверждения. Новая редакция применяется при принятии опубликованной версии. Историческая основа и замороженные отчёты сохраняют прежнюю редакцию; сама смена шаблона не делает исходные факты более свежими. Проверяется, что публикация не оставляет шаблон, текущий результат и подтверждение в несовместимых редакциях, а самостоятельные методики не изменяются.

Смешанная методика включает настраиваемые обязательные показатели, веса и формулу итога. Согласованный инвариант: известное невыполнение обязательного показателя не компенсируется высоким итоговым баллом. Формула должна иметь проверяемые входы и пример результата; невыполнение и отсутствие данных различаются.

При неполноте показываются предварительный балл, признак его предварительности и явный перечень недостающих показателей. До получения всех необходимых показателей подтверждение выполнения запрещено. Полнота сама по себе не разрешает подтверждение при провале обязательной метрики или итоговой формулы. Эта проверка требуется на уровне сценария/сервера, а не только состояния кнопки.

Неприменимость оформляет куратор для показателя, конкретной команды/кластера и периода с обязательной причиной. Показатель исключается из расчёта этой области в этот период; исходная методика и исключение сохраняются раздельно. Исключение является частью официального пакета согласования. Пропуск данных не создаёт исключения автоматически.

После исключения неприменимых показателей эффективные веса оставшихся применимых показателей нормализуются пропорционально до 100%: effectiveWeight_i = originalWeight_i / sum(originalWeight_j для оставшихся применимых показателей) × 100%. Формула применима при положительной сумме оставшихся весов. Настроенные исходные веса сохраняются. Согласованный пример: 60/20/20, последний показатель исключён, эффективные веса 75/25. Точность хранения и округление отображения ещё задаются.

Если все показатели цели объявлены неприменимыми в данной команде/кластере, результат — «Неприменима», без числового балла и подтверждения достижения. Такая цель исключается из процента выполнения соответствующей области и учитывается отдельным количеством. Пустой применимый состав не превращается в 100% выполнения; другая область и общий ДИТ не получают этот статус автоматически.

Для взвешенной методики согласован предварительный балл P = sum(w_i × r_i для известных применимых показателей) / sum(w_i для известных применимых показателей), где r_i — нормированный результат показателя в процентах. Покрытие C = sum(w_i для известных применимых показателей) / sum(w_i для всех применимых показателей) × 100%. Формулы применимы при положительных знаменателях. Вес отсутствующего показателя сохраняется в применимом составе; предварительный расчёт не делает его неприменимым.

Согласованный пример: веса 50/50, первый результат 80%, второй отсутствует — P = 80%, C = 50%, подтверждение недоступно. Покрытие по весам не заменяет проверку получения всех необходимых показателей. Нормирование исходного значения в r_i и округление ещё должны быть заданы методикой. Этот способ не распространяется автоматически на другие формулы.

Перевыполнение разрешено: r_i и общий числовой балл могут превышать 100%, общего автоматического ограничения вкладов на 100% нет. r_i — нормированное выполнение по методике, отдельное от сырого факта в процентах, часах, количестве и других единицах. Проверочный пример для взвешенной формулы: результаты 120% и 100% с весами 50/50 дают 110%, без обрезки первого результата. Сумма нормированных весов и покрытие данных не являются тем же показателем, что перевыполнение. Высокий общий балл не компенсирует известный провал обязательного показателя и не снимает требования к подтверждению. Точные функции нормирования по типам числовых условий ещё согласуются.

Условие достижения каждого числового показателя задаёт куратор: «не меньше», «не больше», «в диапазоне», «точно равно», с целевым значением или границами. Проверка факта на соответствие условию и преобразование факта в r_i — разные операции. Будущая спецификация должна определить единицы, смысл границ, точность сравнения и функцию нормирования для каждого поддержанного случая; выбор условия не задаёт эти функции автоматически.

Для числовых условий «в диапазоне» и «точно равно» подтверждена шкала: условие выполнено → 100%, известно нарушение → 0%, факт отсутствует → «Нет данных», без нулевой подстановки. Границы диапазона включаются. Проверочные примеры: диапазон 80–90 — факты 80/85/90 дают 100%, 79/91 дают 0%; точная цель 85 при факте 85 даёт 100%, при факте 84 — 0%. Точность сравнения и допуски не определены этими примерами. По просьбе пользователя такие частные детали вынесены в уточнения спецификации метода; перед реализацией необходимы явные правила и проверки, без продолжения подробного опроса сейчас.

Для показателей на рост/снижение выбран процент относительно целевого значения; режим прогресса от исходного состояния не выбран. При положительных величинах базовая формула роста r = 100 × факт / цель, снижения r = 100 × цель / факт, с учётом настроенного максимума ниже. Согласованный пример снижения: цель 10, факт 8 — 125%, исходное состояние 20 не входит в эту формулу. Пример роста для проверки формулы: цель 80, факт 96 — 120%. Это нормированное выполнение, сырые факты сохраняются отдельно. Нулевые случаи описываются отдельными правилами; произвольные отрицательные величины, диапазон и точное равенство не должны молча подчиняться обычному отношению.

Подтверждена отдельная шкала для неотрицательного счётчика с нулевым планом (например, отсутствие нарушений/просрочек): факт 0 → 100%, факт >0 → 0%, отсутствие факта → «Нет данных» без подстановки нуля. Фактическое количество показывается рядом. Проверочные примеры: план 0 и факт 0 дают 100%; план 0 и факт 3 дают 0% с видимым количеством 3; пустое значение не превращается в успешный ноль. Эта шкала не распространяется автоматически на положительный план с нулевым фактом, произвольные отрицательные величины и другие типы показателей.

Согласован настраиваемый куратором максимум перевыполнения M>100% для показателя. В рассмотренной методике «не больше положительной цели» при неотрицательном факте: если факт>0, r=min(M,100×цель/факт); если факт=0, r=M. Предел применяется всем результатам этого показателя, а не только нулю. Согласованный пример с M=200% и целью 10: факт 8 → 125%, факт 5/1/0 → 200%; исходный факт виден отдельно. 200% — пример, общего значения по умолчанию не выбрано. M должен быть конечным; отсутствующий факт не получает максимум. Этот параметр не возвращает глобальный потолок 100% и не отменяет обязательные условия. Применимость параметра к другим методикам определяется их контрактом, а не молчаливым копированием формулы.

Правила частичного невзвешенного расчёта и неизвестного обязательного показателя задаются отдельно. Нельзя дополнять пропуск нулём или исключать его из применимого состава молча. Проверяемые сценарии включают согласованный пример P/C; предварительный высокий балл с пропуском и запретом подтверждения; полный набор с выполненной формулой; известный провал обязательной метрики при неполноте; исключение только одной области/периода и окончание срока исключения; все показатели неприменимы с отдельным статусом и исключением из знаменателя процента выполнения. Нулевая сумма доступных весов не создаёт числового результата; подробное поведение задаётся явно.

## Получение фактов и пакетная публикация

Источник настраивается для цели, а не для каждого продукта отдельно. У каждой цели свой источник со всем необходимым набором данных; постоянная ссылка ОКО относится к этому источнику. После получения продуктовые строки обогащаются общей структурой кластера, продукта и лидеров. Идентификаторы, реальные колонки и формат конкретной выгрузки определяются при её подключении; внутренний productId не доказывает наличия такого поля в источнике. Полнота получения требует технической проверки адаптера, независимо от одной постоянной ссылки.

Подтверждены штатные способы по цели: если настроен отчёт ОКО (Qlik Sense), используется он; если ОКО для цели вообще не настроено — Excel/CSV; без дашборда и файлов для целей, ведущихся только статусом, — ручной ввод статуса. Конкурирующие источники для сравнения значений не нужны. Сбой настроенного ОКО обрабатывается резервом ниже, а не автоматическим переходом на файл. Каждый сотрудник получает свежие данные напрямую при доступности источника; права читателей на ручную правку не расширялись. Редакция Qlik, интерфейсы, SSO и область данных проверяются при подключении.

Ручная статусная цель — отдельный предусмотренный вид ведения, а не ошибка загрузки числовых показателей. Подтверждён набор состояний: «Не начата», «В работе», «Выполнена». Это состояния самой цели; они не подменяют пять состояний отдельных работ. Будущая спецификация должна описать поля без вымышленных числовых фактов: пустой числовой набор сам по себе не объявляет такую цель неприменимой и не создаёт числовой результат. Ввод куратора входит в его накопленный пакет, читателям общая принятая редакция доступна через Git. При «Выполнена» обязательно краткое описание полученного результата; ссылка или файл прикладываются при необходимости. Проверочный пример: черновик с незаполненным результатом сохраняется, но для подготовки выполнения куратор должен описать результат; отсутствие необязательного вложения не блокирует действие. Ручная корректировка ошибочного факта источника по ранее принятым правилам — отдельный процесс, не конкурирующий штатный канал получения.

Для файловой цели куратор один раз настраивает соответствие колонок (команда/кластер, значение, дата/период), затем применяется сохранённая настройка. Перед сохранением значений показываются распознанные данные, пропуски и ошибки. Проверочный пример: следующий файл того же формата использует настройку цели; открытие предпросмотра и его отмена не меняют факты. Структура файла проверяется при каждой загрузке; сохранённая настройка не означает доверие любому новому содержимому.

Если часть строк содержит ошибки, куратор может сохранить корректные строки. Непринятые показываются отдельным списком с причинами, данные явно помечаются неполными. Проверочный пример: 95 корректных строк и пять ошибочных — после явного применения сохранены 95, пять видны в отчёте отклонения с причинами, неполнота отражена в результате. Ошибочные строки не создают факты и не стирают ранее принятые значения. Подтверждение при отсутствии обязательных данных по-прежнему блокируется.

Повторный исправленный файл дополняет ранее принятые данные того же периода: после первых 95 строк можно отдельно дозагрузить пять исправленных, сохранив прежние корректные строки. Полноту текущего набора следует пересчитать по ожидаемому составу и полученным фактам, отдельно от истории ошибок прошлой операции. Будущая спецификация идентичности факта должна различать одинаковый повтор, новый факт и другое значение того же факта. Для изменившегося значения того же показателя, команды и периода предпросмотр показывает «было / станет»; куратор выбирает исправления и применяет одним действием. Прежние значения сохраняются в истории; невыбранное исправление не применяется. Проверочный пример: два отличающихся значения показаны в предпросмотре, куратор выбрал одно — изменено только выбранное, его прежняя редакция доступна в истории. Согласованное ручное исправление источника не стирается автоматически.

Оперативные факты и текущий расчёт по общей принятой методике отделяются от согласованного среза. Git/main распространяет настройки, методики, общие комментарии и согласованные итоги. Прямое получение новых фактов не требует изменения Git и не перезаписывает основание опубликованного подтверждения или исторического отчёта. Будущая спецификация должна определить происхождение, область, период, время источника, полноту и редакцию методики для каждого расчёта. Проверочный пример: при неизменном HEAD обновление источника меняет оперативный расчёт; прежний согласованный срез остаётся воспроизводимым.

При недоступности прямого получения, в том числе из-за прав доступа к Qlik, сохраняются последние успешно полученные локальные данные с датой и предупреждением. Если таких данных нет, приложение берёт соответствующие опубликованные данные репозитория. Поэтому общий пакет должен содержать нужные факты/срез для резервного чтения, а не только описание методики. Для результата различимы путь получения, исходная дата/период, полнота и давность. Чтение кэша и скачивание из Git не обновляют дату факта. Согласованный пример: локально вчера получены 92%, в Git более старые 88%, сегодня источник недоступен — отображаются локальные 92% с датой и предупреждением. На ноутбуке без локальных данных используются опубликованные 88% с их датой. Если нет и опубликованного факта, отображается отсутствие данных; ошибка получения не создаёт нулевой результат. Невалидный или неуспешный импорт не заменяет последний успешный факт.

Куратор накапливает изменения и проверенные итоги в своём рабочем пакете. Отправка PR выполняется по важному событию либо один-два раза в неделю; каждое обновление факта или сохранение записи не создаёт отдельный PR. Подтверждён отдельный накопленный PR каждого куратора за цикл: владелец принимает его независимо либо отправляет на доработку. При отправке готовятся машинные файлы и сводка всего пакета; окончательный merge остаётся в Bitbucket. Проверочный пример: несколько загрузок, исправлений и комментариев куратора А накапливаются без новых PR, затем он отправляет один пакет; пакет куратора Б можно принять отдельно. Предельный объём пакета и правила совмещения изменений ещё уточняются.

Нехватка данных должна быть явной; пользователь допускает исключение из расчёта либо отображение неполноты. Не следует автоматически считать отсутствие нулём или неприменимостью. Подтверждено: отсутствие применимого обязательного показателя блокирует подтверждение выполнения, даже если предварительный балл рассчитан без него. Проверочный пример: по двум полученным показателям предварительный балл 100%, третий обязательный показатель отсутствует — показаны пропуск и предварительность, подтверждение недоступно. Согласованная неприменимость N/A с причиной/периодом остаётся отдельным основанием. Правила необязательных показателей ещё уточняются; предварительный балл, покрытие и перечень пропусков сохраняют свой смысл.

## Исходные данные и обогащение

Подтверждено отдельное представление исходных данных отчёта, обогащённых данных и визуализации. Точная основная иерархия: кластер с одним лидером кластера → продукты, у каждого один лидер продукта → при необходимости команды со своими лидерами. Лидер кластера, лидер продукта и лидер команды — разные поля/связи предметной модели, не дополнительные роли доступа. Командная связь не является обязательным промежуточным уровнем обогащения. Ранее подтверждённая возможность нескольких команд у продукта сохраняется для детализации, связи ведёт куратор через общий справочник и публикацию. Ограничение принадлежности команды единственному продукту не вводится без отдельного требования.

Предлагаемая логическая цепочка: исходные бизнес-поля и метаданные получения → проверка/нормализация → обогащение справочниками → единые расчёты и представления → экраны, позднее отчёты. Исходные бизнес-поля не перезаписываются добавленными организационными полями. Из результата должно быть возможно проследить исходную строку, источник/период, версию сопоставления и методику. Отсутствующие связи, необходимые выбранному срезу или расчёту, видны с причиной и задачей для куратора. Отсутствие необязательной командной детализации само по себе не объявляет основное представление кластера, продуктов и их лидеров неполным. Неполнота не превращается в ноль.

Будущая спецификация должна определить идентичность и детализацию исходного факта, версии сопоставлений и расчётов, ожидаемый охват, сохранение исторических оснований и контроль повторного учёта при связях с несколькими объектами. Приоритет — продуктовые факты в основном срезе по лидерам; правила командного распределения не утверждены и не навязываются как базовый сценарий. Для агрегата требуется явная единица учёта и методика. Физическое хранение исходных файлов и состав публикуемого среза определяются после оценки объёмов; требование не предписывает помещать все полные выгрузки в Git. Контракт обогащённых данных должен использоваться всеми экранами и будущей отчётностью, исключая самостоятельные копии логики в каждом потребителе.

## Справочники и ожидаемый состав

Команды, кластеры, продукты, ИТ-услуги и руководители ведутся УОР через приложение и общий процесс публикации. Сущности имеют устойчивую идентичность; изменение имени не создаёт новую сущность. По D-125 новые назначения целей и изменения организационных связей действуют только с момента публикации в main. Выбор иной деловой даты и ретроактивное переназначение не вводятся. Прежние согласованные срезы и их основания не пересчитываются; организационные связи и их историческое состояние сохраняются в основании результата. Q-03 закрыт.

Цель имеет основного куратора и со-кураторов. Основной куратор и участники сопровождения обозначают ответственность, не отдельные уровни доступа. Панель кураторов остаётся одинаковой. Назначение ответственного, авторы конкретных действий и технические полномочия Bitbucket — разные данные; изменение ответственного не переписывает авторство старых фактов, подтверждений и PR. При необходимости основного куратора меняют вручную через PR/main; маршрутизация уведомлений использует текущее принятое назначение. Временное замещение с автоматическим возвратом не входит в выбранный процесс; локальные неопубликованные черновики автоматически другому куратору не передаются.

Справочник организации отличается от ожидаемого состава конкретной цели. Пришедшие строки источника не определяют этот состав автоматически. Для новой команды выбрано правило назначения всех целей её кластера. Команда и связанные назначения подготавливаются согласованным набором изменений. PR показывает влияние на применимость, ожидаемый состав, расчёты и подтверждения; прошлые результаты не переписываются по сегодняшней структуре.

Новая команда по умолчанию получает общий шаблон командного уровня каждой назначенной цели. Куратор может отдельно задать её методику, целевые значения и срок. Это не подмена командной методики формулой кластерного уровня. По D-125 новое назначение вступает в силу с публикации в main; отдельная дата действия куратором не задаётся. Отсутствие фактов или необходимых правил новой команды не даёт ей выдуманного результата. Приёмка должна включать добавление команды, автоматически созданные назначения, прежний исторический состав и влияние нового состава на затронутые текущие основания подтверждения без пересчёта прежних согласованных срезов.

Команда закреплена за кластером; сценарий её перевода между кластерами исключён пользователем из текущего объёма. Модель и интерфейс не должны вводить этот процесс как обязательный. Идентичность сущности и сохранённые исторические основания остаются необходимыми для переименований, новых назначений и повторных расчётов.

## Планы и исполнение

Кураторы вручную ведут планы и состояние работ в приложении; оно является единым местом ведения. Подготовленные изменения становятся общими через установленный процесс PR и main. Интеграция с внешним трекером не является обязательной частью подтверждённого сценария.

План содержит полноценный список работ и вех с исполнителями, сроками и состояниями. План, измеренный показатель и подтверждение УОР имеют разную семантику. Само завершение работ не подменяет проверку методики и подтверждение достижения. Куратор, записывающий план, и бизнес-исполнитель работы — разные участники; модель ответственности, области и отношения отдельных работ ещё согласуются.

Подтверждён выбор ответственных по командам: куратор может назначить одного человека от кластера на несколько команд либо отдельных людей по командам. Область ответственности должна быть явно видна; отдельный человек в каждой команде не обязателен. Назначение не меняет права доступа и авторство прежних действий. Проверочный пример для будущей спецификации: команды А и Б имеют одного ответственного от кластера, команда В — своего; все три назначения представлены раздельно и однозначно. Автоматическое наследование, замещение и состав соисполнителей работ пока не согласованы.

Куратор отмечает риск срыва работы до просрочки, его причину, прогнозную дату завершения и требуемую помощь. Плановый срок хранится отдельно от прогноза. Проверочный пример: плановый срок 15 ноября, прогноз 25 ноября; изменение прогноза не заменяет плановый срок, обе даты различимы читателю. Эти сведения проходят тот же процесс общей публикации; сами по себе они не меняют измеренный показатель или подтверждение достижения. Автоматическое определение риска пока не согласовано.

Для требуемого решения руководителя куратор ведёт отдельный запрос, связанный с работой: предмет решения, кто должен его принять, срок и принятое решение. Назначение адресата не выдаёт право редактирования; руководитель остаётся читателем, если у него нет отдельно подтверждённых прав куратора. Решение в бизнес-процессе не тождественно принятию PR с записью об этом решении. Будущая спецификация должна описать переход от ожидаемого решения к зафиксированному результату и различить срок решения, план работы и её прогноз. Конкретные состояния, правила закрытия и уведомления ещё уточняются.

Куратор явно связывает зависимые работы, в том числе разных команд. Читатель видит блокирующую работу, её ответственного и связанные цели под угрозой. Будущий контракт зависимости должен однозначно задавать направление связи: какая работа ожидает результат какой. Проверочный пример: работа команды Б ожидает результат работы команды А; из Б доступны блокирующая работа А, её ответственный и затронутые цели. Конкретные виды зависимостей и календарное планирование ещё не выбраны. Обязательная диаграмма Ганта из этого требования не следует; риск исполнения и измеренный статус цели различаются.

При задержке приложение показывает куратору всю затронутую цепочку для пересмотра прогнозов. Куратор проверяет ситуацию и вручную задаёт новые прогнозные даты связанных работ; плановые сроки сохраняются отдельно. Проверочный пример: А задерживается и блокирует Б, а Б блокирует В; куратор видит всю цепочку и связанные цели, а просмотр цепочки сам по себе не меняет даты. Изменения прогноза входят в обычный процесс PR и публикации. Автоматический расчёт новых прогнозных дат не является выбранным процессом.

Одна работа хранится одной записью с устойчивой идентичностью и может быть связана с несколькими целями. Изменение её состояния отображается во всех связанных целях. Проверочный пример: работа связана с целями А и Б; куратор обновляет её один раз, читатель видит одну и ту же принятую редакцию работы из обеих целей. Достижение каждой цели оценивается по собственной методике и не подменяется завершением работы. Независимые результаты командных частей общей работы ещё не согласованы.

При завершении работы куратор обязательно кратко описывает полученный результат; подтверждающую ссылку или файл добавляет при необходимости. Будущая спецификация должна различить незавершённый черновик и завершение с обязательным результатом: черновой ввод сохраняется, а завершение без описания результата требует заполнить его. Необязательное подтверждение не должно блокировать завершение всех работ. Читатель видит результат принятой редакции; выполнение работы не заменяет проверку достижения цели. Хранение, перенос, доступность и версионирование файлов подтверждения ещё не выбраны.

Работы имеют состояния «Запланирована», «В работе», «Приостановлена», «Выполнена», «Отменена». При приостановке и отмене куратор обязательно указывает причину; это не заменяет обязательный результат при выполнении. Риск и блокировка отображаются отдельно от состояния, например: «В работе · есть риск · ожидает результат команды А». Будущая спецификация должна отдельно описать допустимые переходы, обязательные поля и историю изменений.

Куратор может вернуть ранее выполненную работу в состояние «В работе» с обязательной причиной. Прежнее завершение и его результат сохраняются в истории; изменение проходит PR и становится общим после принятия. Проверочный пример: работа завершена с результатом R, затем обнаружена неполнота; куратор подготавливает возврат с причиной, после публикации текущее состояние «В работе», прежний результат R доступен в истории. Автоматическое переоткрытие связанных работ и изменение статусов целей из этого решения не следуют. Возврат отменённой работы пока не согласован.

При отмене блокирующей работы показывается предупреждение у зависимой. Куратор указывает заменяющую работу либо снимает зависимость с обязательной причиной; изменение входит в PR. Проверочный пример: Б ожидает А, А отменена — у Б видно предупреждение и причину отмены А; куратор предлагает замену А на В либо обоснованно снимает связь. Сама отмена А не означает выполнения Б или получения ожидаемого результата. Зависимость и принятое решение о ней прослеживаются в истории.

Простой клиентский путь проверяется сквозным сценарием: читатель находит отклонение, понимает его причину, открывает связанную работу, видит ответственного, срок и следующее действие. Куратор создаёт/обновляет работу в нужном контексте, проверяет изменения и отправляет PR; дальнейший результат и замечания понятны из приложения. Конкретные экраны, количество шагов и нормативы времени пока не утверждены. Предлагаемый способ уменьшения перегрузки — краткая сводка с раскрытием подробностей по необходимости; это требует пользовательской проверки.

## Время и актуальность

Для общих сроков, границ дня и напоминаний выбран единый часовой пояс Москвы — Europe/Moscow. Будущая спецификация должна проверить одинаковую интерпретацию на ноутбуках с разными локальными часовыми поясами. Исходные дата/период факта и время источника сохраняют свой смысл; выбор общей зоны не даёт оснований молча переопределять период внешней выгрузки. Время дневного напоминания определено в разделе уведомлений.

Срок только датой действует до конца указанного дня по Москве. Просрочка начинается с 00:00 следующего дня в Europe/Moscow; выходной не переносит дату автоматически. При необходимости куратор явно меняет срок через PR с сохранением истории. Будущий контракт должен сравнивать момент с началом следующего дня, а не придумывать техническую точность «последней секунды». Проверочный пример: срок 15 ноября — в течение 15 ноября работа в состоянии «В работе» ещё в срок, в 00:00 16 ноября эта работа просрочена, независимо от отметки рабочего дня в календаре напоминаний. Дата решения, срок работы и срок достижения цели сохраняют свою предметную принадлежность.

Временной контракт цели отдельно задаёт режим «состояние на дату» или «результат за период», официальный срок достижения и частоту обновления фактов. Дополнительно каждый показатель может иметь собственную частоту и допустимую давность, настраиваемые куратором. Период факта, время изменения источника, загрузки и публикации сохраняют различимый смысл. Обновление Git и пересчёт по новому шаблону не создают новое измерение и не делают прежние факты свежими. Сроки и частота получения фактов не подменяют интервал проверки main клиентом. Календарные границы, числовые настройки и значения по умолчанию ещё требуют согласования; закрытый исторический период и требование свежести текущего состояния должны различаться.

Согласованное поведение устаревания текущих данных: сохраняется последний результат с датой, явно показывается предупреждение, куратор получает уведомление. Новое подтверждение актуального выполнения блокируется до обновления необходимых данных. История не переписывается; локальный сигнал давности не заменяет опубликованный официальный результат новым статусом достижения. Неизвестная дата актуальности источника отличается от установленного просроченного значения и не подставляется сегодняшней датой.

Проверяемый сценарий актуальности должен включать два показателя одной цели с разными частотами и допустимой давностью. Просрочка ежедневного показателя не должна ошибочно объявлять просроченным допустимый месячный показатель; на уровне цели показывается конкретная причина ограничения подтверждения. Перезагрузка старой выгрузки не обнуляет её возраст.

## Ручные исправления фактов

Куратор может исправить ошибочный факт; сохраняются исходное значение, источник, автор исправления и причина. Исправление связывается с исходной записью и её областью/периодом, получает редакцию и проходит обычный процесс согласования PR. Официальным оно становится после merge владельцем. Подготовленное исправление не меняет принятую читателями версию до публикации.

Исходная запись и история сохраняются; изменение основания расчёта требует пересчёта и проверки применимости прежнего подтверждения. Замороженный отчёт не перезаписывается. Дата редактирования или публикации исправления не подменяет дату измерения или актуальности факта.

При повторном импорте того же факта, расходящемся с принятой корректировкой, официальное исправленное значение сохраняется, а куратору показывается расхождение. Он оставляет исправление или предлагает новое значение через PR; смена официального значения требует merge владельцем. Сопоставление учитывает источник, показатель, область и период/дату измерения. Повтор одного расхождения не должен создавать бесконечные дубликаты задач. Совпадение значения источника с исправленным сохраняет историю; подробный жизненный цикл закрытия расхождения ещё задаётся.

## Согласование и выпуск через Bitbucket

Приложение предоставляет всем кураторам, включая владельца, одинаковую панель подготовки, проверки, отправки и сопровождения изменений. Ветки и файлы передаются Git-командами под учётной записью сотрудника. Управление нативными PR выполняется через поддерживаемые возможности установленного Bitbucket. Итоговое слияние выполняется владельцем в Bitbucket; приложение отслеживает его результат и не имеет собственного действия merge.

PR является публикацией накопленного пакета по событию или один-два раза в неделю. Ссылки на PR в сценариях изменения факта, работы, риска, назначения или комментария означают включение в пакет, а не немедленное создание отдельного PR. Автоматическое получение оперативных фактов имеет отдельный жизненный цикл.

Кураторы ведут свои зоны ответственности; зона — фильтр «Моя зона ответственности» по умолчанию и рабочая договорённость. Права у всех кураторов равны, технического запрета редактировать чужую зону нет; общие данные видны всем. Пересечение правок является редким исключением. Подтверждён базовый процесс при подготовке/доработке пакета: разные поля совмещаются с актуальным main в предпросмотре; для разных значений одного поля показываются исходное, принятое и предлагаемое значения, куратор явно выбирает итог, после чего повторяются проверки и сводка. Это совмещение предложения, не действие итогового merge; сложный самостоятельный процесс совместного редактирования из этого решения не следует.

Для PR определяются стабильный идентификатор рабочего пакета, исходная версия main, точная редакция предложения, состав файлов и зависимостей, авторство, основания расчёта и подтверждений. Человеческая сводка должна отражать машинные изменения и показывать их влияние на цели, периоды, значения, статусы и актуальность. Изменение main или предложения требует пересчёта применимости сводки и проверок.

Необходимы сценарии повторной отправки без дубликата PR, таймаута после успешного создания, доработки существующего PR, отмены/отклонения, конфликта и утраты актуальности подтверждения. Состояния приложения сопоставляются с реальными состояниями и событиями конкретной версии Bitbucket. Уведомления не дублируются при каждом опросе и ведут к нужному PR или замечанию.

Проверки перед внешним слиянием должны быть согласованы с возможностями корпоративного Bitbucket и доступной CI-инфраструктурой. Один факт отсутствия текстового Git-конфликта не доказывает корректность совмещённых методик, фактов и подтверждений. Конкретные гарантии блокировки слияния определяются после проверки среды; локальный предпросмотр не выдаётся за уже настроенный серверный merge check.

## Идентичность и определение доступа

По D-120–D-123 источник режима и имени — только hostname-профиль в закрытом служебном Git-репозитории с соответствием hostname → человек/роль. Привязка профиля к аккаунту Bitbucket и отдельная проверка личности для включения режима не вводятся. Основной репозиторий приложения остаётся один; служебный реестр является явным исключением к D-110, а не несколькими рабочими пространствами. Полный контракт — [15-access-policy.md](15-access-policy.md).

Реестр задаёт `viewer`, `curator`, `chief`; главный УОР в обычной панели имеет возможности куратора. Читать служебный репозиторий могут только УОР, изменять реестр и назначения главного — только главный УОР. Кураторы получают для него Read, владелец обслуживает защищённую ветку с необходимыми правами Bitbucket. Это не новая функция обычной панели.

При старте локальный Node получает hostname стандартным `os.hostname()` и проверяет принятую версию реестра. Перед каждым push, включая повтор, hostname и активная роль проверяются заново непосредственно перед сетевой записью. Локальный отказ означает ноль попыток push и записей PR. Реальная авторизация Git/Bitbucket для push, операций PR и merge выполняется независимо от hostname-профиля; аккаунт отправителя с этим профилем не сравнивается. Итоговый merge главного/владельца остаётся в Bitbucket. По D-123 проверка соответствия профиля Bitbucket account ID не включается в текущую схему.

По D-098 ранее проверенный профиль режима позволяет создавать и редактировать локальные черновики при временной недоступности реестра. Явный отзыв записи отличается от недоступности; история и черновики сохраняются. Отправка требует свежей проверки, восстановления связи недостаточно. Состояние и offline-кэш режима привязаны к фактическому hostname, идентификатору установки и репозиториям; аккаунт Bitbucket в эту привязку не входит (D-123). Перенос архива на новый ноутбук не переносит допуск. Полный реестр не выдаётся читателям, не включается в основной Git или обычный архив. Приёмка включает отзыв после входа, повтор push, недоступность и перенос без сетевых записей при локальном отказе.

Приветствие при старте — немодальное мини-окно «С возвращением, <имя>» с закрытием вручную или через 5 секунд. Имя берётся из собственной допустимой проекции; при его отсутствии — «С возвращением». Приветствие не задерживает работу и не подтверждает полномочия.

Контракт происхождения различает аутентифицированного отправителя PR, автора изменения, сборщика и проверяющего факты, установку приложения и рабочий пакет. Аудит сетевого отправителя сохраняется отдельно от hostname-профиля, не используется для выбора режима и не сравнивается с профилем (D-123). Для пакета задаются стабильный идентификатор, операции и редакции, исходная версия main, хеш содержимого, затронутые сущности и периоды. Время локального действия и время регистрации события Bitbucket имеют отдельное происхождение.

Идентификатор установки создаётся при подготовке нового рабочего места и не выдаётся за удостоверенную идентичность физического устройства. Чистая поставка не содержит чужого идентификатора установки; перенос на другую станцию создаёт новый, сохраняя происхождение старых записей. Смена учётной записи сохраняет различие авторов. Общее наблюдение за ещё не отправленными локальными черновиками не предполагается.

Границы расширения проверяются на конкретном примере нового сервиса. Новая интеграция разделяет получение данных, разбор и принятие проверенного результата, чтобы не создавать обход общей модели фактов. По D-097 модули поставляются общим выпуском через Git; конкретная регистрация проектируется в рамках этой поставки. Независимая динамическая установка исполняемых модулей для текущего этапа не требуется.

Понятие «универсальный модуль» раскрывается перечнем поддержанных вариантов и ограничений. В спецификациях должно быть видно, какие изменения требуют кода, а какие доступны куратору через настройки.

## Уведомления и подписки

Подтверждены уведомления внутри приложения: риски и блокировки адресуются основному куратору цели и ответственному за затронутую работу, запрос решения — человеку, от которого ждут решения. Остальные сотрудники могут подписаться на нужные цели. Подписка не ограничивает видимость остальных общих данных и не выдаёт право редактирования.

Подтверждён порядок повторов: новое событие — один раз; по открытым рискам, блокировкам и просроченным решениям — раз в день, частоту настраивает куратор. После перерыва показывается актуальное напоминание без накопления пропущенных повторов. Проверочный пример: приложение не запускалось несколько дней, риск остаётся открытым — при запуске показано актуальное напоминание, а пропущенные дневные повторы не воспроизводятся очередью. Получение того же события при повторном опросе не считается новым событием. Плановый повтор по нерешённой причине отличается от такого дубля.

Повторные ежедневные напоминания показываются только по рабочим дням общего календаря УОР, который настраивает куратор. Общая версия календаря распространяется в установленном процессе публикации. Будущая спецификация должна проверить, что в нерабочий день календаря очередной дневной повтор не создаётся, а после перерыва в рабочий день показывается актуальное напоминание без очереди пропущенных повторов. Выбор календаря повторов не определяет правила переноса сроков, границы периодов фактов или оценку их давности.

Ежедневное напоминание по умолчанию назначено на 09:00 по Москве; куратор может менять время. Если приложение запустили позже назначенного времени, показывается актуальное напоминание при запуске. Будущая спецификация таймера должна проверить открытое приложение к назначенному моменту, поздний запуск в рабочий день, повторный запуск и возобновление после сна без дублирования одного планового напоминания. Поведение при запуске до назначенного времени после многодневного перерыва следует явно согласовать в окончательном дизайне таймера, сохранив принцип одного актуального напоминания без очереди пропущенных повторов.

Будущая спецификация должна связать адресата со справочником людей и идентичностью подключённого пользователя, различить событие, причину проблемы и состояние чтения уведомления. Один человек, совпадающий по нескольким назначениям, должен понимать одно событие без лишних дублей; это требование удобства для проектирования механизма. Доставка общих событий учитывает получение данных из Bitbucket/main локальным приложением. Для границ дня используется Europe/Moscow. Основного куратора меняют вручную; эскалация и механизм при закрытом приложении ещё не согласованы.

## Первоначальный перенос

По D-112 переносятся текущие цели, справочники, комментарии и история; кураторы проверяют и исправляют их в новом приложении. Спецификация миграции включает исходный формат, таблицу сопоставлений и идентификаторов, проверку ссылок и количества записей, список неподтверждённых или неперенесённых элементов с причинами и понятный предпросмотр результата. Повторный запуск не должен создавать дубли.

Неполные исторические основания отмечаются явно; прежние факты и правила не реконструируются догадкой. Сохраняются исходное происхождение и отличие последующих исправлений. По D-111 автоматически ничего не удаляется. Нужна проверка переноса на реальном обезличенном образце и возможность продолжить после ошибки, сохранив источник.

## Описательные поля без кода

По D-109 куратор добавляет описательные поля без программирования и использует их в таблицах, фильтрах и дашбордах. Общие настройки полей проходят обычные черновик и PR; настройка поля не меняет официальную методику расчёта сама по себе. Поддержанные типы и область применения полей ещё проектируются.

Контракт должен определять устойчивый идентификатор поля, сущности и область применения, тип значения, допустимые настройки и проверку, версию определения и поведение существующих значений при изменении настройки. Видимое имя не должно быть единственным ключом хранения. Общие формы, таблицы, фильтры и блоки дашбордов читают одно определение, а не вводят отдельные несовместимые описания. Приёмка: куратор добавляет поле через приложение, использует его в таблице, фильтре и дашборде, затем публикует настройку и другой пользователь получает её через общий процесс.

## Единый поиск

По D-108 нужен общий поиск по объектам всех модулей: целям, продуктам, лидерам, работам и решениям. Выбор результата сразу открывает карточку соответствующего объекта. Новый модуль подключает к тому же механизму свои объекты и переходы.

Контракт определяет устойчивую идентичность результата, тип, отображаемое имя, контекст, доступные для поиска поля, обновление поисковых данных и маршрут карточки. Приёмка расширения должна показать, что объект нового модуля находится из общей строки и открывается без отдельной поисковой страницы этого модуля. Поиск не изменяет предметные данные и права редактирования. Точное сопоставление запроса и технология хранения индекса ещё проектируются.

## Резервные копии и перенос рабочего места

По D-107 нужны автоматические резервные копии и перенос одним архивом через приложение. Механизм общий для настроек, черновиков, локальной истории и данных самостоятельных модулей. Новый модуль описывает свои сохраняемые данные и версии через контракт, чтобы участвовать в тех же сценариях без собственного отдельного инструмента копирования.

Спецификация определяет состав архива, согласованное состояние данных во время создания, совместимость версий, проверку целостности, предварительный просмотр восстановления и восстановление после ошибки. Общий сценарий не подменяет авторство старых записей и не публикует черновики в Git. Закрытый служебный реестр и переносимые полномочия исключены из обычного архива по D-120–D-122 и документу 15; после переноса роль проверяется заново. Расписание, место копий и правила переноса прочих приватных подключений ещё проектируются; по D-111 автоматическое удаление сохранённых данных не предусматривается. Приёмка должна включать восстановление на чистом рабочем месте и сохранение исходных данных при непригодном архиве.

## Конструктор общих дашбордов

По D-100 куратор собирает аналитические экраны из готовых блоков без написания кода. Общая конфигурация проходит локальный черновик и публикацию через накопленный PR. Новый тип блока добавляется как программное расширение в общей поставке по D-097. Настройки визуализации не меняют официальные факты, статусы и методики целей.

Спецификация должна определить каталог поддержанных блоков, доступные подготовленные данные, настройки, общие фильтры, сохранение композиции, предварительный просмотр, версии конфигурации и поведение при недоступных данных или компоненте. Приёмка: куратор собирает новый экран из существующих блоков и публикует его обычным процессом, другой пользователь получает этот экран с общей версией. Простота настройки проверяется на конкретном сквозном примере; drag-and-drop, произвольный код и универсальный язык запросов этим решением не предписаны.

## Признаки готовности к реализации

По D-115 карта целей непрерывная, изменения выполняются по необходимости. Спецификация жизненного цикла не должна вводить обязательный ежегодный сброс или подменять прежние целевые значения новыми в исторических основаниях. Периоды фактов, сроки отдельных целей и изменения планов сохраняются явно.

По D-116 неактуальная цель архивируется и возвращается через PR. Архивирование сохраняет дату, причину, историю и доступ через поиск; активный обзор её не показывает. Проверка должна включать поиск архивной карточки, неизменность прежних оснований и возврат через общую публикацию. Признак архивирования не должен подменять выполнение цели или автоматически отменять связанные работы.

По D-118 ручная цель допускает возврат из «Выполнена» в «В работе» с обязательной причиной через PR. Приёмка включает отказ при пустой причине, сохранение прежнего завершения в истории, различие чернового и опубликованного статуса и получение нового состояния после merge. Эталон ручной цели не заменяется проверкой аналогичного перехода отдельной работы.

По D-113 первый запуск общий, сразу для всех сотрудников. Отдельный пилотный этап не входит в план. Проверки переноса, предметных расчётов, ролей и цикла PR/merge/обновления относятся к подготовке выпуска, а не заменяются самим массовым запуском.

По D-104 аналитика поддерживает дневную и недельную динамику оперативных показателей отдельно от согласованных срезов. По D-105 ОКО отдаёт текущее состояние; история автоматически накапливается при обновлениях. По D-106 общая история распространяется через обычные PR кураторов и main; свежие локальные наблюдения обозначаются отдельно, за дни без данных в исходном ряду остаются пропуски. Контракт различает область показателя, дату/период факта, источник, получение, полноту и основание расчёта; время загрузки не подменяет дату факта. По D-111 история бессрочна, автоматическое удаление не допускается.

По D-119 недельное представление использует пятничные точки, а не произвольную сумму или среднее; одинаковые значения соединяются горизонтальной линией. По D-124 Q-02 закрыт: если свежего пятничного наблюдения нет, показывается последнее известное к этой пятнице значение с исходной датой и предупреждением «Данные не обновлялись». Если до этой пятницы значений нет, показывается «Нет данных», не ноль. Дата недельной точки и исходная дата данных сохраняют разный смысл.

Такая пятничная точка — производное представление. Она не создаёт нового измерения, не заполняет дневной пропуск исходной истории по D-106, не обновляет давность и сама не создаёт подтверждение выполнения или согласованный срез. Приёмка включает новое пятничное наблюдение; одинаковые значения; последнее значение четверга при отсутствии пятничного с исходной датой и предупреждением; полное отсутствие прежних значений; неизменность исходных пропусков, дат и подтверждений. Проверяются также доступ к прежним периодам после миграции и получение общей истории после merge. Ретроспективное получение из ОКО не предполагается. Q-03 закрыт D-125: назначения целей и изменения организационных связей действуют с публикации в main; отдельная деловая дата и ретроактивное переназначение не вводятся.

Подтверждённый профиль одного получения ОКО по D-103 — до 2 000 строк для одной цели. Проверки загрузки, сопоставления, расчёта и просмотра данных должны включать набор этого размера. Это не установленный размер накопленной истории и не правило отбрасывания больших файлов. Числовые критерии времени выполнения, количество одновременно обрабатываемых целей и объём истории ещё предстоит определить; скорость не объявляется достигнутой без измерения.

По D-114 ориентир аудитории — 100 сотрудников с локальными установками. Проверка должна различать отзывчивость отдельного приложения и совокупные обращения клиентов к Bitbucket/ОКО. Число пользователей не является подтверждением допустимого числа параллельных запросов внешнему сервису или наличия доступа к каждому источнику.

Сценарий можно передать агенту, когда определены его входы, выходы, состояния, примеры и проверка; зависимости доступны; значимых двусмысленностей в рамках задачи не осталось. Для качества и производительности заданы согласованные измеримые критерии.

Новый исполнитель проверяет комплект на воспроизводимость: по описанию восстанавливает небольшой сквозной сценарий и отмечает места, где пришлось угадывать. Такие пробелы устраняются до распространения подхода на весь проект.

Реализация начинается с выбранного и согласованного проектного решения, затем идёт по плану небольшими проверяемыми срезами. Итоговая приёмка оценивает пользовательский результат, корректность данных и работу в согласованной среде.
