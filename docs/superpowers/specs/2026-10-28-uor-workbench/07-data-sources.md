# Источники фактов и контракт получения данных

Дата: 27 октября 2026 года. Статус: исследование и основа дальнейшей спецификации подключения источников; готовый адаптер не определён.

## Подтверждённая модель работы

Для цели определяется штатный способ получения данных:

- Есть отчёт ОКО/Qlik Sense — автоматическое получение.
- ОКО для цели вообще не настроено, есть Excel или CSV — импорт файла.
- Нет дашборда ОКО и файлов, цель статусная — ручной ввод статуса.

Способ получения задаётся для цели; сравнение конкурирующих значений разных каналов не требуется. Состав полей ручного статуса предстоит определить в будущей спецификации.

Центрального сервера нет. Каждый сотрудник самостоятельно получает факты на своём ноутбуке. Для автоматического режима порядок такой: успешное прямое получение; при недоступности Qlik — последний успешный локальный факт с датой и предупреждением; если его нет — опубликованные данные Git. Если факта нет и в Git, явно показано отсутствие данных. Ошибка Qlik не переключает цель на Excel. Одинаковый полный доступ всех сотрудников к Qlik не требуется.

Git содержит общие настройки, комментарии, согласованные итоги и необходимые факты или срез для резервного получения. PR готовятся пакетно один или два раза в неделю либо при важном событии. Каждое обновление фактов не требует PR. Общие настройки содержат определения показателей и правила получения без паролей, токенов и других секретов.

У фактов сохраняются происхождение, дата данных, давность и охват. Дата скачивания пакета Git показывается отдельно: загрузка не делает старые данные свежими. При ошибке Qlik последние локальные 92% сохраняются с датой и предупреждением; более старый Git-факт их не заменяет.

Текущий расчёт по опубликованной методике отделён от согласованного среза. Различие объясняется периодом, датой данных, версией методики и датой согласования. Читатели не получили права вручную изменять официальные значения. Согласованное ручное исправление ошибки источника по D036 и D037 остаётся отдельным процессом, а не штатным вторым источником.

## Проверенные возможности Qlik

1. **Engine JSON API позволяет получать рассчитанные данные объектов.** Метод GetHyperCubeData возвращает страницы данных прямого гиперкуба; суммарный предел одного запроса — 10 000 ячеек. Для сводных таблиц используется другой метод. Получение полного набора требует учёта режима объекта и страниц. [Документация GetHyperCubeData](https://help.qlik.com/en-US/sense-developer/May2026/Subsystems/EngineJSONAPI/Content/service-genericobject-gethypercubedata.htm).

2. **В Qlik Sense Enterprise on Windows предусмотрен ExportData.** Метод возвращает временную ссылку на файл, доступный создавшему его пользователю, и проверяет право exportdata. Есть ограничения объектов, форматов и размера; CSV поддерживается не для всех объектов. Метод прямо обозначен как неподдерживаемый в SaaS. [Документация ExportData](https://help.qlik.com/en-US/sense-developer/May2026/Subsystems/EngineJSONAPI/Content/service-genericobject-exportdata.htm).

3. **В Qlik Cloud ExportData заменён Reporting Services API.** Для данных объекта предусмотрен запрос sense-data-1.0 с результатом XLSX. Генерация асинхронная: запрос, проверка статуса, получение файла. Контекст выборок можно передать через закладку. Это отдельная альтернатива Windows, доступность которой ещё предстоит установить. [Сравнение API](https://portal.qlik.dev/apis/api-comparison-chart/), [Reports API](https://qlik.dev/apis/rest/reports/), [Пример экспорта](https://portal.qlik.dev/embed/reports/qlik-api-export-data/).

4. **Авторизация различается между развёртываниями.** Для Windows официальный пример JWT использует административно настроенный virtual proxy. Для Cloud Qlik рекомендует OAuth 2.0 для большинства сценариев; API key действует с правами создавшего его пользователя. Это не устанавливает схему доступа в нашей среде. [Windows и JWT](https://portal.qlik.dev/toolkits/qlik-cli/qlik-cli-qrs-get-started/), [Авторизация Cloud](https://portal.qlik.dev/authenticate/).

5. **HTML дашборда не задаёт универсальный контракт данных.** Это технический вывод из модели Qlik: начальная порция гиперкуба может быть неполной, последующие страницы получают отдельными вызовами. Контракту нужны идентификаторы объекта и контекст выборок; видимое число или сохранённая страница их не заменяют. [Получение данных гиперкуба](https://portal.qlik.dev/extend/extensions/extension-api/build-extension/hypercube/).

Редакция, версия, лицензии, SSO и допустимый способ фонового доступа пока неизвестны. Наличие ссылки на дашборд не подтверждает пригодность конкретного API, экспорта или авторизации. Новые серверы и прокси этим исследованием не предусматриваются.

## История оперативных показателей

По D-104 нужны дневная и недельная динамика отдельно от согласованных срезов. По D-105 в ОКО доступно только текущее состояние, приложение автоматически сохраняет историю при обновлениях. История описывает полученные наблюдения; восстановление прежних дней из ОКО не предполагается. Контракт сохраняет дату/период источника отдельно от момента получения; чтение резервного набора не делает прежний факт свежим и не должно создавать выдуманное измерение за новый день.

По D-106 куратор включает накопленные наблюдения своей зоны в обычный PR, после merge общая история распространяется через main. Более свежие локальные наблюдения обозначаются отдельно; общий опубликованный ряд и согласованный срез различаются. За дни без данных остаются пропуски. Получение ОКО каждым клиентом не делает его локальную историю общей автоматически; история клиента не отправляется отдельным PR при каждом обновлении. Сбор при закрытом приложении и восстановление пропущенных дат этим решением не предусмотрены.

## Состав будущего контракта

Подключение задаётся для цели: у неё свой источник со всем нужным набором продуктовых данных. Для ОКО используется постоянная ссылка этого источника; отдельные источники на продукты не требуются. Реальные внешние ключи, колонки и способ полного получения набора проверяются при подключении, а не выводятся из стабильности ссылки.

Для цели и её показателей необходимо зафиксировать:

- **Идентификацию:** режим получения, первичный источник, среду, app ID, object ID, показатель и соответствие полям общей модели. Для Excel и CSV — файл, лист или таблицу, заголовки и формат; для ручного статуса — основание и допустимую роль; для Git — версию пакета и происхождение включённых фактов.
- **Контекст:** выборки, закладку или фильтры, подразделение, период и его границы. Одинаковое имя показателя при разных выборках не гарантирует сопоставимость.
- **Ожидаемый состав:** необходимые подразделения, строки, измерения и поля, ключи сопоставления, единицы, масштаб и правила интерпретации значений.
- **Полноту:** ожидаемый и полученный охват, отсутствующие обязательные элементы, ограничение прав, обрезку экспорта и неполученные страницы.
- **Актуальность:** дату данных и время обновления самого источника отдельно от времени локального получения либо скачивания пакета, периодичность и ожидаемую задержку.
- **Авторизацию без секретов:** способ входа, требуемые права и область видимости. Учётные данные в общий Git не включаются.

## Полнота и подтверждение выполнения

Для файловой цели куратор один раз настраивает колонки и повторно использует настройку. Перед сохранением показаны распознанные данные, пропуски и ошибки. Предпросмотр не меняет факты. Куратор может сохранить корректные строки; непринятые показываются с причинами, данные явно неполные. Исправленный файл дополняет прежние корректные данные того же периода. Изменения уже имеющихся значений показываются как «было / станет»; куратор применяет выбранные исправления одним действием, прежние значения сохраняются в истории.

Ручная статусная цель имеет состояния «Не начата», «В работе», «Выполнена». При «Выполнена» обязательно краткое описание результата; ссылка или файл — при необходимости. Числовой факт для неё не выдумывается.

По D-118 куратор может вернуть такую цель из «Выполнена» в «В работе» с обязательной причиной. Прежнее завершение сохраняется, изменение становится общим через PR и merge. Источник ручного статуса не подменяется числовым прогрессом.

Неполноту необходимо показывать явно вместе с причиной и затронутым охватом. Отсутствие данных применимого обязательного показателя блокирует подтверждение выполнения цели до получения данных, даже если предварительный балл рассчитан без него. Неприменимость N/A — отдельный случай с причиной и периодом действия. Правила исключения данных из предварительного расчёта, политика необязательных показателей и пороги полноты ещё не согласованы. Ошибка доступа, обновления или отсутствие факта во всех доступных источниках не должны молча превращаться в ноль либо N/A.
