# Уточнение: ОКО через СберБраузер и записываемый сценарий

Дата: 28 октября 2026 года. Основание — прямое уточнение пользователя при подготовке плана: запуск сессии СберБраузера, известная ссылка отчёта, запись действий/фильтров/скачивания, сохранение и автоматическое повторение. Это основной путь ОКО первой версии; выбор протокола больше не оставлен открытым.

Документ дополняет 15–19 и имеет приоритет в части способа ОКО. Реальная совместимость СберБраузера и корпоративного входа ещё проверяется BP-03; этот текст не означает выполненного входа или скачивания.

## Что должно получиться

1. Куратор открывает настройку источника цели в разделе «Данные».
2. Указывает известную постоянную ссылку отчёта и локальный профиль браузера.
3. Приложение запускает установленный СберБраузер с выделенным сохраняемым пользовательским профилем. Повторный запуск использует его сессию.
4. После подтверждённого открытия отчёта куратор включает запись, применяет фильтры и запускает выгрузку.
5. Приложение фиксирует поддержанные действия и завершающее скачивание. Куратор завершает запись, проверяет шаги и один раз подтверждает безопасные значения параметров фильтров.
6. «Проверить сценарий» повторяет действия и показывает файл/столбцы/пропуски; проверочный прогон сам не создаёт факты или подтверждение цели.
7. Сценарий и ссылка источника сохраняются в рабочий пакет и публикуются обычным накопленным PR.
8. Любой пользователь с доступом к отчёту запускает опубликованный сценарий через «Обновить данные». Локальный планировщик может выполнять ту же операцию в работающем приложении.
9. Скачанный файл проходит общий конвейер Raw → Normalized → Enriched → Calculated. Первичный источник остаётся ОКО, а не файловый резерв.

Нужный ручной корпоративный шаг переводит операцию в waiting_user; после него проверяется состояние отчёта и выполнение продолжается. Нажатия «успех» без фактического файла нет.

## Что уже есть в исходном коде

В исходной ревизии 0.4.1 есть `src/features/connectors/browser.ts`: openBrowser, startRecording, finishRecording, executeBrowser; `contracts.ts`, `transport.ts`, private-config и browser fixture tests. Уже используются Playwright, persistent profile, очередь профиля, download event и декларативные действия.

Это основа переиспользования через узкий порт. Описанный отдельно Python-loader в SYSTEM_BLUEPRINT не является доступным исходным пакетом этого checkout; объявлять его запущенным приложением нельзя. Новый обязательный Python-worker ради дублирования существующего Node-кода не вводится.

Из описания прежнего контура известны корпоративный Sberbrowser, NSS/mTLS и SSO. Их фактическая работа на целевом ноутбуке проверяется в BP-03: браузер использует разрешённую корпоративную конфигурацию, приложение не заменяет её догадкой о странице ввода пароля.

## Профиль, запись и общий сценарий

Приватная привязка содержит путь установленного браузера, локальный managed profile, разрешённые origin, настройки таймаутов/размера и ссылки на разрешённые средства входа. Она остаётся локальной. Обычный запуск использует выделенный persistent profile, а не копирует произвольный открытый профиль сотрудника. Подключение к уже работающему процессу возможно только после отдельного подтверждения технической возможности в среде.

Имя профиля не является ролью УОР. Учётные сведения, cookies, сертификатные ключи и снимки браузера не входят в общий сценарий, Git-пакет или обычный перенос полномочий. Запись начинается только после authenticatedSelector и отсутствия видимой формы входа. Открыть профиль для входа можно без подключения recorder-инструментов.

```ts
type StableBrowserLocator =
  | {kind:'css'; selector:string}
  | {kind:'role'; role:BrowserAriaRole; name:string; exact:true}
  | {kind:'label'; text:string; exact:true};
type RecordedBrowserStep =
  | {action:'goto'; url:string}
  | {action:'click'|'wait'|'download'; locator:StableBrowserLocator; framePath?:StableBrowserLocator[]}
  | {action:'fill'|'select'; locator:StableBrowserLocator; parameter:string; framePath?:StableBrowserLocator[]}
  | {action:'check'; locator:StableBrowserLocator; checked:boolean; framePath?:StableBrowserLocator[]};
type BrowserScenarioDefinition = Header & {
  sourceId: UUIDv4;
  startUrl: string;
  authenticatedSelector: string;
  steps: RecordedBrowserStep[];
  parameters: Record<string, string>;
  expectedExport: { format: 'csv' | 'xlsx'; requiredColumns: string[] };
};
```

entityType — `browser_scenario`; SourceDefinition получает `browserScenarioRef?:VersionRef|null`. Qlik-источник использует опубликованную версию сценария, читатель не может исполнять чужой неопубликованный черновик. Изменение сценария и source reference публикуются согласованно в одном пакете. Имя типа BrowserStep старого helper и нового wire сопоставляет явный адаптер.
role валидируется по поддержанному ARIA whitelist; locator имеет exact semantics, не выбирает первый из нескольких совпавших элементов. framePath задаёт только разрешённые report frames и не разрешает запись формы входа.
BrowserAriaRole: button/link/combobox/textbox/checkbox/option/tab/menuitem/radio/dialog/heading/table/row/cell/listbox. Остальные роли отклоняются до replay.

Поддержанные действия: goto, click, fill, select, check, wait, download. Текстовые значения — именованные безопасные параметры, заполняемые/подтверждаемые один раз после записи. Пароли, OTP, токены и шаги входа не записываются. Последний шаг — ровно одно download; временный подписанный URL выгрузки не сохраняется как постоянная ссылка.

Выбирается однозначный устойчивый locator (роль/подпись или проверяемый CSS/data-testid/id/name). Неоднозначное или неподдержанное действие явно показывается, а не теряется молча. Произвольный JavaScript, shell и координатный replay не являются языком сценария. Для iframe проверяется допустимый frame/origin; неподдержанная область требует явной адаптации и проверки, а не обещания записать любой сайт.

wait ожидает объявленный маркер готовности/завершение действия с таймаутом, а не произвольную паузу в секунды. Перед выгрузкой проверяются заданные фильтры/готовность отчёта; сохранившийся выбор предыдущего прогона не считается начальным состоянием автоматически.

Успех требует download event, завершённого файла, непустых байтов, допустимого формата и ожидаемых колонок. Полнота предметных данных проверяется далее по mapping и expectedPopulation 16, не по одному наличию файла. Ошибка или отмена сохраняет прежний успешный набор и понятную причину.

## Команды и роли

Точные payload и реализации фиксирует часть 06 плана, используя envelope/jobs 17:

| Команда | Назначение | Кто |
| --- | --- | --- |
| `source.browser.profile.set` | Настроить собственную локальную привязку; не публикует её. | Пользователь своего рабочего места. |
| `source.browser.login.open/finish` | Открыть профиль без записи и завершить ручной этап. | Все, собственная сессия. |
| `source.browser.record.start/finish` | Записать и получить черновой список действий. | Curator/chief. |
| `source.browser.record.test` | Проверить свой сценарий на реальном файле без принятия фактов. | Curator/chief. |
| `source.browserScenario.draft.save` | Сохранить типизированный черновик для общего пакета. | Curator/chief. |
| `source.capture` | Повторить опубликованный сценарий и принять допустимые факты. | Все с реальным доступом к источнику. |

Проверяется владение записью и профилем. Один профиль не используется одновременно несколькими автоматизациями; ожидающий запуск имеет очередь/отмену. Автоматическая установка неизвестного браузера, отключение TLS и перенос чужой сессии не нужны этому пути.

## Дополнения, обнаруженные при детализации плана

Это конкретизация уже согласованных функций, а не новые бизнес-возможности:

- `workDependency.draft.save` записывает отдельную WorkDependency; `customFieldValue.draft.save` — типизированное значение поля. Оба проходят общий черновик/PR, не обходят строгую схему Work/CustomFieldDef.
- SourceFieldMapping.parsingProfile описывает sheetName, csvDelimiter (запятая/точка с запятой/tab), csvEncoding (utf8/windows1251), dateFormat (iso/dd.mm.yyyy/excel-serial), decimalSeparator и groupSeparator. Неразрешимая дата не угадывается; несовместимые разделители отклоняются; результат виден в предпросмотре.
- Серверные actor/Clock и эфемерная актуальность расчёта уточнены в CONTRACTS.md плана. Открытие карточки не размножает основы и не оставляет устаревшее canConfirm после продвижения часов.
- EvaluationBasis получает templateRef и evaluatedAt первой материализации: версия шаблона входит в смысловой digest, часы — нет. Это служебная прослеживаемость: текущая freshness проецируется заново, а исторический результат/автор/срез не переписываются. Неизвестное прежнее время остаётся null, не равно дате миграции.
- У PublicationAnchor wire revision относится к принятой ревизии пакета; редакция строки metadata в хранилище — отдельный version counter. Уточнение неизвестного времени merge не меняет принятую package revision/hash/commit.
- Для переноса предусмотрен защищённый бинарный `GET /api/v1/backups/:backupId/file` своего архива, для доказательства — `GET /api/v1/artifacts/:artifactId` допустимого сохранённого объекта. Это не произвольный путь файловой системы: владение, hash, размер и связь с опубликованным/собственным Evidence проверяет сервер. Бинарные ответы имеют свои Content-Type/Disposition/hash headers, не JSON envelope.

## Проверка

T42–T48 части 06 плана: схема/профиль → recorder → версия/проверка → replay/приём → мастер → настоящий локальный браузерный стенд → СберБраузер в банке. Локальный Edge/Chromium fixture доказывает исполнение механизма, а не совместимость конкретной банковской сборки.

BP-03 проверяет реальный executable/profile, NSS/SSO, маркер входа, действия настоящего отчёта, параметры фильтров, готовность, скачивание и полноту, повтор с сохранённой сессией, истечение входа и отмену. Нет доступа/параметров — явная BANK_INPUT_REQUIRED/AUTH_REQUIRED, не фиктивный успех.
