# Приёмка целевой версии и контракт передачи агенту

Дата: 28 октября 2026 года. Статус: проект требований к реализации и её доказательствам; перечисленные проверки ещё не выполнены на новой системе. Этот документ не является утверждённым планом изменения кода.

Основание: D-001–D-126 [журнала решений](05-decisions.md), [данные и расчёты](16-data-calculation-contract.md), [интерфейс и API](17-interface-api-contract.md), [интеграции и эксплуатация](18-integration-operations-contract.md), [допуск](15-access-policy.md). Синтетические примеры не объявляются банковскими данными.

## 1. Границы первой версии

В общий выпуск входят цели и методики, справочники, источники и обогащение, текущая и согласованная аналитика, работы/риски/решения, панель УОР, накопленные PR, уведомления, поиск, общие поля, конструктор дашбордов, история, перенос и восстановление. Отчёты/презентации и произвольные новые личные сервисы в приёмку этого выпуска не входят; у платформы есть предусмотренные точки расширения.

Первый запуск — сразу для всех, ориентир около 100 сотрудников. Это не разрешение выпускать непроверенную миграцию: общий выпуск проходит перечисленные проверки до подключения сотрудников. Дополнительный пилотный режим не вводится.

Целевые версии пользователя: Node.js 22.16.0, npm 10.9.2, Python 3.13.5. Python нужен соответствующему адаптеру, если он выбран после проверки ОКО; наличие Python не означает второй обязательный сервер. Текущий `RM_UOR/package.json` уже допускает Node 22.16.0; целевую совместимость всё равно проверяют на указанном runtime.

## 2. Проверочные наборы

Для каждого случая фиксируются: версия набора, время проверочных часов, исходная версия main, hostname-профиль, методика, область/применимость, исходные строки или ручная запись, справочники, ожидаемые значения/состояния/побочные эффекты. У чисел и дат нет зависимости от сегодняшнего дня тестовой машины.

Входные исходные данные неизменяемы. Проверка сопоставляет результат, происхождение и сохранённые основания; сравнение только скриншота недостаточно. Wire-формат чисел и ID берётся из документа 16, форматы HTTP — из 17, пакета — из 18.

Обязательные уровни:

| Уровень | Что доказывается |
| --- | --- |
| Чистый расчёт | Условия, нормирование, веса, обязательность, N/A, полнота, давность, точность и ручные состояния без UI/сети/БД. |
| Сервис и хранилище | Транзакции, ссылки, версии, история, повтор команд, сохранение незавершённых данных и отсутствие обхода политик. |
| HTTP | Валидация, проекция читателя, команды, ошибки, реальные серверные запреты записи и работа фоновых операций. |
| Интерфейс | Клиентский путь, контекст, состояния, понятные ошибки, клавиатура и адаптация; UI отражает то же состояние, что API. |
| Полный сценарий | Получение → обогащение → расчёт → черновик → предпросмотр → PR → внешний merge → обновление второго клиента. |
| Корпоративный источник | Реальный разрешённый вход, полная выгрузка и Bitbucket-операции в банковской среде. Моки этот уровень не заменяют. |

## 3. Каталог обязательной предметной приёмки

| ID | Вход / действие | Ожидаемый результат |
| --- | --- | --- |
| AC-01 | ДИТ: факт 92, условие ≥90. Кластер: факт 88, условие ≥95. | Условие ДИТ выполнено, кластера — нет; скрытого правила «выполнены все дочерние» нет. Подтверждение УОР проверяется отдельно. |
| AC-02 | Нулевой план неотрицательного счётчика: факт 0 / 3 / отсутствует. | Балл 100% / 0% / «Нет данных». Факт 3 остаётся виден, отсутствующее значение не становится нулём. |
| AC-03 | Условия точного равенства и включённого диапазона; факт внутри, на границе, вне, отсутствует. | 100% для выполнения условия, 0% для нарушения, неизвестно без данных; границы включены. |
| AC-04 | Для ≥100 факт 120. | Допустимо перевыполнение 120%; исходный факт не обрезан до 100. Декоративная шкала не подменяет число. |
| AC-05 | Два применимых показателя: веса 20/80, баллы 80/100; первый обязательный. Условие итогового балла ≥95%. | Взвешенный балл 96% проходит итоговый порог, но невыполненный обязательный показатель блокирует выполнение цели. Балл не равен подтверждению. |
| AC-06 | В AC-05 первый показатель отмечен N/A с причиной, областью и периодом. | Он исключён; оставшийся получает полный относительный вес. Причина и период доступны. Все показатели N/A → «Неприменимо», не успешные 100%. |
| AC-07 | Один необходимый показатель отсутствует. | Показаны предварительный балл по формуле 16 и список недостающих данных; новое подтверждение запрещено. Доли известного и применимого состава различимы. |
| AC-08 | У двух показателей разная допустимая давность; один устарел. | Его последнее значение и дата сохранены, есть причина устаревания и уведомление куратора; новое подтверждение блокируется. Старый принятый срез сохранён. |
| AC-09 | Общая методика обновлена и опубликована; есть связанное назначение и назначение со своей методикой. | Связанное использует опубликованную новую методику, собственное сохраняется. Старые согласованные основания не переписаны. |
| AC-10 | Ручная цель завершается без результата, затем с результатом. | Без результата готовый пакет/подтверждение не проходят; незавершённый ввод сохраняется. С результатом допускается предложение через PR; файл необязателен. |
| AC-11 | Ручная цель «Выполнена» возвращается в «В работе». | Причина обязательна; изменение официально только после публикации, прежнее завершение сохранено. См. A-03 документа 14. |
| AC-12 | Продукт получает новую связь с кластером либо назначение цели. | До публикации — только предпросмотр; после — новая текущая основа с publicationAnchor. Выбора даты нет. Старый согласованный срез показывает прежнюю связь и результат (D-125). |
| AC-13 | В пятницу есть новые одинаковые значения; в следующую пятницу обновления нет. | Ровная линия; без обновления показано последнее известное с исходной датой и предупреждением, без нового измерения. Без прежнего значения — «Нет данных» (D-124). |
| AC-14 | Цель архивирована с датой и причиной, затем возвращена через PR. | Активный обзор меняется после публикации; поиск и история сохраняются, связанные работы сами не отменяются. |
| AC-15 | Цель на дату и цель за период получили наблюдения разных дат/периодов. | Режим хранится в цели, выбор следует правилам 16; будущий факт не переносится назад, несовместимые периоды не суммируются. Давность считается по определённому якорю, не по времени чтения кэша. |
| AC-16 | Для назначения куратор выбрал ожидаемые продукты A/B; пришли строки только A. | Отсутствие B видно в полноте и блокирует подтверждение. Ожидаемый состав не выводится из пришедших строк, не подменяется всем оргсправочником и сохраняется в основании. |

## 4. Данные, происхождение и публикация

| ID | Вход / действие | Ожидаемый результат |
| --- | --- | --- |
| AC-20 | ОКО недоступен, локально есть вчерашние 92%, в Git старые 88%. | Отображаются 92% с исходной датой и предупреждением. Без локального набора — 88% из Git; без обоих — отсутствие данных. Ошибка не создаёт факт 0. |
| AC-21 | У цели настроен ОКО; пользователь предлагает Excel как запасной путь. | Автоматического переключения на файл/ручное значение нет. Три режима источника не смешиваются. |
| AC-22 | Продукт не сопоставлен, затем куратор готовит связь. | Исходная строка неизменна; несопоставленность видна. Предпросмотр обогащения показывает эффект, общая версия меняется после merge. |
| AC-23 | Импорт файла: 3 корректные строки и 1 ошибочная. | Куратор может принять 3, отклонённая строка показана с причиной. Неполнота явно сохранена. Повтор того же принятия не дублирует факты. |
| AC-24 | Следующая выгрузка дополняет набор и содержит изменившееся известное значение. | Новые записи дополняют; исправления показаны «было / станет», применяются по выбору одним действием. Прежние значения в истории. |
| AC-25 | После принятой ручной корректировки источник прислал другое значение. | Принятая корректировка не затёрта; расхождение доступно куратору. Новое официальное значение требует нового предложения и публикации. |
| AC-26 | Несколько обновлений источника и сохранений черновика за цикл. | Наблюдения/черновики сохраняются без PR на каждое действие. Один явный submit создаёт накопленный PR этого куратора. |
| AC-27 | Ответ на создание PR потерян после успеха; команда повторена. | Найден существующий PR packageId; повтор не создаёт второй PR. Неизвестный результат не объявляется ошибкой или успехом без сверки. |
| AC-28 | Два куратора отправили свои пакеты. Один merged, другой возвращён на доработку. | Пакеты независимы; замечания дорабатываются в прежнем PR, общая версия соответствует только принятому. |
| AC-29 | Два ноутбука получили один merge в разное время. | Идентичность публикации и принятая редакция одинаковы, appliedAt разный. Подтверждённое mergedAt одинаково; без метадаты время явно неизвестно, не равно pull. Чтение проверенного main не требует обязательного REST-доступа каждого читателя. |
| AC-30 | Повтор команды, частичный сбой записи либо восстановление процесса. | Идемпотентность и журнал 18 дают один итог или явно незавершённое состояние; факт и его история не расходятся. |
| AC-31 | Подготовленные коммиты есть, Git требует авторизацию при push. | Открывается штатная интерактивная консоль/окно Git; пользователь вводит данные самостоятельно. Приложение ожидает результат, не записывает пароль в конфиг/логи и не объявляет отправку успешной раньше проверки. |
| AC-32 | Вход отменён, терминал закрыт либо допуск отозван во время входа. | Коммиты и пакет сохранены. Перед передачей действует свежий gate; нет слепой отправки по прежнему разрешению. Неопределённый внешний эффект сверяется до повтора. |
| AC-33 | Git push успешен, но API Bitbucket требует отдельного входа. | Видно «Коммиты отправлены, PR ожидает авторизации». Повтор продолжает PR-этап без новых коммитов, дубликатов PR и требования совпадения аккаунта с hostname. |
| AC-34 | Файл изменил исходное значение, затем отдельно предложена официальная ручная корректировка. | Импортное исправление создаёт исходную редакцию локального оперативного слоя; ManualCorrection — отдельное предложение с причиной и публикацией. Импорт не перезаписывает принятую ManualCorrection. |

## 5. Доступ, сохранность и интерфейс

| AC-40 | Активный hostname curator/chief без сопоставления аккаунта. | Имя и режим из реестра; отсутствие account binding не блокирует режим. Панель подготовки одинакова, кнопки merge нет. |

| AC-45 | Обычный читатель меняет фильтры, вид дашборда и независимый локальный инструмент. | Общие факты/методика/статус УОР неизменны; локальные настройки сохраняются при общем обновлении. |
| AC-46 | Куратор отменяет блокирующую работу либо возвращает завершённую работу. | Для отмены есть замена или снятие зависимости с причиной; для возврата есть причина и сохранённое завершение. Прогноз не меняет плановый срок. |
| AC-47 | Решение просрочено в 00:00 следующего дня по Москве. | Выходной срок не переносит; напоминание идёт по календарю УОР, по умолчанию в 09:00. После перерыва — одно актуальное напоминание без очереди повторов. |
| AC-48 | Глобальный поиск и переход между пятью разделами. | Найденный объект открывается с понятным контекстом; локальный фильтр не запрещает видеть другие подразделения. Архивные объекты находятся. |
| AC-49 | Настройка методики, колонок импорта, поля и дашборда. | Основной путь не требует кода/JSON; видны проверка, результат и влияние. Общие изменения публикуются через PR. |
| AC-50 | Прерывание обновления или восстановления до/после точки принятия. | Выполнено правило 18: старое рабочее состояние либо новое согласованное; более новые пользовательские данные не стёрты. Ошибка восстановления явно блокирует запись до разрешения. |
| AC-51 | Чтение прошлых периодов после архивирования/обновления схемы. | Вся история доступна, автоматического удаления и lifetime-лимита записей нет. |
| AC-52 | Ширины 320/360/1024 px, клавиатура, загрузка/пусто/ошибка. | Основные действия доступны, формы подписаны, фокус не теряется при фоновых обновлениях, горизонтальный скролл ограничен таблицей. Цвет не единственное обозначение. |
| AC-53 | Проверенный пакет присутствует в main, но точное время merge через Bitbucket не получено. | Текущая общая версия применяется, новые назначения/связи доступны по принятой редакции; дата публикации обозначена неизвестной. Только запрос, которому действительно нужна точная историческая временная граница, получает EFFECTIVE_TIME_UNVERIFIED. До публикации main черновик не активируется. |
| AC-54 | Архив восстанавливается в непустое рабочее место с совпадающими ID/revision. | Preview показывает замену целого состояния, не неявное объединение. Перед активацией есть проверенная спасательная копия текущего состояния; прежние данные доступны через неё и не удалены автоматически. Изменившийся targetRevision отклоняет старый restoreToken. |
| AC-55 | Куратор настраивает источник/колонки, добавляет комментарий и доказательство, сохраняет согласованный срез. | Для каждого действия есть типизированная команда; обычный комментарий не подтверждает цель, сохранение среза не создаёт автоматическую аттестацию, общая версия меняется через пакет/PR. |
| AC-56 | У читателя нет personId из закрытого реестра. | Подписки работают без распознавания личности. Предлагаемый выбор себя в общедоступном справочнике для уведомлений остаётся локальной настройкой, не меняет роль и не создаёт привязку Bitbucket. Приложение не выдаёт этот выбор за удостоверенную личность автора. |

## 6. Проверка банковской среды

Проверки имеют отдельные результаты и зависимости. Пока они не выполнены, допустимы реализация независимых контрактов и проверки с синтетическими адаптерами; полный производственный запуск интеграций не считается готовым.

| Проверка | Необходимый вход | Сохраняемое доказательство | Что зависит от результата |
| --- | --- | --- | --- |
| BP-01 Bitbucket | Разрешённое подключение, редакция/версия, тестовая ветка/PR и права. | Создание/повтор/чтение замечаний, merged/declined; источник mainCommit и реального mergedAt, ограничения main. Секреты не в отчёте. | Реальный адаптер PR, точная дата публикации, корпоративная приёмка. |
| BP-02 Служебный реестр | Адрес, принятая ветка, файл и проверочные профили. | Read куратора, изменение только главным, неизвестный/отозванный hostname и проверка перед push. | Реальный допуск и его отзыв. |
| BP-03 ОКО | Одна фактическая цель и разрешённый способ полного получения. | Схема полей/ключей/дат, полнота, ограничение запросов, результат успешного получения и отказа. | Реальный Qlik-адаптер; файлы и ручные цели не блокируются этим тестом. |
| BP-04 Перенос | Прежняя карта, справочники, комментарии, история и используемые вложения. | Число входных/принятых/проблемных объектов, связи, основания, проверка куратора. Неизвестные значения не дорисованы. | Итоговая миграция и полнота общего выпуска. |
| BP-05 Рабочий ноутбук | Целевой runtime, Git, сеть, сертификаты и доступные каталоги. | Запуск, БД/SQLite, чтение источника, обновление, копия/восстановление. | Подтверждение установки и совместимости в банке. |
| BP-06 Интерактивный Git | Целевой Git/транспорт, разрешённый вход, штатный helper/терминал, существующие корпоративные hooks. | Запрос входа, отмена, exit code/remote-сверка, свежий pre-push gate после ожидания, сохранение hooks и независимый PR-вход. | Штатный интерактивный push D-126; способы запуска терминала на других ОС не считаются проверенными этим тестом. |

Реальная проверка запрещённого действия проводится на согласованной тестовой ветке/данных; схема не требует менять рабочие права сотрудников ради теста. Полные банковские исходники и секреты в публичный репозиторий не добавляются.

## 7. Нагрузка и эксплуатационная наблюдаемость

Исходный профиль: до 2 000 строк одного получения цели, около 100 локальных установок, бессрочная история. Это не лимит общего числа строк и не нагрузка общего прикладного сервера.

До выпуска измеряются загрузка 2 000 строк, расчёт, обзор, поиск, недельная история, копия и применение обновления. В протоколе — набор, объём истории, аппаратный профиль, runtime, число повторов, p50/p95, пиковая память и ошибка/отмена. Внешнее ожидание отделено от CPU/SQLite.

Предложение проектировщика для локальных операций на согласованном тестовом ноутбуке: p95 списка/поиска из индекса ≤500 мс; нормализация и расчёт 2 000 корректных строк ≤2 с без сетевого ожидания. Это проектные цели, не достигнутые показатели. Сетевое ожидание и длительная копия показывают прогресс и не блокируют UI; коррекция цели по замеру документируется с причиной.

Лог связывает requestId/commandId/jobId/packageId и стадию, но не содержит токены, полный закрытый реестр и исходные банковские файлы. Пользователь видит понятную причину, состояние сохранности и доступное следующее действие.

## 8. Условия передачи задачи агенту

Будущий план создаётся по согласованному проектному решению. Каждая задача содержит точный исходный commit и область изменений, нужные разделы 15–19, зависимости, конкретные файлы/команды, ожидаемые входы/выходы, обязательные AC-ID и способ продолжения после ошибки. Задача не получает «готово» только за наличие интерфейса или совпадение типов.

Текущий код находится в `RM_UOR`, совместимая копия — в `RM_UOR-compat-22.16.0`; это не два источника разработки. Исполнитель перед изменениями явно фиксирует выбранный основной checkout и его git status. Копию не обновляет параллельно автоматически. Местные AGENTS.md и навигация читаются; новые решения пользователя имеют приоритет над прежними правилами.

Известные переходы от версии 0.4.1: парольный реестр → политика hostname; release/current → нативный накопленный PR; прежние процедуры очистки видимых журналов → бессрочное сохранение без автоматического удаления. Эти старые механизмы не остаются скрытым обходом новой модели. Конкретные миграционные изменения должны быть в будущем плане, а не выполнены чтением этого документа. Независимый локальный инструмент в AC-45 может быть проверочным модулем платформы; новый личный сервис первой версии этим не заказывается.

В существующем package.json есть `npm test -- <затронутые тестовые файлы>` и `npm run build` (TypeScript + Vite). Это реальные имена команд, но новая реализация ими пока не проверена. Сам `build` не доказывает запуск сервера, совместимость Node 22.16.0, работу источников или корпоративный вход.

После реализации предъявляются: изменение и причина, результаты обязательных AC, команды/runtime/время/exit code, интерфейсный результат при изменении пути, миграционный отчёт, открытые зависимости BP и сохранность прежней базы. Старые счётчики тестов не переносятся как новый результат.

## 9. Граница готовности

Проектирование завершено для передачи на планирование, когда между 15–19 нет существенных противоречий, все известные бизнес-правила связаны с контрактами/AC, технические выборы явно отмечены, а реальные неизвестные среды вынесены в BP с зависимостями. Затем фиксируется согласованная редакция и составляется пошаговый план.

Производственный выпуск готов только после реализации, прохождения нужных AC/BP, проверки реального переноса и восстановления. Сейчас выполнена подготовка документов; новая система не реализована и перечисленные продуктовые проверки не запускались.
