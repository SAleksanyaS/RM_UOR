# Как пользоваться рабочим местом УОР ДИТ

Пошаговое руководство для директора, ИТ-лидера, куратора и сопровождающего. Версия 0.4.1 · 25 октября 2026 года.

**Если приложение уже открывается, переходите к [маршруту директора](#4-маршрут-директора-и-ит-лидера) или [маршруту куратора](#5-маршрут-куратора-от-цели-до-публикации).** Установка нужна только на новом компьютере.

## 1. Что здесь происходит

Рабочее место отвечает на три вопроса: **чего нужно достичь, что подтверждают данные и что делать дальше**. УОР — управление обеспечения развития.

| Вы | Что можете делать |
| --- | --- |
| Директор или ИТ-лидер, режим читателя | Смотреть цели, факты, исполнение, сроки, комментарии и отчёты; получать опубликованные данные |
| Куратор УОР | Всё перечисленное, а также настраивать цели и источники, принимать факты, вести работы, подтверждать результат и готовить публикацию |
| Руководитель УОР | Работать как куратор и выпускать подготовленные изменения через интерфейс Git |
| Сопровождающий | Устанавливать приложение, настраивать учётные записи, доступы, перенос и резервирование |

В интерфейсе есть две роли: читатель и куратор. Кураторский пароль открывает редактирование внутри приложения; доступ к Git или исходному дашборду он не выдаёт.

Несколько слов, которые встречаются на экранах:

| Слово | Простое объяснение |
| --- | --- |
| Цель | Какого результата нужно достичь и по какому правилу его оценивают |
| Факт | Реальное измеренное значение за выбранный период |
| Снимок | Сохранённый набор фактов с периодом и происхождением |
| Черновик | Ваша сохранённая правка до общего выпуска |
| Публикация | Передача выбранной проверенной версии коллегам через общий выпуск |

## 2. Первый запуск на новом компьютере

### Подготовьте папку и инструменты

Потребуются Node.js **22.16.0** и npm **10.9.2**, Git и браузер. Устанавливайте их разрешённым в организации способом. Python 3.13.5 можно оставить: приложение его не использует.

1. Получите проект у сопровождающего или из согласованного репозитория.
2. Поместите его в разрешённую рабочую папку. Пример пути: `C:/ApprovedApps/RM_UOR`; замените его своим.
3. Откройте консоль в корне проекта — там, где находится `package.json`.
4. Установите зависимости:

```text
npm ci
```

### Выберите пустую установку или демонстрацию

**Выполните только один вариант подготовки:** пустой, демонстрационный или пустой с внутренним репозиторием. Сначала выберите подходящий вариант, затем запускайте его команду.

Для новой рабочей установки:

```text
npm run setup:workspace -- --mode empty
```

**Результат:** подготовлено пустое рабочее место. Прежние цели, факты, комментарии и журнал разработки не переносятся; собственная история начнётся с работы на этой установке.

Для знакомства с вымышленными примерами выполните **вместо предыдущей команды**, тоже на новой установке:

```text
npm run setup:workspace -- --mode demo
```

**Результат:** подготовлены синтетические примеры, на которых можно изучить интерфейс. Команда подготовки не очищает и не заменяет существующую установку. Для обычного продолжения работы повторять её не нужно.

### Задайте внутренний репозиторий и проверьте настройки

Если сопровождающий уже выдал адрес внутреннего Git, его можно указать сразу при подготовке новой установки:

```text
npm run setup:workspace -- --mode empty --repository "<URL внутреннего репозитория>" --publication internal
```

Это альтернативная команда подготовки; замените текст в угловых скобках реальным согласованным URL. Проверьте местные параметры в `config/site.local.json`. Локальный файл исключён из Git; исходный пример находится в `config/site.example.json`.

| Поле | Что указать |
| --- | --- |
| `allowedWorkspaceRoots` | Существующую разрешённую папку проекта или её утверждённую родительскую папку |
| `repositoryUrl` | URL согласованного репозитория; рабочие данные — только во внутренний |
| `publishedBranch` | Основную ветку, обычно `main` |
| `releaseBranch` | Ветку подготовки выпуска, обычно `release/current` |
| `publicationMode` | `demo-only` для публичного демонстрационного контура; `internal` только для разрешённого внутреннего |
| `autoOpen` | `true`, чтобы браузер открывался при запуске |

Секреты в этот файл не вставляют. Git использует штатную авторизацию пользователя. При пустом списке разрешённых папок в локальном файле запуск блокируется.

### Откройте приложение

```text
npm run dev
```

**Результат:** открывается браузер с рабочим местом. Обычно адрес — `http://127.0.0.1:5173`. Если браузер не открылся, откройте адрес, напечатанный в консоли. Консоль оставьте открытой; для остановки нажмите **Ctrl+C**.

Повторный запуск использует ту же локальную базу. Это не новая установка и не очистка данных. Подробности корпоративной подготовки и переноса — в [инструкции сопровождения](guides/corporate-transfer.md).

## 3. Вход куратора и файл учётных записей

Для просмотра пароль не нужен. Для редактирования нажмите **«Войти как куратор»** справа сверху, выберите свою учётную запись и введите пароль. **Результат:** в профиле появится ваше имя, а в меню — разделы настройки и публикации. Нажатие на профиль куратора возвращает режим читателя.

Если вашего имени нет в списке, учётную запись нужно настроить **на этом компьютере**. Она не появляется от одного обновления Git.

### Подготовка через локальный файл

1. Скопируйте публичный шаблон `config/curators.example.json` в `.runtime/local-config/curators.input.json`.
2. В локальной копии заполните имена и индивидуальные пароли. Поле `name` — имя в списке входа, `code` — пароль. Примеры замените своими значениями.
3. Выполните из корня проекта:

```text
npm run setup:curators:file -- --file .runtime/local-config/curators.input.json
```

**Результат:** учётные записи подготовлены на этом компьютере. После запуска приложения имена появятся в форме входа. Пароли не нужно вставлять в командную строку или в общие документы.

Файл `curators.input.json` содержит открытые пароли и остаётся приватным. Рабочий реестр `.runtime/local-config/curators.json` хранит идентификаторы, имена, соль и хеши. Реальные пароли и реестр не включаются в публичную поставку.

### Подготовка одного профиля без файла

Для одной учётной записи сопровождающий может запустить:

```text
npm run setup:curators
```

Команда спрашивает имя и пароль; ввод пароля скрыт. В рабочем реестре сохраняются соль и хеш, а не открытый пароль. После изменения реестра перезапустите приложение. Повторная настройка уже существующего имени сохраняет его идентификатор.

Не отправляйте реестр, открытые пароли или файл их первоначальной загрузки в публичный Git. При переносе нужно сохранить устойчивые идентификаторы кураторов и отдельно настроить их доступ. Порядок — в [инструкции переноса](guides/corporate-transfer.md); устройство ролей — в [описании учётных записей](guides/roles-and-accounts.md).

## 4. Маршрут директора и ИТ-лидера

При первом открытии показывается **«Обзор ДИТ»**. Если слева видны только значки, нажмите стрелку **«Развернуть меню»**. На узком экране используйте кнопку открытия навигации.

| Сделайте | Что увидите |
| --- | --- |
| Откройте «Обзор ДИТ» | Общую картину активных целей, подтверждённые результаты, остаток и полноту данных |
| Нажмите на ИТ-лидера | Его персональный срез с назначенными целями и результатами |
| Нажмите на название цели | Карточку с показателями, порогами, участниками, периодом, происхождением фактов и комментариями |
| Откройте «Матрица целей» или «Направления» | Сравнение по лидерам или группировку по направлениям |
| Откройте «Повестка директора» | Ближайшие сроки, отклонения, изменения и решения с ответственными |
| Откройте «Еженедельный отчёт» | Опубликованную куратором текстовую сводку: итоги, главные выполненные задачи УОР, вопросы внимания и планы |
| Откройте «Планы и сроки» / «Исполнение и удержание» | Заявленные работы, вехи, сроки и проверки удержания |
| Нажмите «Обновить данные → Только данные УОР → Начать обновление» | Опубликованную коллегами версию без запроса исходных дашбордов |

**Пример чтения карточки:** у цели указан период данных и статус «ожидает подтверждения». Это означает, что расчёт дал положительный результат, но куратор ещё не подтвердил достижение. Если фактов нет, результат неизвестен. План на 100% сам по себе не подтверждает измеренную цель.

Официальный срок, обязательство исполнителя и прогноз — разные сведения. Смотрите, какое из них показано рядом с датой. Полнота данных также показана отдельно от результата.

## 5. Маршрут куратора: от цели до публикации

**Цель → данные → предпросмотр → принятие → проверка → публикация.** Каждый шаг сохраняет свой результат. Завершение предыдущего шага не выполняет следующий автоматически.

### Шаг 1. Создайте или измените цель

Откройте **«Настройка целей → Добавить цель»**. Для существующей цели откройте её карточку и нажмите **«Показатели и источник»**.

| Шаг мастера | Что заполнить |
| --- | --- |
| Паспорт цели | Полное название, ожидаемый результат, владельца, куратора; срок, направление, вес и приоритет — при наличии утверждённых значений |
| Показатели | Метод расчёта, показатели и единицы, официальный и при необходимости внутренний пороги |
| Ответственные | ИТ-лидеров и точный состав участников; для общей цели — общий контур ДИТ |
| Источник | Откуда поступают данные и как они связаны с целью |
| Проверка расчёта | Пробные значения и проверку ожидаемого результата |
| Сохранение | Сохранить цель и связанные определения в черновики |

**Результат:** цель появляется в локальном каталоге. Пробные значения не становятся фактами и не публикуются. Новая цель остаётся доступной для просмотра даже без фактов.

**Пример:** для доли команд заранее выберите все команды, которые должны участвовать в расчёте. Если пришли строки только по части команд, результат покажет неполноту; присутствующие строки не заменяют весь ожидаемый состав.

### Шаг 2. Загрузите реальные данные

Выберите подходящий путь:

| Данные | Действие | Что получится |
| --- | --- | --- |
| Excel / CSV / таблица | «Загрузить реальные данные» после мастера или «Загрузить данные» в карточке | Мастер сопоставления столбцов, участников и показателей |
| Исходная форма модели зрелости | «Источники и факты → Загрузить Excel / CSV» → выбрать соответствующую цель | Мастер подбирается по настройке цели; для исходной формы — специальный импорт зрелости |
| Ручной факт | «Источники и факты → Внести факт вручную» | Значение с выбранными целью, участником и периодом; для целей с настроенной методикой откроется табличный ввод |
| HTTP / Confluence / Qlik / браузер | «Получение данных» → настройка личного профиля и способа получения | Локальная загрузка под вашими правами с отдельным итогом операции |

Для таблицы укажите период, сопоставьте имена и показатели, устраните ошибки. Поддерживается объявленный формат; произвольная книга Excel не распознаётся автоматически. Формулы и макросы не исполняются. Подробности модели зрелости — в [отдельном гайде](guides/maturity-import.md); подключений — в [runbook](BANK_CONNECTORS_RUNBOOK.md).

**Исходный файл остаётся локальным.** Отдельная настройка источника не подтверждает, что доступ уже работает. Ошибку сети, прав, сертификата или формата нужно устранить; старый файл не становится успешной новой загрузкой.

### Шаг 3. Проверьте предпросмотр и примите факты

Для табличного импорта нажмите **«Рассчитать предпросмотр»**. Сверьте **цель, период, значения, полный состав участников и ошибки**, затем нажмите **«Принять факты»**. В специальном импорте зрелости используйте соответствующие действия распознавания и сохранения. Предпросмотр позволяет обнаружить неверное сопоставление до записи.

**Результат отдельного принятия:** создаётся личный снимок, по которому приложение рассчитывает текущий результат. До принятия значения из табличного предпросмотра не заменяют рабочие факты. Повтор тех же данных не должен создавать новую редакцию; исправленные данные сохраняют прежний снимок в истории.

### Шаг 4. Выполните две разные проверки

| Проверка | Что сделать | Что означает отметка |
| --- | --- | --- |
| **Корректность снимка** | В карточке изучить источник, период, охват, значения и визуализацию; нажать «Снимок и визуализация верны» | Данные проверены и могут участвовать в публикации; отрицательный результат тоже можно проверить |
| **Достижение цели** | Для положительного расчёта добавить обоснование или доказательство и нажать «Подтвердить выполнение» | УОР подтверждает выполнение именно на этой основе расчёта |

**Пример:** снимок показывает результат ниже порога. Его можно проверить и опубликовать как достоверное отклонение; подтверждение выполнения от этого не возникает.

Изменение фактов, правил или состава участников требует актуального подтверждения. При ухудшении прежнее положительное подтверждение теряет силу. Сохранение плана или комментария не создаёт измеренных наблюдений.

### Шаг 5. Подготовьте общий выпуск

1. Откройте **«Публикация»** или нажмите **«Проверить и отправить»** после настройки цели.
2. Получите свежий предпросмотр.
3. Отметьте нужные правки, проверенные снимки, подтверждения, доказательства и шаблоны. Проверьте итоговый состав. Связанные доказательства выбранного подтверждения обязательны; прочие файлы выбираются отдельно.
4. Если одно поле изменили вы и коллега, сравните прежний, свой и общий варианты, выберите значение и сохраните решение конфликта.
5. Отправьте выбранный состав и дождитесь **итога операции**. Сообщение о запуске ещё не означает успешную отправку.

**Результат:** выбранные записи находятся в готовящемся выпуске `release/current`. Руководитель УОР проверяет его через Git UI и включает в `main` обычным слиянием по принятому порядку. Коллеги получают результат через **«Обновить данные → Только данные УОР»**.

Если предпросмотр устарел, обновите его и снова проверьте состав. При ошибке отправки черновики сохраняются. Не удаляйте `.runtime` и не перезаписывайте работу коллег, чтобы обойти конфликт.

Публичный режим `demo-only` принимает демонстрационные данные. Корпоративные данные отправляются только после настройки разрешённого внутреннего репозитория и соответствующих прав.

## 6. Еженедельный отчёт для директора

Откройте **«Еженедельный отчёт»** в левом меню. Это краткий текст о состоянии дел за неделю. Он помогает быстро понять, что изменилось, что сделано УОР, где нужно внимание и что запланировано дальше.

| Раздел сводки | Что написать куратору |
| --- | --- |
| Главная сводка | Главные изменения и результаты простыми словами |
| Главные выполненные задачи УОР | Самые значимые завершённые работы и их результат |
| Требует внимания | Проблемы, риски и решения, которые нужны от руководителя |
| Планы следующей недели | Ближайшие действия и ожидаемые результаты |

Куратор выбирает **«Отчётную неделю»**, нажимает **«Подготовить свою сводку»** или **«Изменить свою сводку»**, заполняет четыре раздела и нажимает **«Сохранить черновик»**. В списках пишите одну задачу или пункт на строке. Кнопка **«К публикации»** открывает общий раздел подготовки выпуска. Сохранённая правка проходит обычный путь: выбранный состав → `release/current` → выпуск руководителем в `main` → обновление данных у директора.

**Результат для директора:** опубликованный текст выбранной недели. Для перехода по неделям есть кнопки **«Предыдущая неделя»** и **«Следующая неделя»**. Личный черновик куратора не появляется у коллег от одного сохранения. Пока сводка не выпущена, читатель видит **«За эту неделю опубликованных сводок пока нет»**. Текстовый отчёт не заменяет факты и подтверждения цели.

## 7. Отчётный снимок и презентация

Раздел **«Отчёты и презентации»** доступен и читателю, и куратору.

1. Выберите период фактов, цели и ИТ-лидеров.
2. При необходимости задайте период сравнения и шаблон презентации.
3. Нажмите **«Сформировать снимок»**.
4. Проверьте таблицу, происхождение и ограничения.
5. Выберите **«Печать / просмотр»**, **«Скачать HTML»** или **«Скачать PPTX»**. В окне печати браузера можно сохранить PDF.

**Результат:** отдельный отчётный снимок со значениями, источниками и подтверждениями на момент формирования. Изменение выбора не изменяет уже сформированный отчёт: нажмите «Сформировать снимок» ещё раз для нового.

Куратор может сохранить состав отчёта и настроить поддерживаемые привязки загруженного PPTX. Для модели зрелости есть [отдельная инструкция](guides/maturity-presentation.md). Сложные объекты PowerPoint и статический текст шаблона не обновляются произвольно; проверяйте итоговую презентацию визуально.

## 8. Обновления, перенос и сохранность

| Нужно | Что выбрать |
| --- | --- |
| Получить выпущенные коллегами данные | «Обновить данные → Только данные УОР» |
| Запросить настроенные источники под своими правами | «Обновить данные → Только источники»; при необходимости сначала «Войти в источник» |
| Получить общие данные, затем источники и пересчёт | «Обновить данные → Обновить всё» |
| Узнать результат и причину ошибки | «История и обновления», текущая операция |
| Обновить программу | «Обслуживание» → обновление программы; [подробная инструкция](guides/code-update.md) |
| Перенести существующие факты и файлы на другой компьютер | Куратору: «Обслуживание → Рабочий набор и хранение → Перенести рабочее место»; [порядок переноса](guides/workspace-maintenance.md) |

Обновление данных и обновление программы — разные действия. Расписание получения работает, пока приложение запущено и нужная сессия действительна.

Рабочая база и личные материалы находятся в `.runtime`. Обычный переносимый ZIP исключает пароли, реестр кураторов, сессии, cookies, браузерные профили и сертификаты; их готовят отдельно. SQLite-копия хранит базу, но не заменяет перенос с внешними файлами. Перед восстановлением прочитайте состав копии: восстановление заменяет текущий рабочий набор и требует нового входа.

### Передать чистую программу без своих рабочих данных

Для новой установки у коллеги подготовьте чистую поставку:

```text
npm run export:clean -- --output .runtime/exports/RM_UOR-clean.zip
```

**Результат:** ZIP с программой для новой установки, без вашей рабочей базы, фактов, журналов и секретов. Это другой способ передачи, чем перенос существующего рабочего набора через «Обслуживание».

Если разрешён перенос уже настроенных локальных учётных записей, добавьте `--with-local-accounts`:

```text
npm run export:clean -- --output .runtime/exports/RM_UOR-clean.zip --with-local-accounts
```

Будут подготовлены **два отдельных архива**: чистая программа и приватный ZIP с локальным реестром хешей паролей. Архив программы остаётся без учётных записей. Приватный архив передают отдельным разрешённым способом; в публичный Git его не загружают. Подробный порядок установки и проверки — в [инструкции сопровождения](guides/corporate-transfer.md).

## 9. Если что-то не получилось

| Что видно | Что сделать |
| --- | --- |
| `npm`, `node` или `git` не найдены | Проверить установку инструментов и заново открыть консоль |
| Запуск запрещён из этой папки | Проверить фактический путь и `allowedWorkspaceRoots` в `config/site.local.json` |
| Адрес не открывается / служба не отвечает | Проверить окно запуска, сообщение об ошибке и напечатанный адрес; не запускать второй экземпляр поверх первого |
| Нет нужного раздела или кнопки | Проверить роль справа сверху; редактирование доступно куратору |
| Учётная запись отсутствует или пароль не подходит | Обратиться к сопровождающему этой установки; обновление Git пароли не переносит |
| «Нет данных» или неполный охват | Проверить период, состав участников и принятые факты; отсутствие данных не означает нулевой результат |
| Источник требует входа или выдаёт отказ | Выполнить обычный вход, проверить права, сеть и профиль с сопровождающим; изучить итог операции |
| Публикация недоступна | Проверить внутренний репозиторий, Git-права, режим публикации и конфликты |
| Предпросмотр устарел | Обновить предпросмотр, повторно проверить значения и выбранный состав |
| Отчёт не показывает сравнение | Проверить наличие сопоставимых принятых фактов для обоих периодов |
| После перезапуска старая операция отмечена прерванной | Изучить её итог, затем повторить нужное действие; прежние факты не удалять |

Для обращения к сопровождающему достаточно указать **действие, время, раздел и текст ошибки**. Секреты, cookies и полную `.runtime` в общую переписку не отправляют.
