Сначала прочтите [AGENTS](../../AGENTS.md), [README](../../README.md), [MASTER_SPEC](../MASTER_SPEC.md), [module-map](../architecture/module-map.md), [акт0.6](../validation/product-2026-11-02.md) и [границы](../remaining-work.md). Старый PROGRESS/контракты0.5 остаются историей архитектуры; не начинайте их реализацию заново.

## Перед изменением

Получите фактический main, запишите SHA и статус дерева, сохраните незавершённую работу. Не предполагайте прежнее имя ветки. Разрешение владельца на публикацию выпуска0.6 не является бессрочным разрешением на любую будущую задачу. Не меняйте старые checksum-контракты ради зелёного теста.

Среда закреплена: Node 22.16.0/npm 10.9.2/существующий lock. Целевой браузер — СберБраузер 152; синтетический Chromium в тесте не доказывает банковскую совместимость. На Linux подготовленный комплект использует runtime/node; ежедневный launcher не устанавливает зависимости.

## Где менять

- Production: `src/server/main.ts` → `createWorkbenchRuntime` → `createWorkbenchApp`; `src/app/main.tsx` → `WorkbenchApp`. Legacy entrypoint не подключать как запасной путь.
- Каждая feature владеет своим contracts/service/UI/tests. Таблица0.6 в module-map показывает новые архивные owners и seams. Общие wiring-файлы меняет один координатор.
- Личный захват, общие источники и AI используют разные recovery namespaces. Неизвестная отправка требует reconcile прежней команды; новый commandId не является восстановлением.
- Typed archive проверяется на активных и staged roots; полный backup включает новые сохраняемые модули и visible/hidden raw. Чужая личность не становится своей от смены role/name.
- Pure evaluation не читает UI/HTTP/БД. Исторический snapshot не пересчитывается по свежим именам/корректировкам; missing никогда не становится success.
- Shared setup — selected common definitions/materials/presets. Cookies, сертификаты, личная конфигурация и browser profiles остаются локальными. Узкое разрешение на выбранные XLSX/PPTX описано в AGENTS/material manifest.
- При update сначала assertIdle/drain, затем canonical backup/quiesce/launcher/health/commitpoint. Не отменяйте пользовательскую работу для получения idle и не откатывайте принятые новые данные после commitpoint.

## Проверки

Для существенного бага сначала воспроизведите дефект, затем owning regression и сквозной путь. Настоящие HTTP/SQLite/Git/браузерные проверки важнее mock ответа успешного бизнес-API. Внешний банковский сервис можно заменить явно синтетическим адаптером, не заявляя реальную приёмку.

```text
npm test -- <затронутые файлы> --maxWorkers=2
npm run build
```

Один общий suite выполняется после стабилизации. После локального исправления повторяйте затронутые проверки; не переносите старые числа passed на новый SHA. После кода выполняется независимое ревью; P0/P1 должны быть закрыты. Документируйте scope, версии, exitcode, фактические артефакты и целевые ограничения.

## Поставка

`npm run export:clean` формирует исходный ZIP принятого commit. `scripts/package-prepared-linux.mjs` формирует отдельный Linux x64 комплект из чистой ревизии и закреплённых локально установленных зависимостей. Проверяйте извлечённый комплект, отсутствие private state, Git clean/origin/main и повторный запуск с сохранением файла. Пользовательский PDF содержит действующие снимки UI и явные границы банка/Office. Не публикуйте `.runtime`, логи, сертификаты или случайные файлы анализа.
