# Передача AI-PDLC и перенос в корпоративный контур

Версия 0.2 · 24 октября 2026 года

## 1. Что это за проект и с чего продолжать

«Рабочее место УОР ДИТ Operations» — локальное веб-приложение управления технологической повесткой. УОР — управление обеспечения развития. Аудитория: директор ДИТ, ИТ-лидеры кластеров, кураторы УОР и руководитель УОР.

Сначала прочитать:

1. `docs/superpowers/specs/2026-10-24-uor-dit-operations-design.md` — действующая продуктовая и архитектурная модель.
2. `docs/decisions/2026-10-24-requirements-update.md` — последние исправления замысла.
3. `docs/superpowers/plans/2026-10-24-local-data-and-dashboard.md` — исполнимый порядок первого этапа.
4. `docs/guides/curator-workflow.md` и `docs/guides/setup-and-run.md`.

На момент создания этого документа приложение не реализовано. После продолжения агент обязан сначала посмотреть фактическое дерево и историю репозитория и определить уже выполненные задачи. Не повторять готовую работу только потому, что чекбокс в плане не обновлён.

## 2. Что обязательно сохранить

- Локальный запуск из разрешённой директории через `npm run dev`; окружения устанавливаются по гайду.
- Отдельные команды обновления общих данных, всех источников, выбранного источника и всего состава.
- Проверка новой версии при запуске с уведомлением и семантической сводкой.
- Личные факты и доступы отделены от общих определений и намеренно опубликованных проверенных снимков.
- `release/current` накапливает изменения кураторов, руководитель выпускает merge в `main`.
- Автоматическое объединение независимых изменений без force push.
- Видимость стадии, времени стадии и всего действия, включая сохранение и публикацию.
- Директорский обзор обязательно по фамилиям ИТ-лидеров с раскрытием целей/участников.
- Положительный факт сначала ожидает подтверждения УОР. Подтверждение требует артефакт или комментарий и связано с точным набором данных/правил.
- Любое подтверждённое ухудшение автоматически возвращает невыполнение; отрицательные статусы не требуют согласования.
- При использовании чужого проверенного снимка видны куратор, дата, период и исходный способ получения.
- Реальный браузерный сбор в первом этапе остаётся заглушкой. Факт такой заглушки виден в UI и документах.

## 3. Настройки переноса

| Зона | Что сделать в банке | Как проверить |
|---|---|---|
| Репозиторий | Задать корпоративные URL, провайдер и разрешённые ветки | Чтение main; запись куратора в release/current; отказ читателю |
| Корень приложения | Указать разрешённые реальные директории для ОС | Старт внутри; понятный отказ вне; пути с пробелами/кириллицей |
| Среда | Предоставить закреплённые Node/npm/Git, затем Python для реального сборщика | Версии, npm ci из корпоративного registry, npm run dev |
| CA/прокси | Настроить штатные доверенные сертификаты и маршрутизацию | Git/npm/источники без отключения TLS-проверки |
| Идентификация | Развернуть локальный кодовый реестр либо заменить RoleService корпоративным входом | Роль не выдаёт Git-права; автор публикации проверяем |
| Данные | Локально импортировать рабочую карту целей и справочники | Исходные id и назначения сохранены, новые поля не придуманы |
| Лидеры/структура | Проверить соответствие продукт → команда → лидер и даты действия | Нет неясных/двойных соответствий в итогах |
| Методики | Подтвердить пороги, применимость, исключения, сроки и охват | Независимый контроль нескольких фактов и агрегатов |
| Снимки | Разрешить общую публикацию только допустимого содержимого | Нет личных доступов, профильных данных и запрещённых артефактов |
| Браузер | Позже реализовать адаптер корпоративного Сбербраузера/сертификата | Матрица ОС/CPU/версий, реальный вход/выгрузка/отказ |
| Доступы | Заполнить ссылки на оформление прав | Правильный объект доступа и действующая инструкция |
| Выпуск | Настроить main/release/current и merge commit | Повторный цикл выпуска без повторения старых изменений |
| Объёмы | Измерить рост локальной БД и Git | При больших артефактах подключить корпоративное хранилище через интерфейс |

Адрес GitHub не должен быть частью расчётного кода. Провайдер Git и базовый адрес задаются конфигурацией. Пример тестового URL в гайде не означает, что корпоративное приложение продолжает отправлять туда данные.

## 4. Реестр кураторов

Имена, устойчивые id и зоны ответственности — предметные настройки. Кодовые хеши и параметры проверки — локальная секретная конфигурация. Начальный персональный код заказчик передал в отдельном канале; не извлекать его из переписки в публичные примеры и не дублировать в инструкции.

Если банк требует более строгую идентификацию, заменить реализацию `RoleService`, сохранив контракт профиля и проверки публикации. UI-признак «куратор» не является достаточным доказательством персонального Git-доступа.

## 5. Наполнение по карте целей

Исходные корпоративные HTML/Excel/PPTX не входят в публичную поставку. Агент получает их в разрешённой папке и импортирует как данные. HTML не исполняется. Импорт сначала показывает состав и отличия, затем сохраняет черновик.

Владельцы, кураторы, внутренние значения, веса и приоритеты могут быть не заданы в исходнике. Их оставляют незаполненными и предоставляют редактор. Не назначать людей и пороги по догадке.

Сравнительный отчёт требует соответствующих снимков. Единственный текущий файл не является основанием для создания прошлой недели. Отдельные показатели, вынесенные в исходной презентации отдельно, не добавлять в базовую модель без изменения методики.

## 6. Разделение этапов

Первый этап: готовые данные → расчёты → подтверждения → визуализация и ручная настройка → общая публикация/получение. Следующий этап: реальный сбор по ранее определённому интерфейсу. Затем отчётность, шаблоны и остальные источники согласно приоритету заказчика.

Это ограничение начального объёма не отменяет будущих требований, но не допускает объявить интеграцию готовой по демонстрационному сценарию.

## 7. Что предъявить как доказательство работы

Реальный старт из разрешённой папки; визуальная демонстрация обзора директора/лидера/цели; последовательность положительного результата и кураторского подтверждения; автоматическое ухудшение; читатель с проверенным чужим снимком; две параллельные независимые правки и выпуск; панель времени операций; история обновлений.

Отдельно перечислить фактически проверенные ОС и сетевые интеграции. Локальный Git-тест не выдавать за корпоративную авторизацию, а работа UI на Windows не доказывает сертификатный сбор на macOS/СберОС.

## 8. Обновление документации

После реализации задачи отмечать результат и команды в плане, README и связанном гайде. Сохранять описание текущего состояния: что работает, что демонстрационное, что ещё не проверено. Новые уточнения заказчика отражать одновременно в мастерспеке и журнале решений.
