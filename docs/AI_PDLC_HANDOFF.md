# Передача AI-PDLC и перенос в корпоративный контур

Передача первого реализованного этапа · 24 октября 2026 года

## 1. Что это за проект и с чего продолжать

«Рабочее место УОР ДИТ Operations» — локальное веб-приложение управления технологической повесткой. УОР — управление обеспечения развития. Аудитория: директор ДИТ, ИТ-лидеры кластеров, кураторы УОР и руководитель УОР.

Сначала прочитать:

1. `docs/superpowers/specs/2026-10-24-uor-dit-operations-design.md` — действующая продуктовая и архитектурная модель.
2. `docs/decisions/2026-10-24-requirements-update.md` — последние исправления замысла.
3. `docs/superpowers/plans/2026-10-24-local-data-and-dashboard.md` — исполнимый порядок первого этапа.
4. `docs/guides/curator-workflow.md` и `docs/guides/setup-and-run.md`.
5. `docs/superpowers/plans/2026-10-24-overview-refinement.md` — текущее продолжение и упрощение обзора.
6. `docs/demo/first-stage-walkthrough.md` и `docs/verification/first-stage-evidence.md` — сценарий демонстрации и актуальные доказательства.
7. `docs/superpowers/plans/2026-10-24-maturity-import-and-history.md` и `docs/guides/maturity-import.md` — текущий адресный импорт XLSX и история.
8. `docs/remaining-work.md` — аудит всех незавершённых требований; не считать мастерспеку перечнем уже реализованных возможностей.

Первый этап приложения реализован: React/TypeScript, локальная Fastify-служба, SQLite в `.runtime`, каталоги и снимки, расчёт, подтверждение УОР, обзор по ИТ-лидерам, редактирование и Git-публикация. Реальный сбор из корпоративного браузера остаётся заглушкой. Сначала посмотрите фактическое дерево, тесты и [границы этапа](first-stage-validation.md); не повторяйте готовую работу только потому, что чекбокс исходного плана не обновлён.

Основные команды: `npm ci`, `npm run setup:curators`, `npm run import:map -- "путь/к/карте.html"`, `npm run dev`. Проверки разработки: `npm test`, `npm run build`. Отдельного установщика и иконки нет.

Текущий адресный этап добавляет UI-загрузку XLSX модели зрелости: файл → период и цель → распознавание/сопоставление → разница и расчёт → явное сохранение. До принятия preview текущие факты не меняются. Предпросмотр связан с куратором, сроком действия и версией основы; неизвестные команды и метрики не создают методику из данных. Парсер `src/features/importing/maturity-parser.ts` читает только данные XLSX и кэш результатов формул, без их исполнения. Объединённый этап проверен: 161 тест, сборка и локальный HTTP-предпросмотр рабочего файла; детали в журнале доказательств.

## 2. Что обязательно сохранить

- Локальный запуск из разрешённой директории через `npm run dev`; окружения устанавливаются по гайду.
- Отдельные команды обновления общих данных, всех источников, выбранного источника и всего состава.
- Проверка новой версии при запуске с уведомлением и семантической сводкой.
- Личные факты и доступы отделены от общих определений и намеренно опубликованных проверенных снимков.
- `release/current` накапливает изменения кураторов, руководитель выпускает merge в `main`.
- Автоматическое объединение независимых изменений без force push.
- Видимость стадии, времени стадии и всего действия, включая сохранение и публикацию.
- Директорский обзор обязательно по фамилиям ИТ-лидеров с раскрытием целей/участников.
- Положительный факт сначала ожидает подтверждения УОР. Подтверждение требует артефакт или комментарий и связано с точным набором данных/правил.
- Любое подтверждённое ухудшение автоматически возвращает невыполнение; отрицательные статусы не требуют согласования.
- При использовании чужого проверенного снимка видны куратор, дата, период и исходный способ получения.
- Реальный браузерный сбор в первом этапе остаётся заглушкой. Факт такой заглушки виден в UI и документах.
- Главная по умолчанию показывает весь активный портфель: распределение целей и общий статус, назначения по ИТ-лидерам и реестр. Любая цель выбирается отдельно, даже без фактов; проценты разных целей не усредняются. Подробная матрица и направления открываются отдельно; технические коды не заменяют полные названия.
- Направления — отдельный редактируемый справочник с шестью начальными значениями; исходные категории карты сохраняются. Неоднозначные привязки подтверждает куратор, общие итоги не удваивают назначения.
- Лидер продукта хранится отдельной связью с продуктом. Не заменять его владельцем цели или ИТ-лидером кластера.

## 3. Настройки переноса

| Зона | Что сделать в банке | Как проверить |
|---|---|---|
| Репозиторий | Задать корпоративные URL, провайдер и разрешённые ветки | Чтение main; запись куратора в release/current; отказ читателю |
| Корень приложения | Указать разрешённые реальные директории для ОС | Старт внутри; понятный отказ вне; пути с пробелами/кириллицей |
| Среда | Предоставить Node.js 22.20+ ветки 22.x либо 24+, npm/Git; затем Python при необходимости реального сборщика | Версии, npm ci из корпоративного registry, npm run dev |
| CA/прокси | Настроить штатные доверенные сертификаты и маршрутизацию | Git/npm/источники без отключения TLS-проверки |
| Идентификация | Настроить `.runtime/local-config/curators.json` через setup; согласовать устойчивые id на компьютерах либо заменить RoleService корпоративным входом | Роль не выдаёт Git-права; автор публикации проверяем |
| Данные | Локально импортировать рабочую карту целей и справочники | Исходные id и назначения сохранены, новые поля не придуманы |
| Лидеры/структура | Проверить соответствие продукт → команда → лидер и даты действия | Нет неясных/двойных соответствий в итогах |
| Методики | Подтвердить пороги, применимость, исключения, сроки и охват | Независимый контроль нескольких фактов и агрегатов |
| Направления | Проверить шесть начальных направлений и предварительные связи целей; дополнить через UI | Пустое направление и цель без привязки видимы; общий итог не удваивается |
| Снимки | Разрешить общую публикацию только допустимого содержимого | Нет личных доступов, профильных данных и запрещённых артефактов |
| Браузер | Позже реализовать адаптер корпоративного Сбербраузера/сертификата | Матрица ОС/CPU/версий, реальный вход/выгрузка/отказ |
| Доступы | Заполнить ссылки на оформление прав | Правильный объект доступа и действующая инструкция |
| Выпуск | Настроить main/release/current и merge commit | Повторный цикл выпуска без повторения старых изменений |
| Объёмы | Измерить рост локальной БД и Git | При больших артефактах подключить корпоративное хранилище через интерфейс |

Адрес GitHub не должен быть частью расчётного кода. Провайдер Git и базовый адрес задаются конфигурацией. Пример тестового URL в гайде не означает, что корпоративное приложение продолжает отправлять туда данные.

## 4. Реестр кураторов

Имена, устойчивые id и зоны ответственности — предметные настройки. Кодовые хеши и параметры проверки — локальная секретная конфигурация. Начальный персональный код заказчик передал в отдельном канале; не извлекать его из переписки в публичные примеры и не дублировать в инструкции.

Если банк требует более строгую идентификацию, заменить реализацию `RoleService`, сохранив контракт профиля и проверки публикации. UI-признак «куратор» не является достаточным доказательством персонального Git-доступа.

## 5. Наполнение по карте целей

Исходные корпоративные HTML/Excel/PPTX не входят в публичную поставку. В чистом клоне `catalog/demo.json` и `catalog/demo-snapshots.json` содержат только вымышленные данные. Рабочая карта импортируется из разрешённой локальной папки. HTML не исполняется: читается только JSON-блок `portal-data`. UI-импорт заменяет локальный активный каталог с резервной записью; консольный импорт пишет `.runtime/imports/catalog.json` и требует перезапуска. Отдельного предварительного экрана сравнения импортов пока нет.

Подготовленный для локальной демонстрации набор содержит полную карту из 30 целей и 8 ИТ-лидеров; обзор активных назначений исключает неактивные записи. Предоставленный Excel соответствует историческому срезу 02.10.2026 по сопоставлению с предыдущей колонкой презентации. В самом Excel дата актуальности не указана, поэтому `sourceUpdatedAt` оставлен `null`. Новые результаты из презентации 16.10.2026 не подставлялись в этот снимок. Метод сопоставления и ограничения сохранены в приватных метаданных снимка.

Все 59 команд локального снимка сопоставлены с ИТ-лидерами по слайдам предоставленной презентации. Два сокращённых имени разрешены по единственному совпадению начала строки с Excel. При переносе нужно заново подтвердить соответствия и их период действия; публичный демонстрационный набор эти привязки не содержит.

Владельцы, кураторы, внутренние значения, веса и приоритеты могут быть не заданы в исходнике. Их оставляют незаполненными и предоставляют редактор. Не назначать людей и пороги по догадке.

Сравнительный отчёт требует соответствующих снимков. Единственный текущий файл не является основанием для создания прошлой недели. Отдельные показатели, вынесенные в исходной презентации отдельно, не добавлять в базовую модель без изменения методики.

## 6. Разделение этапов

Первый этап: готовые данные → расчёты → подтверждения → визуализация и ручная настройка → общая публикация/получение. Следующий этап: реальный сбор по ранее определённому интерфейсу. Затем отчётность, шаблоны и остальные источники согласно приоритету заказчика.

Локальные факты принимаются через серверный слой, импорт карты доступен через UI и CLI. В текущем проходе подключается адресный UI-импорт XLSX модели зрелости; универсальный пользовательский импорт любых Excel не реализован. Локальное обновление источника проверяет уже загруженные факты, а не выполняет браузерный сценарий. Реальные сертификаты, Сбербраузер, Qlik/Confluence, recorder, расписания, презентации и недельные отчёты не заявляются готовыми.

История фактов должна читать снимки без вызова изменяющего текущие подтверждения расчётного пути. В новых снимках сохраняется `evaluationBasis`: методика цели и ожидаемые назначения на момент принятия. Старые снимки без такой основы явно считаются историческими с неизвестными правилами. Разные источники, пороги, составы или несовместимая основа разрывают сравнимый тренд. Повтор одинаковых фактов одного периода не создаёт редакцию, исправление сохраняет предшествующий снимок.

Правки кода этого тестового этапа заказчик разрешил отправлять непосредственно в `main`. Для содержания приложения сохраняется `release/current` → merge руководителем → `main`.

Это ограничение начального объёма не отменяет будущих требований, но не допускает объявить интеграцию готовой по демонстрационному сценарию.

## 7. Что предъявить как доказательство работы

Реальный старт из разрешённой папки; визуальная демонстрация обзора директора/лидера/цели; последовательность положительного результата и кураторского подтверждения; автоматическое ухудшение; читатель с проверенным чужим снимком; две параллельные независимые правки и выпуск; панель времени операций; история обновлений.

Отдельно перечислить фактически проверенные ОС и сетевые интеграции. Локальный Git-тест не выдавать за корпоративную авторизацию, а работа UI на Windows не доказывает сертификатный сбор на macOS/СберОС.

Текущий испытанный локальный контур — Windows с Node.js 24.19. Проверки macOS/СберОС и корпоративной сети ещё предстоят. Окончательные результаты текущей ревизии фиксируйте после завершения проверки, не переносите число тестов от предыдущей ревизии автоматически.

Отметка 130 тестов в 20 файлах относится к предыдущему этапу. Свежая проверка импорта XLSX и истории: 161/161 тестов в 26 файлах, TypeScript/Vite build успешен, HTTP-предпросмотр предоставленного файла распознал дубликат без изменения снимков. Это не проверка корпоративной выгрузки и не визуальная приёмка: CUA недоступен.

Интерфейс использует публичную тему SDDS Service Malachite (`@salutejs/sdds-themes`), а не утверждение о соответствии внутреннему банковскому стандарту. Согласованный знак находится в `public/brand/rm-uor.png`: DO и подпись «РМ УОР», без правой надписи «ДИТ». Историю решения и исходный промпт см. в `docs/decisions/2026-10-24-interface.md`.
