# Работа кураторов и выпуск общей версии

Это целевой порядок приложения по мастерспеке v0.2. Пока продукт не реализован, кнопки и автоматизация ниже являются требованиями.

## Читатель

При входе выбирает «Не куратор». Видит цели, факты, источники, прогресс, подтверждения и комментарии. Может обновить данные УОР, личные источники или всё. Проверенные данные других кураторов помечены именем и датой. Право чтения общего репозитория не равно доступу к дашборду.

## Куратор

1. Выбирает кураторский вход и вводит индивидуальный код.
2. Открывает свою цель, назначение, источник или статью.
3. Меняет содержимое; локальный черновик сохраняется автоматически.
4. Нажимает «Сохранить и отправить».
5. Видит стадии: проверка → получение общей релизной версии → объединение → отправка.
6. Получает результат «Отправлено в готовящийся выпуск» или конкретную ошибку. «Сохранено локально» не означает, что коллеги получили изменение.

Индивидуальный код включает профиль. Git-доступ с правом записи настраивается отдельно и требуется для успешной отправки.

## Проверка снимка

После получения фактов проверяются период, источник, охват, особые состояния и визуализация. Куратор нажимает «Проверил данные и расчёт — отправить». В набор входят выбранные нормализованные данные и метаданные, а артефакты выбираются отдельно.

Красный результат тоже может быть корректным проверенным снимком. Его публикация не требует подтверждения выполнения.

Если расчёт положительный, текущая надпись — «Выполнено, ожидает подтверждения УОР». Куратор прикладывает артефакт либо пишет содержательный комментарий и подтверждает результат. Дата и оценка закрепляются в истории.

Если позже данные становятся отрицательными, статус меняется автоматически. Старое подтверждение остаётся историческим. Новый положительный период или существенное изменение требует новой проверки; идентичный повтор выгрузки — нет.

## Несколько кураторов

Общая ветка — `release/current`. Изменения разных целей автоматически объединяются, потому что хранятся отдельными объектами. Клиент получает актуальную вершину перед отправкой и повторяет обычную отправку при гонке. Принудительная перезапись истории не используется.

Если два человека всё же изменили одно и то же поле по-разному, приложение сохраняет обе правки и показывает различия. Куратор не должен чинить Git в терминале. Для штатной работы каждый ведёт свою область ответственности.

## Руководитель УОР

В Git UI открывает сравнение `release/current` с `main`, просматривает состав и нажимает merge с сохранением коммитов. После этого версия опубликована. При использовании постоянной релизной ветки не заменять этот порядок squash/rebase без изменения алгоритма синхронизации.

Слияние выпуска и предметное подтверждение выполнения — разные действия. Факт одобрения цели относится к конкретной оценке и ответственному куратору.

## Когда коллеги увидят изменения

До выпуска изменения видны кураторам в режиме готовящейся версии. После слияния в main приложение читателя уведомляет о новой версии. Команда «Обновить данные УОР» получает её, а «Обновить всё» получает её и затем запускает собственный сбор.

Общие комментарии не доставляются мгновенно между компьютерами; рядом видна последняя успешная синхронизация.

## Если отправка не удалась

Черновик остаётся локально. В операции видны причина, этап и время. При восстановлении доступа можно повторить отправку. Нельзя удалять `.runtime` ради устранения ошибки, пока там есть неотправленные изменения или нужная локальная история.
