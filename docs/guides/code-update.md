# Обновление программы с подготовкой и восстановлением

Штатный запуск — `npm run dev` из разрешённой папки. Любой вошедший пользователь может обновить свою программу с правами чтения Git; публикация целей и правки репозитория остаются кураторскими. Обновление не делает push.

## Как проходит обновление

1. Интерфейс получает текущий и опубликованный commit. Проверяются точный origin, чистые отслеживаемые файлы, разрешённая ветка и возможность перехода только вперёд. POST принимает ожидаемые текущую/целевую ревизии; повторная или устаревшая заявка отклоняется.
2. Launcher создаёт отдельную приватную транзакцию `.runtime/code-update/transactions/<UUID>`. В неё извлекается точный целевой commit и устанавливаются зависимости по его package-lock.json. **Рабочий код, node_modules и работающий API в это время не меняются.** При отказе registry/установки программа продолжает работу в прежней версии.
3. Новый код должен содержать `config/update-protocol.json` с `{schemaVersion:1,bootstrap:1}`. Версия без этого контракта отклоняется до остановки приложения. Отслеживаемые `.runtime`, node_modules, site.local.json и локальные .env в целевом Git запрещены.
4. После успешной подготовки launcher снова проверяет ревизии и через приватный IPC просит действующий API завершить рабочие действия. API принимает команду только от своего родительского launcher с текущим приватным токеном. Короткий активный запрос можно дождаться; выполняющаяся рабочая операция или обслуживание дают явный отказ без замены кода.
5. API устанавливает maintenance и делает согласованную SQLite-копию. Затем штатно закрываются его задачи, браузеры и БД; завершается Vite. Git получает проверенный commit через `merge --ff-only`, а готовые зависимости подставляются переименованием папок. Прежние зависимости сохраняются в транзакции.
6. Новая версия запускается с внутренним `UOR_UPDATE_BOOTSTRAP=1`. Её API и расписание остаются заблокированными. Launcher проверяет реальный запуск API через IPC и доступность клиента; обычный успешный HTTP-ответ не заменяет подтверждение закрытого режима.
7. Только после проверки в журнал записывается устойчивый commitpoint. Затем приватная IPC-команда открывает API. До этого момента пользовательские правки/сбор не принимаются, поэтому неудачный запуск можно вернуть к прежней базе без потери новых фактов.

## Что происходит при отказе

- **Подготовка или установка зависимостей:** текущие службы продолжают работать, рабочий checkout и зависимости сохранены.
- **Отказ запуска до commitpoint:** новая версия закрывается; при неизменённом собственном checkout возвращаются прежние код, зависимости и SQLite-копия. Службы прежней версии запускаются автоматически. Сессии и браузерные профили не публикуются, локальный реестр кураторов остаётся на месте.
- **Потеря подтверждения активации после commitpoint:** возврат старой базы уже запрещён. Launcher один раз повторно запускает сохранённую новую версию, сохраняя принятые данные. Если её готовность не подтверждена, остаются журнал и явное сообщение для сопровождения.
- **Прерывание launcher/питания:** следующий запуск проверяет приватный журнал. Незавершённая собственная замена возвращается к прежней версии; подтверждённая версия сохраняется. После потери родителя API/Vite завершаются, чтобы старые процессы не удерживали порты.
- **Чужие локальные правки или сменившийся HEAD:** автоматическое восстановление останавливается. Правки и прежние файлы сохраняются; reset/force/clean с потерей работы не используются.

Возврат к старому коду использует `git switch --detach <предыдущий commit>` только после проверки чистоты и точного собственного HEAD. Это не переписывает удалённую историю и не удаляет ветки. Программа продолжает работать из той же разрешённой папки; повторное обновление допускает ff-only из сохранённого commit. Перед последующей разработкой сопровождающий проверяет состояние ветки: ветка main может всё ещё указывать на проверявшуюся новую версию.

## Зависимости, сеть и файлы

npm CLI берётся из `npm_execpath` штатного запуска либо `npmCliPath` локальной конфигурации. Установка идёт в подготовительной папке. При наличии локального root `.npmrc` он используется как userconfig по ссылке; значения секретов не копируются в общий каталог. Проверяются эффективные registry и strict-ssl=true. Registry требует HTTPS; HTTP разрешён только localhost для стенда. CA/прокси настраиваются штатно, TLS не отключается.

Транзакционные папки, предыдущие node_modules, согласованная копия базы и журнал приватны. Их нельзя удалять общим сборщиком временных файлов, пока транзакция активна или может понадобиться восстановление. Новые исходники и npm-скрипты должны происходить из доверенного согласованного репозитория/registry.

SQLite-возврат проверяет размер, SHA-256 и целостность собственной копии; новые app.db/WAL/SHM сохраняются отдельно перед заменой. Профили браузера, сертификаты и учётные записи не переносятся и не очищаются. Миграция новой версии не должна до commitpoint разрушительно изменять внешние исходники/артефакты; такие изменения требуют отдельной транзакционной миграции файлов. Это проверенный механизм для текущего приложения, не универсальный установщик произвольного ПО.

## Проверка при переносе в банк

Пройти подготовку с доступным и недоступным registry, отказом CA, изменением remote между preview/prepare/apply, занятым рабочим действием и неудачным запуском. Подтвердить блокировку API/расписания кандидата до активации, возврат старых фактов при раннем отказе и сохранение новых фактов после commitpoint. Проверить Windows/macOS/СберОС, переименование node_modules при антивирусе/файловых блокировках и восстановление после прерывания. Локальные стенды не доказывают банковскую сеть или все ОС.
