# Установка с нуля и перенос в банк

## Что переносить

Для новой установки нужен **чистый кодовый ZIP**. Он содержит приложение, тесты, шаблоны настроек и действующие инструкции. Он не содержит старой Git-истории, личной базы, событий разработки, текущих корпоративных данных, зависимостей или паролей.

Отдельные вещи не смешиваются:

| Пакет | Назначение | Кто получает |
|---|---|---|
| Чистый кодовый ZIP | Начать с пустого рабочего места | Пользователи/внутренний репозиторий |
| `*.private-local-accounts.zip` | Сохранить нынешние ID и пароли кураторов через локальный хеш-реестр | Только уполномоченный сопровождающий |
| Переносимый ZIP из «Обслуживания» | Намеренно перенести существующие цели, факты и выбранные файлы | По решению владельца рабочих данных |
| Git bundle / архивная ветка | Сохранить прежнюю историю разработки отдельно | Владелец проекта; для запуска не нужны |

## Подготовка пакета на исходном компьютере

На сохранённом чистом commit выполните:

```text
npm run export:clean -- --output .runtime/exports/RM_UOR-clean.zip --with-local-accounts
```

Если существующие аккаунты переносить не нужно, уберите последний флаг. Кодовый ZIP всё равно не содержит секретов. Приватный архив аккаунтов создаётся **отдельно**, рядом. Не прикладывайте его к публичному репозиторию и не кладите в общий доступ. Если выходной файл уже существует, выберите новое имя: команда его не перезаписывает.

Экспорт берёт сохранённую версию из Git; незакоммиченные программные изменения надо сначала завершить. Манифест внутри пакета содержит версию, commit и хеши файлов. Непроверяемые или запрещённые файлы не становятся частью поставки.

## Новая установка: последовательность

1. Выберите папку, разрешённую банком. Распакуйте **только кодовый ZIP**. Не копируйте старую `.runtime` или `node_modules`.
2. Проверьте наличие Node.js22.20+ветки22.x либо24+, npm,Git и разрешённого браузера. Python не требуется.
3. Если нужен внутренний npm registry/CA/прокси, настройте их до установки. Не отключайте проверку TLS. Доверие Node,Git и браузера настраивается отдельно по правилам банка.
4. Откройте консоль в корне распакованной папки и выполните:

```text
npm ci
npm run setup:workspace -- --mode empty
```

5. Настройте аккаунты одним из способов ниже.
6. Запустите `npm run dev`. Откроется приложение. В режиме empty цели/факты/сводки и история будут пустыми. Повторный запуск сохраняет работу.

Если внутренний репозиторий уже создан, на шаге4 вместо короткой настройки используйте:

```text
npm run setup:workspace -- --mode empty --repository "<URL внутреннего репозитория>" --publication internal
```

Не выполняйте обе команды подготовки подряд: подготовка откажется затирать существующую установку. Для знакомства на отдельной новой папке доступен `--mode demo`; это явный выбор вымышленных данных.

## Пароли: оставить существующие или задать свои

**Сохранить существующие:** распакуйте отдельный приватный архив аккаунтов по его README. Файл должен оказаться в `.runtime/local-config/curators.json`. Сохраните ID без изменения: к ним привязаны личные материалы. Пароли останутся прежними, их значения не нужно восстанавливать из хешей. Перезапустите приложение.

**Задать/изменить:** подготовка создала `.runtime/local-config/curators.input.json` из публичного `config/curators.example.json`. Откройте этот локальный файл. В каждой записи `name` — имя, `code` — пароль. Замените пример собственными значениями. Затем:

```text
npm run setup:curators:file -- --file .runtime/local-config/curators.input.json
```

Пароли записываются в реестр как salted hashes и не выводятся в консоль. Повторное применение того же имени сохраняет его ID. Пустое поле пароля в списке означает «не менять эту учётную запись»; если заполненных записей нет, команда ничего не применяет. Публичный пароль-заполнитель применять нельзя. Исходный локальный файл содержит введённые вами значения, поэтому храните его как секрет; Git его исключает. Интерактивная альтернатива без файла: `npm run setup:curators`.

Вход обычного пользователя не требует пароля. Вход куратора — выбор имени и свой пароль. Локальная роль не выдаёт доступ к Git/источникам. Для промышленного SSO меняется адаптер идентификации, предметные расчёты не переписываются.

## Создать внутренний Git с новой историей

В чистом ZIP нет `.git`. Для нового пустого внутреннего репозитория сопровождающий выполняет:

```text
git init -b main
git add .
git commit -m "Initial corporate baseline"
git remote add origin "<URL внутреннего репозитория>"
git push -u origin main
git branch release/current
git push -u origin release/current
```

Если репозиторий уже содержит работу, используйте принятый процесс интеграции — эти команды не являются разрешением её перезаписывать. Дальше укажите URL/ветки и разрешённые пути в `config/site.local.json`, настройте реальную Git-аутентификацию. Учётные записи/ключи не коммитятся. У кураторов должны быть права подготовки `release/current`, у руководителя — выпуска в main, у читателей — чтения.

## Первое наполнение и проверка

Пройдите [руководство пользователя](../USER_GUIDE.md): добавить лидера → создать цель → показатели/участники/источник → пробный расчёт → принять факты → подтвердить положительный результат → подготовить выпуск → получить его на другой станции. Заполните недельную сводку и проверьте, что до публикации директор её не видит, а после выпуска и обновления видит.

Для презентаций загрузите собственный PPTX в «Отчётах», сохраните индивидуальный профиль и сформируйте снимок. Шаблон зрелости имеет готовый специализированный профиль; произвольная презентация настраивается поддержанными привязками. Исходный рабочий PPTX пользователя не включён в чистую публичную поставку.

Настройку реальных Qlik/Confluence/браузера/сертификатов выполняйте по [банковскому runbook](../BANK_CONNECTORS_RUNBOOK.md). Затем проверьте фактическуюСберОС/macOS, браузер и PowerPoint. Локальные тесты не подтверждают эти условия.

## Очистить только местный журнал

Закройте приложение через Ctrl+C и выполните `npm run history:archive`. Команда сначала сохраняет и проверяет полную SQLite-копию и отдельный приватный архив, затем очищает только события изменений, операции и кэш уведомлений. Цели, факты, черновики, подтверждения, отчёты и пароли сохраняются. Старые ID событий запоминаются, чтобы они не появились снова при запуске. При неудачной копии журнал не очищается.

Это не команда сброса всех рабочих данных. Для новой пустой установки используйте чистый пакет в отдельной папке. Старую историю разработки можно найти в [архиве](../ARCHIVE.md).
