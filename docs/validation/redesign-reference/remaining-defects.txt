F03 — ОТКРЫТО: исторический package preview пересчитывается на текущих входах.
Риск высокий для достоверности/доступности публикации. package-projection.ts:210–220 снова вызывает resolveEvaluationInput с context.clock/context.actor (:213), после чего сравнивает digest и результат. Сам resolver берёт clock.now() и текущие goal/source/template heads (src/features/evaluation/workbench/resolve-input.ts:10–38). После порога свежести старый результат способен дать RESULT_MISMATCH; новый подходящий факт/новая версия определения способны дать BASIS_MISMATCH. Само движение времени не обязательно меняет digest: canonicalBasis не включает timestamp, но результат включает freshness/canConfirm.
Владелец: src/features/publishing/workbench/package-projection.ts; общий helper с src/features/publishing/workbench/publication-apply.ts. Уже правильно: apply, :120–152, собирает exact refs/factRefs и basis.evaluatedAt/basis.actor, отвергает неизвестное историческое время; preview :100–120 сохраняет исторические refs при remap. Переиспользовать этот контракт, не создавать второй алгоритм и не переписывать сохранённые результаты. Текущую свежесть (:197–208) показывать отдельно.
Минимальная регрессия: в package-preview.test.ts сохранить basis/result при T0, перейти через freshness threshold и добавить новый F2/новую definition; историческая проверка сохраняет исходные refs/байты/результат, отдельная текущая оценка отражает изменения. Отсутствующее evaluatedAt даёт явную ошибку, не подстановку now().

F04 — ОТКРЫТО: общий набор кандидатов не ограничен trusted ownership.
Риск высокий для изоляции результата между локальными владельцами; утечка содержимого UI отдельно не доказана. package-projection.ts:185–195 включает repository.readEvaluationCandidates без owner-фильтра, а :205/:213 передаёт accepts:()=>true. Repository выбирает подходящие facts/captures из общей локальной базы (src/server/storage/workbench-repository.ts:401–425). Поэтому чужой private fact может участвовать в выборе/неоднозначности собственного preview.
Уже правильно: closure read в package-projection.ts:125–130 принимает public либо isOwnCoreVersion с installation/person; это правило надо последовательно применить и к кандидатам/их зависимости. Не фильтровать только по actor, который сам по себе не trusted binding.
Минимальная регрессия: два владельца с совпадающими source/metric/scope/time; добавление чужого private fact/capture не меняет свой preview. Подтверждённые общие и разрешённые собственные доступны; отсутствие/несовпадение trusted binding закрывает доступ. Проверять также lineage inputs.

F01 — ЧАСТИЧНО: локальная защита есть, контракт точного будущего remote-кандидата не вынесен до внешнего принятия.
Риск высокий при подключении реального merge-процесса. package-projection.ts:167–181 проверяет combined graph; package-preview.ts:58–104 связывает preview с main и повторно проверяет его; pre-transfer-gate.ts:17–23 повторяет проверки перед отправкой. publication-apply.ts:75–165,226,251–256 проверяет полный принятый граф до локального commit. Это существенные существующие защиты.
Однако validateIncoming остаётся локальной функцией reader apply; BitbucketPort (bitbucket-port.ts:10–19) содержит PR/evidence, но не подтверждённый enforcement точного merge tree. Два независимо допустимых proposal могут конфликтовать предметно после первого внешнего merge; reader лишь остановит применение уже плохого main. Наличие такого merge в банке этой проверкой не установлено; production unavailable port корректно сообщает BITBUCKET_NOT_READY.
Владелец — publishing validation/apply + Git/Bitbucket contract. Выделить общий чистый validator полного точного candidate tree с привязкой repository, source/target OID и digest; повторная проверка при движении target. Финальный merge остаётся внешним. Возможность обязательного Bitbucket gate подтверждать отдельно, не локальным флагом.
Минимальная регрессия: две отдельные capsule с Git-clean, но предметно конфликтующей одной entity revision/ссылкой; полный будущий кандидат отвергается до acceptance, независимые изменения проходят. Изменение target после проверки аннулирует доказательство; unsupported enforcement отображается честно.
