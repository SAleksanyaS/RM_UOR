3. ЕЖЕДНЕВНЫЙ И ПЕРВОНАЧАЛЬНЫЙ ПУТИ

Ежедневно: выбрать сохранённый workflow → «Получить данные» → при истёкшем входе job.nextAction «Войти в ОКО» → после ручного входа «Вход выполнен — продолжить»/job.retry → результат, замечания, исходный/обогащённый файл. «Настроить» — второстепенное действие. Старый успешный результат остаётся доступным во время нового запуска и при отказе; обозначить его временем последнего получения.

Настройка: адрес/свой browser profile → ручной вход без записи секретов → выбрать однозначный marker → записать действия до полного скачивания → автоматически получить steps и sample → явно подтвердить значения фильтров → сопоставить ключ/числа/дату/единицу → загрузить и сопоставить справочник → сохранить → пробный настоящий replay. Само создание workflow не означает получение файла.

Ограничение действующего сервиса: личный record.test требует uor.prepare, то есть curator/chief; viewer может читать свой результат, работать с личным профилем/входом, но не создавать/перезаписывать личный recipe и не выполнять этот replay. Общий source.capture — другой контракт. Не расширять права ради кнопки в эталоне.

4. ЧЕСТНЫЕ ДАННЫЕ И СОСТОЯНИЯ

workbench-workflow-contracts.ts задаёт OkoWorkflowView:
• workflowId/sourceId/revision/title/reportUrl; marker; parsingProfile;
• profile.configured и sessionState closed/open/authentication_required/authenticated;
• recording.state idle/recording/completed/failed/interrupted, recordingId, steps, parameterNames, problem;
• columns/sampleRows, parameters, mapping;
• dictionary.columns/sampleRows/mapping/origin none|local-preview|published/issues;
• result|null: resultId, rowCount, unresolvedRows, issues, previewRows, originalDownload, enrichedDownload, capturedAt, sourceDate;
• warnings. SampleRows и previewRows ограничены 50 строками; rowCount относится ко всему обработанному файлу, не только видимому preview.

ВАЖНО: unresolvedRows — не только отсутствие продукта в справочнике. enrichment.ts:49–79 включает ошибки нормализации/чисел/дат, проблемный directory graph и null scope. Надпись «Строк требуют проверки» точнее текущего «требуют сопоставления». rowCount−unresolvedRows можно назвать «Строк без выявленных замечаний», но нельзя «Принято»: официальный fact acceptance в личном пути не выполняется. Отдельных accepted/rejected counters нет. Число issues — число диагностик, не количество строк. Нельзя выводить принятые/отклонённые из длины issues.

Источник даты: sourceDate становится датой только если строки имеют одну известную дату; иначе null. capturedAt — момент получения, не дата источника. Derived поля включают product/cluster/dit/leader/team names/IDs, number.*, unitCode/sourceDate; исходные колонки сохранены. При совпадении имён используется derived. Превью нужно делить на «Обогащённые», «Исходные», «Замечания», не переименовывать оригиналы.

JobSnapshot даёт status, stage, progress, warnings/error, cancelAvailable, retryAvailable, nextAction. Для текущего personal service отдельные гарантированные стадии parse/enrich не публикуются: service.test выполняет replay → parse → normalize/enrich → serialize → atomic save последовательно (:249–280), но jobs явно выставляются лишь для auth/recovery. Для эталона честное running «Получаем и проверяем файл»; «разбор/обогащение» как отдельный progress потребуют будущего backend instrumentation. Не придумывать проценты и не показывать raw completed/steps на основном экране.

Неизвестный исход — OkoClientError.uncertain и сохранённый commandId/reconciliation, не просто красный toast. completed recording ≠ успешный result. Готовый результат с issues — показывать как «Получено, есть замечания», даже если job.status=succeeded. Смена mapping/dictionary не перерабатывает старые bytes автоматически: новый result появляется только после replay. Для постоянного «результат устарел относительно рецепта» сейчас нет отдельного result.recipeRevision, поэтому не выдумывать устойчивый серверный флаг.

Предпочтительно использовать действующую production composition в отдельном собственном runtimeRoot, локальный loopback report и реальный Chromium. Ни endpoint success, ни SQL result не подменять. Уже есть подходящие helpers:

Минимальная последовательность HTTP и реального браузера:

Для заявленного визуального эталона на действующем runtime предпочтительна последовательность выше; не внедрять mock API или новый production bypass.

7. ПОСЛЕДУЮЩЕЕ УЗКОЕ РАЗРЕШЕНИЕ: ВОСПРОИЗВОДИМЫЙ ЛИЧНЫЙ РЕЗУЛЬТАТ

После завершения read-only разбора root отдельно разрешил ровно один test utility: scripts/design-reference/personal-fixture.ts. App/provider/core и зависимости этим агентом не менялись. Экспорт createPersonalReferenceEnvironment(executablePath) возвращает {providers, prepare({runtime,request}), close}; providers заменяет только внешний launcher настоящим headless Chromium с сохранением production launch/network/download options. prepare допускает только отдельный local-preview runtime, устанавливает curator через разрешённую команду, делает настоящие marker click → recording download → mapping/dictionary upload → replay → persistent result и проверяет оба HTTP download. Показателем успеха служит сохранённое состояние и bytes/hash, не 202 Accepted.

Проверено 2026-11-01 одним узким запуском createLocalRuntime + fixture.prepare на Node 22.16.0 и Chrome 156.0.8078.79; exit 0. Первый обычный sandbox отказал listen(127.0.0.1) с EPERM до выполнения сценария; тот же локальный запуск с разрешённой escalation прошёл. Фактические доказательства: 3 native browser launches, 2 HTTP скачивания отчёта (record/replay), rowCount=8, unresolvedRows=1, sourceDate=2026-10-30. Original oko-operations-2026-10-30.csv: 565 bytes, SHA256 9cb5a16423c80914a039d30b1f487d6ec370251a9c744abb38303fe0fd41aea2. Enriched oko-enriched.csv: 4538 bytes, SHA256 860a864d1fae1e081df8ae802838b95f82063982c7d4d2d6f78e31ead7a7a908 (derived IDs нового запуска могут менять hash). Исходные bytes совпали побайтно; enriched содержит вычисленные имена/точное число, одна строка относится к продукту без записи в личном справочнике. Временный runtime закрыт и очищен штатным helper. Отдельный focused tsc --noEmit с entrypoint personal-fixture.ts также exit 0, без диагностики; suite/build не запускались.
