# ОКО: личный сценарий сохраняет только сырой файл

Дата: 2026-11-01. Основа: рабочая копия `RM_UOR-main` (личные выгрузки ОКО, `oko.workflow.*` / `source.browser.*`).

## Симптом

Скачанный из ОКО отчёт терялся, если после скачивания что-то шло не так: `RECORDING_FAILED` («Запись или выгрузка не завершена»), `DIRECTORY_UUID_REQUIRED`, `SOURCE_SCHEMA_CHANGED`, `INVALID_TABLE`. Файл уже был получен браузером, но в списке не появлялся, потому что сохранялся только вместе с обогащённым результатом — то есть требовал сопоставления столбцов и справочника. Пользователю приходилось записывать сценарий заново.

## Что решено

Личный сценарий теперь **сохраняет сырой файл отчёта** (CSV/XLSX как есть) сразу после скачивания и показывает его в отдельном списке «Мои выгрузки» с подтверждением «Файл сохранён». Сопоставление столбцов и справочник — необязательны и не блокируют сохранение. Обогащение — отдельная будущая задача.

## Имя файла

`ОКО_<название отчёта>_<YYYY-MM-DD_HH-mm>.<csv|xlsx>`

* Название очищается от запрещённых в именах символов и обрезается до 60 символов (пустое → `Отчёт`).
* Время — момент сохранения (UTC в имени, отображается в МСК).
* Расширение исходного файла сохраняется: `.xlsx` остаётся `.xlsx`, всё остальное — `.csv`.

## Кнопка «Скрыть»

Это мягкое удаление: строка исчезает из списка, байты остаются в базе (`deleted_at`), файл по-прежнему можно получить и позже использовать для обогащения. Счётчик `hiddenCount` и подпись «Файлы не удалены и остаются на компьютере» показывают это явно.

## Что НЕ изменилось

* **Sandbox не ослаблен:** `chromiumSandbox: true`, `--no-sandbox` не добавляется, `serviceWorkers: 'block'`, `ignoreHTTPSErrors: false`, список `allowedOrigins` и проверка URL — прежние.
* Файлы остаются личными: ключ владельца `installationId/personId`, в общий каталог и публикации не попадают (`exportWorkspaceCore()` в тестах остаётся пустым).
* Старые результаты не переносятся в список: «Мои выгрузки» начинается с первой выгрузки после обновления.

## Как читать трассу записи (`[record] …`)

Каждый шаг пишется в `.runtime/logs/<время>-dev.log`. Отключить: `UOR_RECORD_TRACE=0`.

| Строка | Значение |
| --- | --- |
| `downloads-dir` | Папка, куда движок пишет выгрузку этого окна (уникальна для каждой записи) |
| `window-opened` | Окно записи открылось, адрес и выбранный маркер |
| `step` | Записан шаг: номер, действие (`click`/`fill`/`select`), locator |
| `event` | Отчёт отдал файл; имя, которое назначил отчёт (например `4e7091ae-….xlsx`), и его расширение |
| `disk-file` | В папке появился файл движка (`<guid>.crdownload` или `<guid>.<ext>`), размер и его стабильность |
| `file-ready` | Байты получены: `via:"disk"` — файл с диска, `via:"copy"` — через `saveAs` |
| `file-read` → `close-called` | Файл проверен по формату, окно закрывается уже после него |
| `copy` / `copy-failed` | Дополнительная попытка `saveAs` (нужен живой коннект); после закрытия окна всегда «has been closed» |
| `empty-artifact` | Отчёт сформировал пустой файл — ждать больше нечего |
| `no-file` | Движок сообщил об ошибке до появления файла |
| `waiting-file` | Раз в 50 опросов: файла ещё нет, окно остаётся открытым |
| `window-closed` | Окно закрылось; `completed:true` — после файла, `false` — файла ещё не было |
| `window-closed-artifact` / `window-closed-with-file` | Окно закрылось само, но файл уже лёг на диск — запись считается успешной |
| `close-called` | Окно закрывает наше приложение; в `from` видно место вызова |
| `signal-abort` | Запись отменена явно (кнопка отмены) |

**Диагноз по трассе реального случая** (`event` → сразу `window-closed` → 150× `copy-failed: has been closed` → `no-file`): отчёт закрывает свою вкладку сразу после выгрузки, и с этого момента **любой** вызов протокола Playwright (`path()`, `saveAs()`) падает навсегда — при этом файл уже полностью лежит в папке загрузок под именем движка. Живая проверка на OKO подтвердила: в `browser-downloads/<uuid>/` появляется `<guid>.crdownload` размером с полноценный XLSX (10 записей ZIP, корректный EOCD), и он не переименовывается в `<guid>`, потому что переименование делает закрытый коннект.

**Почему `.crdownload` — это не недокачанный файл.** Chromium при `Browser.setDownloadBehavior({behavior:'allowAndName'})` сначала пишет `<guid>.crdownload` и переименовывает в `<guid>` только после завершения. Если страница исчезла, переименовывать уже некому, но байты на диске полные. Поэтому готовность определяется не расширением, а двумя признаками: размер перестал меняться (`UOR_DOWNLOAD_SETTLE_MS`, по умолчанию 750 мс) и содержимое прошло проверку формата (для XLSX — целая ZIP-структура с концом центрального каталога).

## Принцип: окно закрывается только после того, как файл полностью лёг на диск

Раньше запись полагалась на статус загрузки (`file.failure()`, `timeoutMs`) и закрывала окно по таймеру. Из-за этого файл терялся: отчёт сам закрывает вкладку на выгрузке, а Playwright сообщает `Target page, context or browser has been closed` или `Браузер не сохранил файл выгрузки`, хотя файл дописывался.

Теперь (`completedBrowserDownload`):

* **Никаких таймаутов.** Ожидание файла не ограничено `timeoutMs`, 15-минутный лимит записи убран, страховочные `guard`-таймеры убраны. Прервать ожидание может только явная отмена записи.
* **Файл берётся из файловой системы, а не через протокол.** `completedBrowserDownload` читает папку `browser-downloads/<uuid>` (`readdir` + `readFile`), которую движок получил при запуске окна. Это работает и после того, как отчёт закрыл свою страницу. `saveAs` остался дополнительной попыткой — он нужен, только если файл с диска исчез, и требует живого коннекта.
* **Наличие файла решает всё.** Файл считается полноценным, когда его размер перестал расти (`UOR_DOWNLOAD_SETTLE_MS`) и формат проверен. Растущий или недописанный архив не принимается за готовый.
* **Статус движка — только подсказка.** `failure()` запоминается, но не прерывает ожидание. Ошибка отчёта поднимается только если файл так и не появился.
* **Окно не трогается до конца.** Убраны `recordingReady` и `page.evaluate` из обработчика `download`: любое обращение к закрывающейся странице давало «has been closed». Браузер закрывается только после чтения и сохранения файла.
* **Папка загрузок не удаляется при записи.** Обработчик `context.once('close')` в `openBrowser` чистит папку только для повтора сценария; во время записи он пропускается — иначе файл исчезает ровно в тот момент, когда его нужно прочитать.
* **Диагностика.** Каждый шаг пишется в лог с префиксом `[record]`. Отключить: `UOR_RECORD_TRACE=0`.

## Прерывание записи: `incomplete: Браузер не завершил выгрузку: Target page, context or browser has been closed`

**Симптом.** После `cancelled` появилась следующая ошибка: файл скачивается, но окно уже закрыто, и Playwright не даёт забрать его.

**Причина.** Порядок был неверен. Сначала опрашивался статус загрузки (`file.failure()`), потом читался файл, и только затем окно закрывалось. Но отчёт на кнопке выгрузки часто сам закрывает вкладку, а Playwright считает такую загрузку прерванной. Любое обращение к странице/контексту после этого даёт `Target page, context or browser has been closed`.

**Что сделано — принцип «сначала файл, потом окно»:**

1. Событие `download` больше не трогает страницу: убраны `recordingReady` и `page.evaluate` до чтения файла.
2. Файл ищется в папке загрузок напрямую (`readFile`), а не через `path()`/`saveAs()`: протокол умирает вместе с закрытой вкладкой, диск — нет.
3. Статус `failure()` учитывается, только если байтов на диске ещё нет.
4. Окно закрывается только после того, как файл прочитан и сохранён; пауз и таймаутов ожидания нет.

## Прерывание записи: `cancelled: Выгрузка отменена` при скачивании

**Симптом.** Пользователь нажимает «Скачать» в отчёте — окно закрывается, запись падает с `cancelled: Выгрузка отменена`, файл теряется.

**Причина.** Запись считалась завершённой только после копирования байтов через протокол. Закрытие окна до этого момента срабатывало в `context.once('close')` → `record.cancellation.abort()`, и чтение файла отвергалось с сообщением `Выгрузка отменена`, хотя файл уже был получен. Кнопка выгрузки часто «убивает» страницу, поэтому сценарий срабатывал почти всегда. Дополнительно `close()`, вызванный из самого процесса скачивания, навсегда «висел» на `await Promise.all([...finishing])` — здесь же лежала и задача, которая его ждала.

**Что сделано** (`workbench-browser-recorder.ts`):

* Закрытие контекста больше не обрывает копирование: `end()` ждёт завершения задач скачивания (с ограничением по времени), и только потом, если файл так и не был получен, поднимается ошибка.
* `close()` не закрывает уже закрытое окно (`context.pages().length === 0`) — повторное закрытие постоянного профиля не завершается никогда.
* `end()` идемпотентен, поэтому гонка «таймер + закрытие окна» больше не оставляет ожидающих.
* Текст ошибки стал точным: `Выгрузка прервана: окно записи закрылось до получения файла` — только для реально потерянного файла.

## Формат выгрузки: не только CSV/XLSX

Раньше файл принимался только с расширением `.csv` или `.xlsx`, иное имя давало `format: Ожидалась непустая CSV/XLSX выгрузка отчёта`. Если кнопка отчёта отдаёт `report.xls` (старый Excel) или `tsv`, файл отклонялся.

Теперь формат определяет сам отчёт: принимается любое расширение (1–8 символов), проверяется только то, что это непустой файл, а не HTML-страница входа. Тип содержимого проставляется по расширению (`text/csv`, `xlsx`, иначе `application/vnd.ms-excel`). Имя сохранения `ОКО_…<ext>` теперь копирует расширение источника вместо сведения всего к `csv`/`xlsx`.

Ограничение: разбор в таблицу по-прежнему умеет только CSV и XLSX — для `.xls` файл сохраняется и виден в «Мои выгрузки», но обогащение по нему не строится (оно и не входило в raw-only поток).

Регрессии: `keeps a finished download when the window closes before the file is copied`, `accepts an XLS export without narrowing the report format`.

## Прерывание записи: `configuration_required: Действие или locator не поддерживается записью`

**Симптом.** Сразу после скачивания файла запись падала с `configuration_required`, окно закрывалось, сценарий не сохранялся.

**Причина.** Скрипт записи в странице сообщает `{action:'unsupported'}`, когда у элемента нет устойчивого locator (например, кнопка выгрузки без `id`, `name`, `aria-label` и текста). Такой объект не проходит `recordedBrowserStepSchema`, и обработчик считал это фатальной ошибкой: `record.problem` выставлялся, а обработчик скачивания затем перебрасывал его через `if (record.problem) throw record.problem`, поэтому валидный файл отбрасывался.

**Вторая половина.** Даже без ошибки скачивание требовало, чтобы последним шагом был именно `click`. Если нажатие не записалось (страница проглотила клик, элемент без locator), приходила ошибка «Выгрузка не связана с записанным нажатием».

**Что сделано** (`src/features/connectors/workbench-browser-recorder.ts`):

* `unsupported` обрабатывается до очистки состояния и является пропуском в записи, а не сбоем: окно остаётся открытым, `problem` не выставляется, следующее действие пишется нормально.
* Скачивание принимается и без записанного `click`: шаг `download` добавляется сам, с locator маркера готовности отчёта. Если `click` записан — он, как и раньше, превращается в финальный `download`. Записей ровно одна, финальный шаг всегда один.

Регрессия: `workbench-browser-recorder.test.ts` → «treats an unaddressable element as a gap and still ends the recording on the download» (проверяет, что окно не закрылось, статус остался `recording`, а скачивание завершило запись с шагом `download`).

## Известные ограничения

* Ранее сохранённые результаты в «Мои выгрузки» не переносятся (сознательно).
* Обогащение справочником не входит в этот поток — отдельная задача; для неё достаточно сохранённых байтов и `sha256`.
* Список ограничен 20 последними выгрузками сценария в представлении; полный список доступен запросом `source.browser.exports`.
* Нативные браузерные наборы (`workbench-browser-picker/recorder/source`) в этом окружении не запускаются: нет установленного Edge (`npx playwright install msedge`).
